# BoS · резервне копіювання та чисте відновлення

Кандидат A10 зберігає узгоджену базу разом із документами, кодом і конфігурацією. Перед копіюванням керувальний процес припиняє приймати запити й очікує завершення вже прийнятих записів. Він утримує блокування установки до завершення процедури. Timeout або примусове переривання не дають дозволу на копіювання.

## Що входить до копії

- Native SQLite: усі 45 таблиць, ID/FK, версії, історія, точні Decimal, наступні номери та записи користувачів/прав/сесій.
- Усі приватні файли, включно з файлами без поточного посилання з таблиці; оригінальні байти і SHA-256.
- Повний перевірений пакет коду з версією і закріпленими залежностями, конфігурація та зібрана статика.
- Маніфест файлів і типізований звіт A07. Позначка COMPLETE публікується останньою; невдалі власні проміжні результати не видаються за готову копію.

Копія містить секрет та приватні дані конкретної компанії. Вона створюється у новому приватному каталозі поза кодом, компанією та реєстром інсталятора. Її не додають до репозиторію чи архіву вихідного коду. Готову копію команда не перезаписує.

## Чисте відновлення

Відновлення створює тільки нову установку в раніше відсутньому каталозі. Чинну установку або довільний наявний каталог вибрати для перезапису не можна. Код і залежності беруться з перевіреної копії; дані відновлюються після перевірки порожнього нового target.

До завершення всіх перевірок runtime залишається недоступним для керованого запуску. Перевіряються native SHA бази, таблиці, суми окремо за валютами, ID/FK, послідовності, оригінали, код і статика. Пізня помилка перевірки знімає ознаку готовності до звільнення блокування установки.

Нова установка отримує нові UUID, секрет і назву cookie. Збережені записи користувачів, ролей, сесій та історії залишаються точними; старі браузерні cookies не дають автоматичного входу. Після відновлення користувач входить знову. Після першого нового входу база закономірно змінюється через нову сесію — точний SHA перевіряється до цього входу.

## Автоматична репетиція

З каталогу BoS, з підготовленими runtime prerequisites A09:

```bash
BOS_SERVER_WHEELHOUSE=/srv/bos-wheels \
BOS_CADDY_BIN=/srv/caddy \
python3.12 scripts/check_restore.py --output /srv/restore-check.json
```

Команда сама створює власну синтетичну компанію і тестовий TLS-сертифікат. Перевіряє реальний HTTPS-вхід, контрольовану зупинку, копію, нову установку, повторний запуск оригіналу та HTTPS-вхід/документ після відновлення. Пошкоджену копію, наявний target і пізню відмову перевіряє окремо. Шляху до робочої бази серед її параметрів немає.

Канонічна репетиція 12.09.2026 пройшла 10/10. На першому малому стенді копія створилася за 4.804 с, відновлення за 29.393 с; це не SLA і не оцінка великої робочої бази.

## Команди оператора

Реальний CLI кандидат пройшов 8 сценаріїв на власній тестовій установці. Full verify виправлення stdin завершено: SQLite 151+5+442 та критерій 7 пройшли; загальний результат червоний через відкриті умови, це ще не реліз.

Копія зупиненої власної установки однією командою:

```bash
python3.12 scripts/maintenance_server.py backup \
  --target /srv/bos-company --registry /srv/bos-installer-registry \
  --installation-id UUID --destination /srv/bos-backups/new-copy \
  --caddy /srv/caddy --certificate /srv/tls/localhost.crt \
  --private-key /srv/tls/localhost.key --ca-certificate /srv/tls/local-ca.crt \
  --http-port 8080
```

Команда перевіряє власний запуск через TLS, завершує прийняті запити, створює копію й зупиняє створені нею процеси. Якщо інший керувальний процес уже працює з цією установкою, команда відмовляє.

Для живого керованого сервера використайте `serve` з тими самими параметрами компанії/TLS, без `--destination`, і додайте `--control-stdin`. У цьому терміналі можна передавати по одному JSON-рядку:

```json
{"action":"status"}
{"action":"backup","destination":"/srv/bos-backups/new-live-copy"}
{"action":"resume"}
{"action":"stop"}
```

Після успішної копії сервер залишається зупиненим до явної `resume`. Невдале копіювання теж не запускає його автоматично. `stop`, закриття stdin або SIGINT/SIGTERM завершують тільки власні процеси з очікуванням записів. Без `--control-stdin` команда `serve` працює у foreground і завершується сигналом. Новий мережевий API керування не відкривається.

Відновлення лише в новий раніше відсутній каталог:

```bash
python3.12 scripts/maintenance_server.py restore \
  --source /srv/bos-backups/new-copy --target /srv/bos-restored \
  --registry /srv/bos-installer-registry --origin https://localhost:9443 \
  --wheelhouse /srv/bos-wheels
```

Звіт `complete=true` цієї команди обмежений даними та кодом (`scope=clean_restore_data_and_code_only`). `post_restore_http_verified=false` прямо вказує, що відновлену програму ще треба запустити. Повна автоматична репетиція вище окремо перевіряє реальний HTTPS-вхід після restore. Для нового origin потрібен відповідний TLS-сертифікат.

## Межі поточного стану

Працює керування всередині одного процесу на перевіреному Linux. Unix IPC не прийнято через EPERM; нових мережевих каналів керування немає. Перевірки Windows і PostgreSQL відкриті.

Перемикання поколінь, оновлення N → N+1, rollback після оновлення та відновлення після знеструмлення не прийняті. Типізований файловий descriptor не є дозволом запускати нове покоління. A10 загалом і повний MVP не прийняті; усі 11 критеріїв залишаються обов’язковими. Відомий дефект A09 для запиту 13 MiB збережений як непройдений.
