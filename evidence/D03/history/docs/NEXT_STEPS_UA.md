# Актуальний статус після ERP-розширення

ERP для локальної демонстрації вже реалізована. Перелік функцій та межі — у `ERP_GUIDE_UA.md`. Подальший пілот: узгодити реальні довідники, одиниці виміру, комплект документів, ролі й критерії приймання; перевірити відтворення процесу на 3–5 реальних погоджених замовленнях. Сервер, облікові записи, автоматичні інтеграції й повний бухгалтерський облік залишаються окремими етапами.

Нижче збережено попередній план; пункти щодо створення локального ERP тепер слід читати з урахуванням наведеного статусу.

# Наступні кроки BoS

## Найближчий пілот

Мета — продати й перевірити обмежений процес промислових закупівель на наданому клієнтом прикладі. Вхід: 3–5 погоджених комплектів, відповідальний закупівельник та інженер, еталон правильного порівняння. Вихід: RFQ, таблиця вартості й виключень, список уточнень, погоджені доручення. До старту погодити оплату й обсяг пілота, доступ до документів, спосіб приймання та що вважається зміною обсягу.

Вимірювати час на один комплект, частку правильно витягнутих обов’язкових полів, кількість виправлень людиною, наявність джерела для кожного висновку та успішне збереження доручень. Цільові значення погодити на еталоні; не оголошувати економію до вимірювання базового процесу.

## Майбутній виділений сервер

Поточний локальний запуск не слід просто відкрити назовні. Спочатку потрібні справжній вхід, організації та серверна перевірка доступу на кожному API, файлі, чаті, пошуку й дорученні. Демонстраційний вибір ролі слід прибрати з робочого сервера. Це окремий критерій готовності, а не зміна назви ролі.

Цільова структура: reverse proxy з HTTPS → WSGI/ASGI-застосунок Django → PostgreSQL; приватне сховище документів; резервні копії з перевіркою відновлення; журнал подій, помилок і доступності. Черга фонового виконання потрібна після появи OCR, довгих імпортів або синхронізацій. Секрети передаються через захищене оточення; production-конфігурація повинна відмовлятися стартувати без потрібних параметрів.

Сервер застосунку з API зовнішньої моделі та сервер, який виконує локальну модель, — різні конфігурації. Для першого потрібні мережевий доступ до API та контроль витрат. Для другого окремо вимірюються пам’ять, продуктивність, якість і паралельність моделі на наших сценаріях. Розмір обладнання та бюджет визначати після цих вимірювань.

Підготовка до запуску: міграція тестової копії → перевірка прав між двома клієнтами → ізольовані файли й пошук → відмова/тайм-аут моделі → дубль/конфлікт погодження → відновлення резервної копії → браузерне приймання → окреме рішення про публікацію. Сервер, домен та підписки для цієї збірки не замовлялися.
