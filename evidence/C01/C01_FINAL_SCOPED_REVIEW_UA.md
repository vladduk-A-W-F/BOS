## Прийнята поведінка

- Employee FK і SalesOrder FK додані без переписування історичних assignee, ідентифікаторів, дат чи статусів. Старі чотири нові поля залишаються NULL; зв’язки захищені від видалення. Архівування зберігає Task та його історію.
- Зміни йдуть через preview, явне підтвердження та атомарний Task/Audit/receipt. ERP mutex береться до доменних читань, Task та відповідні Employee блокуються в узгодженому порядку. Права, джерела й fingerprint перевіряються знову; SQL-помилка відкочує весь ефект. Повтор повертає той самий результат без нового запису.
- Результат завершення, причина та before/after diff зберігаються. Reopen залишає попередній результат. Звичайна чернетка active/process може зберігати короткий literal текст, але завершення й виправлення завершеного результату вимагають придатного тексту та Employee FK.
- Видимість охоплює поточне замовлення й усі історично пов’язані джерела. Переприв’язування або unlink не стирає історичний контроль доступу. Історія має whitelist, підписану пагінацію та повторну перевірку прав; довільний legacy payload не видається.
- Owner receipt lookup дозволяє читати результат після нового входу, але не виконувати підтвердження старої сесії. Pending/expired не видається за доказ відсутності паралельного commit. Прямі REST-зміни й технічний admin не обходять погодження.
- Активні, архівні та прострочені доручення обчислюються спільними scoped queries; реальний нуль не підміняється демо-значенням. Історичний persisted status не переписується під час читання.

Очікування явно зафіксовані, не генеруються з фактичного результату.

Чотири старі історичні методи B01/B02/B03 мають буквально незмінні тіла після вилучення лише трьох нових рядків wrapper. Це перевірено незалежним AST-вибором функцій та побайтовим порівнянням тексту з checkout до інтеграції. Wrapper виконує саме старий метод у новому синтетичному subprocess, перевіряє exit/один тест/OK та ізолює фізичний DDL. Нічого не очищає у заповнених source snapshots. Для B03 стару Task schema дозволено лише після доказу відсутності нових Task-полів. Старі відмови rollback, high-water та точний schema/row/sequence oracle збережені; actual дочірні виконання є у фінальному логу. Поповнений typed transfer залишається **53 таблиці**, з legacy NULL, новими FK/result/archive і receipts.

Адаптації старих Task API тестів переводять позитивні записи на погоджені команди та додають перевірку відмови raw write; старі змістовні read/validation assertions збережені. `check_original.py` додає три перевірки, тому його майбутній загальний лічильник не слід називати незмінними 151. Цей інтеграційний запуск належить full24.

Access: старі **177** definitions та **57** field IDs збережені, стало **180** definitions. Результат є складеним: **730/774** у першому проході плюс повтор **саме 44/44** проблемних ключів; це не новий суцільний запуск 774. ## Native restore: окрема прийнята перевірка

Другий фактичний запуск `native-2.json`: **16/16, complete=true**, SHA-256 `3550c6189246f7fb1ae431ddb66d7bd4260d69b3f4bf1b154b30c0302683ca07`. Старі 14 сценаріїв і exact 53 таблиці збережені; додано 2 сценарії Task. Чотири Task включають 2 legacy з NULL та 2 нові; 6 receipt переходів дають історії 4 і 2. FK, result, archive та повна історія збігаються після чистого native restore, state SHA-256 `551364c0f3ea62ef611a453bd3b86c208066ed806a3c8c0a3bc2bd5532a092f0`. Нова сесія читає власні 6 receipts; виконання старої сесії повертає 403; нових бізнес-ефектів немає. B03 повний snapshot і 7 повторів також залишилися точними. Початкова резервна копія незмінна; це підтверджено збереженим actual report, без її читання рецензентом.

Перший native запуск зупинився після 12 успіхів: root зберіг B03 whole-snapshot до додавання Task, хоча home.tasks є частиною цього snapshot. Мій початковий source review пропустив цю залежність. Мінімальна виправлена послідовність — Task populate перед B03 populate після імпорту — залишає всі старі буквальні порівняння; product backup/restore не змінено. Raw red і попередній source збережені, другий actual запуск підтвердив виправлення.

Native16 виконано на core checkpoint `200649439f2ba89c5e4583d00c5a9a1059ab5329bf46d1e0fe3bdf29d5ffbb54`, до останнього захисту malformed assignee_id. Ця вузька зміна views включена у final55 та остаточні SHA; повний інтегрований proof очікується від full24. Не приписуємо native16 пізніший source.

## Межі прийняття

У цьому scope блокерів не залишилося. Погоджено інтеграцію exact SHA кандидата та обов’язковий full24. Висновок не підтверджує браузерний інтерфейс, PostgreSQL, Windows, CI, готовність production або всього MVP. A10 activation/upgrade/rollback та інші відкриті загальні gates цим висновком не закриваються. Відома нестабільність A09 13 MiB не досліджувалася й не оголошується виправленою. Попередні незмінні звіти збережено окремо.
