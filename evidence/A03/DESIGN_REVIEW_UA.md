# A03/A04: ідентичність і серверні права BoS

Вузький read-only огляд поточного checkout: settings, middleware, URLconf, API/admin, proposal/confirm, context builders і bootstrap перевірок. Бази не відкривав, код не змінював. Додатково прочитано `/workspace/scratch/c7b51e996a9f/output/BoS_Plan_Pack_UA/docs/ACCESS_AUDIT_UA.md`: це **конкретна маршрутна матриця**, а не лише аудит. Її §5 містить64 унікальні API patterns, §5.1 —26 ERP actions, §6 —95 admin patterns, §6.1 —4 заплановані auth routes. Ці числа — результат resolver автора від10.09, а не новий прогін цього огляду. Нижче дизайн узгоджено з цією матрицею; перед прийманням перевірити фактичний resolver після змін.

Поправки до початкового draft після знаходження матриці: Employee.user має SET_NULL, не запропонований мною PROTECT; working role setter —404, не403; manager має відфільтрований GET Transaction, а observer його не має; масовий export потребує окремої capability і недоступний observer; CEO-only ERP actions включають opening/payment, а не лише три вже захищені дії. Збережено прийняті ceo/manager/observer та окремий технічний admin без автоматичного staff для бізнес-ролі.

## A03 — мінімальні зміни

1. Залишити Django User. Додати до Employee nullable OneToOne `user` з **SET_NULL**, як у §3 попереднього плану, і `related_name='employee'`. Усі Employee/Salary/ERP ID та зовнішні ключі зберігаються. Вилучення доступу — деактивація User, а не видалення Employee. Існуючі рядки не зіставляти автоматично за ПІБ/email. Окрема команда прив’язує **явно вказані** user_id/employee_id, відхиляє повторне суперечливе зіставлення й журналює результат. Нові облікові записи не отримують роль із текстового Employee.role.
2. Один серверний resolver `actor(request)`: active Django User, його явний Employee-зв’язок за наявності, рівно одна група з ceo/manager/observer. Немає групи або кілька бізнесових груп → явна відмова. Попередня матриця не вимагає, щоб кожен технічний/керівний User був штатним Employee; не вводити цю додаткову заборону для всіх endpoint. Для inspection/operator потрібен реальний actor та дозволений Employee; довільний inspector_id/operator_id не є повноваженням. Технічний admin — окреме явне призначення, не неявний fallback CEO. Архівування прив’язаного Employee має припиняти його робочий доступ, навіть зі старою сесією.
3. Увімкнути SessionAuthentication та IsAuthenticated за замовчуванням у DRF; для звичайних Django views використати той самий resolver/permission helper. Зараз DRF має authentication=[], AllowAny; Django middleware бачить User, але цього недостатньо для DRF. Додати справжні login/logout/current-user і стандартний CSRF, включно з multipart та входом. На вході/виході змінюється session key, token і client повторно отримує актуальний CSRF cookie.
4. Зберегти заплановані `/api/auth/{csrf,login,logout,me}/`. Anonymous csrf bootstrap не читає організацію й не надає CEO. GET operations/status у робочій матриці захищений; demo status може показати тільки стан входу до demo-start. У working роль завжди береться із User, а `/api/operations/role/` відсутній у server URLconf та повертає**404** для всіх методів незалежно від payload чи старого `bos_role` у session. Login API не приймає group/role/employee_id як права від клієнта.
5. Навчальний запуск залишається локальним і без введення пароля: окремий POST початку demo-сесії входить у **справжнього синтетичного User**; інтерфейс може виконати цей явний demo-start під час завантаження. Перемикач ролі входить у інший demo User, а не змінює групу одного спільного користувача. Дозволено лише demo, loopback і підтверджений synthetic dataset; робочий профіль відмовляється запускатись із demo identity/secret/AllowAny. Demo-кнопка не є production login.
6. ActionProposal доповнити автором User, зберігши session binding. Confirm повторно перевіряє автора, сесію, актуальні права й область об’єктів **до повернення receipt**, зокрема при replay. Старі пропозиції без автора потребують нового preview; не вгадувати їхнього власника. Audit зберігає actor_id, роль і джерело команди. Зміна ролі/logout не залишає придатний до виконання старий токен погодження.

## A04 — одна матриця й спільні проєкції даних

Розділити permission для дії, queryset для видимих об’єктів і явний перелік видимих полів. API, пошук, export, assistant і admin використовують ці самі правила. Не приховувати JSON-поля лише у frontend. Django permissions доповнюють бізнесову роль; сам is_staff не надає доступ до зарплат. Не робити manager/observer superuser для доступу до admin.

У поточному `boss_project.urls` DEBUG може додати `/media/...`; у working цей прямий шлях не має обходити документну авторизацію. Також перевірити JS/localStorage: після logout/зміни користувача прибирати кешовані приватні відповіді, не лише змінювати меню.

Матриця має дві конкретні межі, які не слід мовчазно змінювати. По-перше, Transaction manager GET Ф стоїть поруч із приміткою «фінансові записи тільки CEO»: зберегти сам GET як дозволену скорочену операційну проєкцію, явно зафіксувавши whitelist полів і виключення salary source/довільного description. Повний ledger і мутації — CEO. По-друге, старий §6 пропонував blanket read-only admin, але master v2.1 вимагає дієвих спільних команд і архівування через канонічні admin місця. Бізнес-ролі досі не мають автоматичного staff; явно уповноважений технічний admin може використовувати вже захищені A05 команди. Не скасовувати ці функції, щоб повернутися до старого blanket disable. Журнали лишаються незмінними; auth керування — окрема capability. Так само позначка «вимкн.» старого AI — стан залежності адаптера, не дозвіл назвати gate4 зеленим від одного404/503.

Окремі інсталяції перевіряються двома synthetic DB/secret/media/cache namespace: cookie A не авторизує B; маркери B не з’являються у A. Однакові числові PK у різних інсталяціях допустимі — не вимагати404 на pk=1, якщо у поточній A законно існує власний pk=1. Це зберігає прийняту архітектуру без нового shared-DB tenant шару.

Практичні пастки контексту: `_build_*_context` зараз має глобальні `ctx_tasks`, `ctx_employees`, `ctx_finance`; ChatHistoryView читає/видаляє загальну історію; operations.export робить прямі values()/snapshot; audit віддає сирий payload. Найменша безпечна реалізація спочатку прибирає кешування приватного контексту або вводить user+scope+permission-version ключі з інвалідацією. Кеш не повинен зберігати доступ після пониження ролі. CEO→manager→observer і зворотний порядок треба перевірити на прогрітому кеші. Текст документів — дані; системний prompt не може замінити фільтрацію перед передачею моделі.

## Як зберегти справжні 151+5 та зробити нові перевірки чесними

- 151 — це 22 workspace +49 ERP +48 operations +32 original. Їхні бізнесові assertions і очікувані кількості не змінювати. Окремим поясненим diff замінити **передумову** anonymous Client на справжній demo login: спільний test helper входить через реальний auth/demo endpoint із CSRF, перевіряє User/Employee/groups. Після seed прив’язати до вже наявних synthetic Employee; не додавати сьомого працівника всупереч assert count=6. Для original без seed можна створити ізольовану identity fixture, перевіривши, що вона не змінює суті перевірених вибірок.
- Кожен `other=client()` входить окремою сесією; перевірка чужого proposal залишається403. Demo role endpoint для observer→manager→ceo має змінювати справжню demo identity; існуючі observer GET200 та write403 залишаються. У working role route404 за прийнятою матрицею. Не патчити Django Client, не використовувати force_authenticate і не додавати runtime allowlist для тестів.
- П’ять launcher tests лишаються без змін. Launcher не є доказом authentication і Windows. Якщо новий auth вплине на запуск, змінювати launcher з реальним smoke входу, не підміняти status/login відповідь.
- Поточний invariant `anonymous=client()` сам викликає GET status. **Не робити auto-CEO на GET status:** це знищить анонімний контроль. Role fixtures створюють і справді login User↔Employee; після login довести їхній actor, не встановлювати `bos_role` як джерело прав. Позитивний CEO контроль мусить бачити seeded salary. Усі п’ять наборів лишаються ≥1000; не зменшувати обхід до403 чотирьох маршрутів.
- Gate4 генерує каталог із `get_resolver()` і `admin.site.get_urls()` після django.setup на новій synthetic DB; враховує DRF action/method mapping і format suffix. Для кожного concrete URL є fixture існуючого об’єкта й запис у матриці. Новий/невідомий маршрут, непротестований метод, невирішений converter або лише404 замість перевірки існуючого об’єкта → red, не skip. HEAD перевіряє також headers; OPTIONS/browsable HTML не має віддавати приватні значення/choices.
- Кожна роль отримує реальні cookies через login; negative контроль — anonymous, inactive, відсутня/неоднозначна роль, manager/observer, підроблений bos_role/payload, застаріла сесія після revoke. Відсутній Employee link окремо перевіряється для дій, що потребують дозволеного inspector/operator, не як вигадана blanket заборона. Обов’язкові positive контроли дозволених дій, щоби тотальна заборона всього не дала green. Перевіряти рекурсивно JSON, HTML, тексти export, streaming bytes, файл/назву вкладення, пошук, admin історію та cache із синтетичними унікальними salary/contact/document маркерами незалежно від HTTP status. У відповідях помилок приватних значень теж не має бути.

Необхідні зміни auth-preconditions у наявних тестах документуються окремо за §6 master; їх не рахувати новими тестами замість151. Обидві СУБД потрібні для висновку. A03 можна прийняти після identity/login/session/mapping тестів; A04 та gate4 — лише після повної матриці, приватних проєкцій і позитивних контролів. Відсутня політика/покриття лишається явно червоною, а не прихованою за неактивною LLM або закритим admin.
