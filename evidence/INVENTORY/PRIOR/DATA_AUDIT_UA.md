## Реальні відкриті ризики PostgreSQL та порядок блокування

`operations/service.py:93` перевіряє fingerprint **до** mutex у dispatch; `before=snapshot()` на 102 також виконується раніше. На READ COMMITTED два різні погодження можуть обидва перевірити старий fingerprint, потім послідовно виконатися. Приклад: дві погоджені корекції +1 для партії10; друга виконає 11→12, хоча перегляд показував10→11. Ризик стосується семантики погодження та атрибуції impact, навіть коли залишок арифметично правильний. `erp/views.py:21` теж читає fingerprint і before до mutex. PostgreSQL-відтворення обов’язкове, зараз це аналіз коду.

CAS `ActionProposal.receipt IS NULL` на `operations/service.py:95` вже захищає одну пропозицію від подвійного claim. Не називати це відсутньою ідемпотентністю. Окремо перевірити різні пропозиції, однаковий ключ платежу, прострочення, rollback/retry. Паралельне збереження документів (`operations/views.py:91–95,220–225`) обходить ERP-mutex; на PostgreSQL нова версія може з’явитися між перевіркою чинності документа й відвантаженням.

Рекомендований перший серверний варіант: зберегти один mutex на інсталяцію, створювати його міграцією, отримувати **до** всіх залежних читань, fingerprint та знімків. Єдиний порядок: mutex → ActionProposal → батьківські сутності → дочірні записи → рухи/аудит/receipt. Застосувати контракт до всіх змін, які впливають на ці читання; окремо закрити фінансові записи поза dispatch. Поточне JSON revision може втрачати інкремент на PostgreSQL після очікування, хоч блокування працює; воно ще не є надійним лічильником версій.

Лише після вимірювання черги mutex переходити до рядкових блокувань. Тоді зафіксувати повний порядок типів: Document/Item → SalesOrder → SalesLine → Production → Purchase → Invoice/Salary → Lot → Reservation; усередині типу PK за зростанням. Спочатку зібрати всі залежності, після блокування перечитати й перевірити; не захоплювати пізніше «попередній» тип. Для створення нової версії документа потрібен сталий батьківський рядок сімейства або окремий ключ блокування: блокування лише старої Document не забороняє INSERT нової. Це проєктний порядок, потребує перевірки всіх writer-шляхів та FK-взаємодій тестами.

## Обмеження й індекси БД

Вже є PK, UNIQUE кодів, UNIQUE Document(code,revision), індекси FK, чотири ERP CheckConstraint, включно з `erp_nonnegative_reserve`, якого не перелічено в пакеті (`erp/models.py:39,59,85`; міграція `erp/0001_initial.py:226–240`). Немає підстав оголошувати всі FK неіндексованими.

Додати після аудиту наявних даних: `0≤received≤quantity` та quantity>0 для Purchase; `0≤produced≤quantity` для Production; `0≤invoiced≤shipped≤quantity` для SalesLine; `0≤paid≤amount` для Invoice; невід’ємні ціни/витрати там, де це правило домену. Поточні release лишають нульові Reservation, тому `quantity>0` несумісне без зміни поведінки. Унікальний scalar ключ внутрішнього платежу/нарахування винести з JSON або додати окрему типізовану сутність; зберегти поточну область унікальності до продуктового рішення.

Sum(Reservation.quantity)≤Lot.quantity і рівність залишку сумі Movement не можна надійно реалізувати звичайним рядковим CHECK. Перший рівень: єдиний write-сервіс, блокування батьківської Lot, звірка інваріантів. Якщо потрібна гарантія для довільного SQL — окремо проєктувати транзакційні тригери/канонічний баланс; сам додатковий кеш reserved без підтримки узгодженості проблеми не вирішує.

Кандидати на індекси, підтвердити EXPLAIN на обсязі пілота: Document(code,id DESC); Reservation(production_id,lot_id) та (line_id,lot_id); Movement(line_id,kind,lot_id) і (line_id,kind,reference); Purchase(item_id,due_date) із фільтром відкритих замовлень; Production(line_id,status); ActionProposal(expires_at) для очищення. Унікальний payment reference має пріоритет над довільним GIN на всі JSON. Індекси не усунуть повні читання таблиць у fingerprint/snapshot (`erp/service.py:140–144`, `erp/queries.py:51–81`).

## Міграція та B5

У встановленому Django `db/backends/postgresql/base.py:101,115,317` підтверджує `BinaryField→bytea`, `JSONField→jsonb`, типовий READ COMMITTED. BinaryField серіалізується base64 (`db/models/fields/__init__.py:2718–2725`); це не автоматична втрата вмісту. Реальні задачі переносу:

- Узгодити валідацію з SQL-типами. **Відтворено:** erp_invoice приймає code довжиною31 і SQLite зберігає його, тоді як Invoice.code має max_length30 (`erp/service.py:74–75`, `operations/models.py:58`). PostgreSQL обмеження varchar(30) цю вставку відхилить; там це ще не запускалося. Перевірити й Decimal-межі: `money_total` дозволяє до 13 цілих цифр, Invoice.amount — лише12 (`operations/models.py:60`).
- JSON: перевірити типи чисел/рядків/boolean, NULL проти JSON null, вкладені ID, некоректні Unicode/NUL і числові межі jsonb. Перестановка ключів jsonb не повинна змінювати бізнесову логіку; не порівнювати сирий JSON-текст. На копії перевірити ORM lookup `payload__reference`.
- Додати серверну DB-конфігурацію й PostgreSQL-драйвер; зараз DATABASES жорстко SQLite (`demo_settings.py:11`), psycopg відсутній у requirements. Застосувати Django migrations, а не SQLite SQL dump. Перенести PK/FK, timestamps, версії, decimal values; скинути sequences; перевірити orphan FK, унікальність, контрольні суми, кількості та інваріанти. Прострочити старі сесії/незавершені погодження після переключення.
- Оригінальний db.sqlite3 має 23 таблиці і не містить ERP; поточна BoS_Demo.sqlite3 має44. Отже, потрібні окремі репетиції upgrade копії оригіналу та переносу наповненої ERP-копії. Міграція лише порожньої бази не є прийманням.
- Документи: зберегти IDs, code/revision, checksum, status, text/sections і контрольовану приватну видачу. Новий об’єкт файлу — незмінний ключ, staging→перевірка checksum→атомарний запис метаданих; після rollback прибирати сирітські staging-об’єкти. Старий BLOB видаляти лише після перевіреної копії та можливості відкату.
- У поточній демо-базі16 Document, усі `content` порожні; їх checksum рахується від text.encode() у seed, а download має той самий fallback (`operations/views.py:85–87`). Це треба зберегти при експорті. Для приймання потрібні також реальні непорожні BLOB, різні версії й граничні розміри. Upload уже обмежено10 MiB (`operations/documents.py:4–18`).
- Список/пошук документів завантажує всі моделі разом із content (`operations/views.py:69`). Спершу виключити BLOB із читань метаданих і виміряти пам’ять; приватне файлове сховище на одному сервері є достатнім початковим варіантом, окремий сервіс не потрібний.

## Оцінки і критерії приймання

Оцінки планові, у людино-днях, включають реалізацію та цільові перевірки, не є результатом вимірювання продуктивності команди.

| Робота | Залежності | Оцінка | Приймання |
|---|---|---:|---|
| Два локальні P1 | Немає | 2–3 | Нові відтворення до виправлення демонструють дефект, після — точний залишок і одна Transaction; наявні перевірки збережені. |
| Порядок mutex, погоджень, повторів, документних змін | Рішення щодо серверних прав; локальні P1 | 4–6 | Дві транзакції на реальному PostgreSQL для всіх10 операцій; stale fingerprint не виконується; receipt/impact відповідають одній дії; deadlock/retry мають визначену поведінку. |
| DB-інваріанти, payment key, цільові індекси | Узгоджені write-шляхи | 2–4 | Невалідні рядки відхиляє DB; повтор платежу не дублює факт; EXPLAIN та звірка агрегатів на даних пілота. |
| Перенос SQLite→PostgreSQL і граничні типи | Конфігурація/права, інваріанти | 3–5 | Дві репетиції на копіях: legacy upgrade і ERP data; контрольні суми документів, точні суми/кількості, FK, наступний INSERT після sequence reset; rollback план перевірено. |
| Перехід RFQ→Purchase | Продуктове рішення B3, write-контракт | 4–6 | Одна підтверджена quote створює один передбачений результат при повторі; Purchase/Request/quote/прихід узгоджені; часткові правила явно прийняті. |
| Приватні файли і перенос версій | Права читання, DB-схема, копіювання | 3–5 | Повний checksum match для всіх версій, завантаження після переносу, отказ/rollback без втрати оригіналу; метадані не читають BLOB. |
| Резервування та фактичне відновлення | Обрані БД і файлове сховище | 2–3 | Відновлений ізольований екземпляр проходить звірку документів, рухів, резервів, рахунків; заміряні час відновлення й остання відновлювана зміна. |

До переходу на дрібні рядкові блокування немає потреби додавати цей окремий етап у критичний шлях: спершу виміряти, чи глобальний mutex обмежує погоджене навантаження.

Резервні копії вже є перед локальними міграціями через SQLite backup API (`scripts/start_local.py:101–107`); це не розклад і не доказ відновлення. Для пілота запропонувати погоджувані цілі RPO≤1 год, RTO≤4 год; щогодинні узгоджені DB-копії, щоденна окрема зашифрована копія, обов’язкова копія перед випуском, щотижнева автоматична перевірка відновлення та щомісячна повна репетиція. Для PostgreSQL зі суворішим RPO — base backup + WAL/PITR. Для файлів потрібен сумісний manifest/версії, тому DB-backup окремо недостатній. У цьому аудиті повне відновлення клієнтської бази не виконувалося; запропоновані RPO/RTO ще не доведені.

## Перевірені зовнішні джерела для технічних висновків

Офіційні джерела, переглянуті10.09.2026; висновок про конкретний BoS залишається аналізом його коду:

- PostgreSQL row locks: [джерело](https://www.postgresql.org/docs/17/explicit-locking.html) — UPDATE отримує row lock і конфліктує з іншим UPDATE того самого рядка.
- PostgreSQL READ COMMITTED: [джерело](https://www.postgresql.org/docs/current/transaction-iso.html) — послідовні SELECT можуть бачити різні committed snapshots.
- Django6 fields: [джерело](https://docs.djangoproject.com/en/6.0/ref/models/fields/) — підтримка JSONField/BinaryField, jsonb і індексація.
- PostgreSQL JSON: [джерело](https://www.postgresql.org/docs/current/datatype-json.html) — типові відмінності та обмеження jsonb.
- PostgreSQL constraints: [джерело](https://www.postgresql.org/docs/current/ddl-constraints.html) — CHECK не гарантує агрегати інших рядків.

Результат аудиту — **план із підтвердженими дефектами та межами доказів**. Не серверне приймання, не твердження про відсутність інших помилок і не завершена міграція.
