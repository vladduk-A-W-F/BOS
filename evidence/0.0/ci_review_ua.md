# BoS · незалежна перевірка каркаса 0.0

Дата: 11.09.2026. Джерела: master v2.1, п'ять `scripts/check_*.py`, `demo_settings.py`, команди синтетичного наповнення. Це перевірка коду та рекомендації; CI, PostgreSQL, Windows і браузер цим оглядом не запускалися. Checkout не змінено.

## Висновок

Каркас повинен залишатися червоним, доки немає реальних доказів усіх 11 пунктів. Передавання `DATABASE_URL` наявним scripts саме по собі не запускає PostgreSQL: чотири функціональні scripts перезаписують `DJANGO_SETTINGS_MODULE` на `demo_settings` та `DATABASES.default.NAME` на `:memory:`. Їхні перевірки треба зберегти, адаптувавши тільки початкове налаштування тестової БД.

| Script | Чинний обсяг | Особливість середовища |
|---|---:|---|
| `check_workspace.py` | 22 | SQLite у пам'яті; SHA локальної `db.sqlite3`; синтетичний ERP |
| `check_erp.py` | 49 | SQLite у пам'яті; SHA локальної `db.sqlite3` |
| `check_operations.py` | 48 | SQLite у пам'яті; SHA локальної `db.sqlite3`; завантаження файлів |
| `check_original.py` | 32 | SQLite у пам'яті; читає HTML відносно `__file__` |
| `check_launcher.py` | 5 | Моки subprocess/venv; це регресія launcher, а не чиста установка |

Сума 151 + 5 — кількість іменованих перевірок у чинних сценаріях, а не кількість усіх операторів `assert`. Нові тести додаються понад цей обсяг. Потрібен звичайний послідовний subprocess-запуск: pytest сам не виконає цей набір як 156 тестів.

## Безпечне підключення без зміни assertions

1. Створювати окрему тимчасову копію дозволених джерел і явно синтетичних fixtures. Не копіювати `db.sqlite3`, `BoS_Demo.sqlite3`, робочі БД, media, резервні копії, секрети або весь `evidence/` за маскою. `.gitignore` не видаляє вже відстежувані файли: перед зовнішнім push перевірити `git ls-files`.
2. У тимчасовій копії створювати нову порожню SQLite `db.sqlite3` як контрольний синтетичний файл для трьох чинних перевірок SHA. Зберегти ці assertions і явно написати в доказах, що перевірено контрольний файл, а не реальні дані. Справжня локальна звірка — окремо в 0.5. `MEDIA_ROOT` також винести до тимчасового каталогу, інакше `check_operations.py` залишає файли в checkout.
3. Замінити лише bootstrap налаштувань у чотирьох scripts спільним `test_settings`/helper. У `evidence/0.0/` пояснити зміну середовища та зафіксувати незмінність тіла кожного сценарію, наприклад SHA відповідної частини файлу. Не мокати ORM, SQL, команди продукту чи `django.setup`. Не трансформувати assertions під час запуску.
4. Кожен script має отримувати нову БД: власну SQLite або власну PostgreSQL DB/схему. Об'єднання сценаріїв у спільній заповненій БД порушить їхні фіксовані ID й counts. Для PostgreSQL потрібен реальний драйвер, `ENGINE=django.db.backends.postgresql` та явні параметри ізольованого сервісу; перед `migrate` перевірити `connection.vendor`, назву БД і реальну `server_version`. Помилка підключення повинна завершувати перевірку червоним, без fallback на SQLite.
5. Заборонити оптимізований Python (`sys.flags.optimize != 0`), інакше більшість чинних assertions зникне. Для Windows встановити `PYTHONUTF8=1` та UTF-8 для subprocess stdout. Зберігати повний stdout/stderr, код завершення, фактичні counts, Python/ОС/СУБД та SHA джерел; не видавати старі `docs/TEST_*.json` за поточний прогін.

## Чесний PostgreSQL

`seed_bos_demo.py` задає `Task(id=i+1)` явно, а наступні дії створюють Task з автоматичним ID. У PostgreSQL це може залишити sequence на початку й дати конфлікт ключа. Цей випадок тут не запускався. Якщо відтвориться, потрібне окреме виправлення джерела наповнення з доказом; не можна приховувати його reset-sequence тільки у harness. Аналогічно не обходити знайдені PostgreSQL помилки довжин або типів. Каркас 0.0 може чесно показати їх червоними.

## Windows та агрегування

Manual job без ранера повинен мати явне `allow_failure: false`; залежність `verify-full` від його артефакту не має бути `optional`. Відсутній обов'язковий Windows-прогін означає заблокований конвеєр або червоний локальний агрегатор, ніколи готовий реліз. Пункт 11 посилається на 1–3 і 6, тому Windows-докази також повинні охоплювати SQLite та PostgreSQL, ≥1000 прогонів кожного інваріанта й точний E2E. П'ять mock-тестів launcher цього не замінюють.

Агрегатор перевіряє повний перелік gate ID 1–11, обов'язкові комбінації ОС/БД, успішні коди дочірніх команд і докази саме поточного commit/pipeline. Відсутні, `НЕ РЕАЛІЗОВАНО`, `НЕ ЗАПУЩЕНО`, чужий SHA або неповний артефакт — ненульовий результат. Локальний компонентний job може пройти власну перевірку; `verify-full` не можна називати успішним на підставі такого часткового результату. `artifacts: when: always` зберігає докази й для червоного job. Bash має передавати помилку subprocess через pipefail; PowerShell — перевіряти `$LASTEXITCODE`.

Без GitLab remote/API доступу шаблон та локальний запуск не підтверджують приємання 0.0 «конвеєр запущено в GitLab». Треба прямо записати `НЕ ЗАПУЩЕНО (немає підтвердженого репозиторію/доступу)` та залишити місце для справжньої URL, а не створювати посилання за припущенням. За master v2.1 незапущений зовнішній пункт не означає green і сам по собі не зупиняє решту дозволеної роботи.
