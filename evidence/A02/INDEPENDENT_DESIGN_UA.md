11.09.2026. Обмежений read-only огляд diff A01 і коду зарплат. Checkout не змінено. Власного повторного запуску шести регресій, PostgreSQL або Windows у цьому огляді не було.

## A01

Блокувальних дефектів у розглянутому diff не знайшов. `finish` повторно використовує один Lot на `lot_id`, тому другий резерв списується з уже зменшеної кількості; перевірки валюти, якості, Decimal та собівартості використовують той самий об'єкт. Окремі резерви, їхня черговість та частковий випуск збережені. Mutex береться до ERP fingerprint/«Було» в обох preview-входах і в execute; після очікування перечитується proposal, а наявний receipt повертається до перевірки fingerprint.

Шість регресій використовують реальні HTTP/ORM та SQL-журнал, охоплюють 5+5, часткові 6+4, різні партії, replay, обидва preview-входи та відмову від надмірного випуску. Це придатні тести вузького A01. Останній тест відмовляє до записів, тож сам по собі не є доказом rollback після списання; чинний окремий валютний сценарій у `check_erp.py` залишається відповідним додатковим доказом. Паралельність усіх операцій і обхідні CRUD/admin-шляхи цим diff не закриті.

У `write_lock` revision обчислюється з об'єкта до очікування UPDATE. Паралельні виклики можуть записати однаковий номер revision; нині цей номер ніде не використовується як версія погодження, а сам UPDATE однаково тримає блокування, тому це не блокує A01. Не починати використовувати цей номер як точний лічильник подій без окремої зміни.

## A02: мінімальна захищена транзакція

Першою SQL-операцією всередині `transaction.atomic()` виконувати no-op запис рядка зарплати:

```python
Salary.objects.filter(pk=self.pk).update(status=F('status'))
self.refresh_from_db()
```

Це бере write-lock SQLite або row lock PostgreSQL **до читання актуального статусу**, без нової моделі, зміни історії чи стороннього mutex. Один `select_for_update()` не захищає SQLite. Не варто застосовувати PostgreSQL `select_for_update()` до `select_related('transaction')` з nullable зовнішнім JOIN: блокування вже отримане простим UPDATE Salary.

Далі, в цій самій atomic:

1. Перевірити актуальний статус. Для узгодженого `paid` повернути існуючі `(self, self.transaction)`, не створюючи записів. Перевірка replay перед новою датою зберігає початкову дату фактичного проведення.
2. `paid` без transaction або з неузгодженими amount/currency/date/direction/category — помилка, яка потребує звірки; нічого автоматично не відновлювати. Старий `test_pay_again_rejected` створює саме `paid` без transaction і повинен лишитися 400. Здоровий replay потребує нового окремого тесту.
3. Платити лише узгодженому pending без попередньо прив'язаного expense; cancelled або наявна суперечлива прив'язка — відмова без переписування історії.
4. Перевірити дату та допустиму валюту, створити одну Transaction із **явним `currency=self.currency`**, amount зі свіжого Salary, direction out, category salary, employee branch.
5. Зберегти paid/payment_date/transaction разом у межах atomic. Будь-яка помилка після INSERT має вийти назовні та відкотити Transaction і Salary. Не ловити помилку всередині atomic з поверненням успіху.

Важливо оновлювати саме `self`: чинний `SalaryViewSet.pay` ігнорує результат `mark_paid()` та серіалізує початковий об'єкт. Якщо використати інший локальний Salary, view треба буде явно перевести на повернутий об'єкт; `self.refresh_from_db()` дозволяє залишити API без такої зміни.

Захищеність цього методу ще не закриває редагування/видалення Salary і Transaction іншими CRUD/admin-шляхами; вони залишаються A05. Не розширювати заяву A02 до всіх способів запису фінансів.

## Реальні регресії A02 без моків

- Два різні ORM-об'єкти pending одного Salary, прочитані до barrier; два потоки з окремими з'єднаннями викликають `mark_paid`. Обидва результати містять той самий transaction ID, а expense count = 1, сума = 100. Такий тест ловить і послідовне використання застарілого ORM-об'єкта.
- Реальний HTTP pay з CSRF-сесією, потім повторний pay: ідентична серіалізація та незмінний transaction count. Для паралельного HTTP перевірити обидва responses і БД; сесії/CSRF підготувати до barrier.
- Окремі EUR/USD/UAH Salary: валюту перевірити в джерелі, витраті та відповіді; не лише в тексті опису.
- Реальний тимчасовий DB trigger на Salary відхиляє перехід у paid, але не no-op pending → pending. INSERT Transaction відбувається, наступний UPDATE падає; після виходу з atomic Salary лишається pending без transaction, expense count і суми не змінені. SQLite trigger через `RAISE(ABORT, ...)`; PostgreSQL — trigger function з exception. Це тест відмови справжньої БД, не підміна ORM.
- Legacy paid без transaction, некоректна дата та cancelled: відмова без нової Transaction і без редагування джерела.

Для конкурентних SQLite тестів потрібна **файлова тимчасова тестова БД та `TransactionTestCase`**, не зовнішня atomic від звичайного TestCase. Django test runner за замовчуванням може створити shared in-memory БД навіть при файловому `DATABASES.NAME`; задавати окремий `TEST.NAME` у тестовому профілі. Shared-cache SQLite може негайно повертати SQLITE_LOCKED замість очікування writer. Це відмінність тестового середовища, яку не слід маскувати під green для двох успішних відповідей. PostgreSQL прогони — окремий реальний доказ, коли середовище доступне.
