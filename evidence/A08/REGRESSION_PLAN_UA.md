# A08 · приватні документи й перенесення байтів

Підготовлено 11.09.2026 за master v2.1, `docs/PROGRESS_UA.md` та прийнятим рядком A08 у `BoS_Plan_Pack_UA/docs/TASK_TABLE_UA.md`. Оцінка залишається **3–5 людино-днів**. Залежності A04/A07 зберігаються; це план наступної задачі, не висновок про завершення A07 або готовність релізу. Уточнення нижче належать A08; заморожену інвентаризацію 85 шляхів / 12 місць не змінено.

## Зафіксована вихідна поведінка

- `operations.Document` зберігає `content` як BLOB, а `checksum` окремим рядком. Ключа приватного файла й окремого розміру немає.
- `operations.views.download` повертає BLOB або, якщо він порожній, UTF-8 текст. Фактичний SHA збережених байтів не перевіряється. Порожній оригінал і відсутній BLOB змішані через перевірку truthiness.
- `document_review` звіряє лише checksum із запиту з полем БД. Пошкоджений BLOB або невідповідний text-only запис може отримати `approved`.
- `Policy.documents()` і `service.newest()` завантажують усі поля. Список, картка та історія версій читають BLOB навіть для metadata.
- Пряме `/media/` закрите middleware і URLconf у A04. Політика об'єкта й окремий дозвіл `download_document` уже існують; A08 має їх зберегти.
- Upload/review вже використовують спільний ERP mutex A06. Це основа для серіалізації запису версії та загальної квоти, а не причина вводити ще одну чергу.
- Upload має ліміт 10 МБ, обмеження розпакування 40 МБ, PDF 100 сторінок, XLSX 5000×100, текст 500000 символів. Загальної квоти інсталяції немає.
- `ChatFile` вже лежить у FileField, має `size`, але не має checksum. Архів чату зберігає рядки й файли. HTTP виклики зовнішньої LLM, включно з `/api/chat/file/`, залишаються 503 за A04/C02; A08 не вмикає їх.

## Мінімальний контракт реалізації

1. Додати необов’язковий FileField приватного файла та розмір до Document без переписування старих ID, version/code, checksum, BLOB, text, sections, access_level або FK. Для ChatFile додати checksum зі станом «ще не звірено» для старих рядків; міграція схеми не вигадує підтверджений SHA.
2. Новий upload записує оригінал у приватний каталог з серверним ключем, фактичними `size` і SHA-256; ім'я користувача лишається metadata. Ключ не є публічним URL. Приватний підкаталог міститься у чинному MEDIA_ROOT, для якого немає web serving; `.url` приватного storage заборонений. Каталоги створюються з 0700, файли з 0600. Windows ACL потрібно реально перевірити окремо, UNIX mode не видавати за Windows доказ.
3. Єдиний accessor перевіряє фактичні байти перед download та review. Якщо встановлений storage key, відсутність/пошкодження файла — явна відмова; fallback на старий BLOB або text заборонений. Якщо ключа немає, читається legacy BLOB. Для text-only допустимі рівно ті UTF-8 байти, SHA яких дорівнює вже збереженому checksum. SHA порожніх байтів означає порожній оригінал; непов'язаний text не підставляється.
4. Невідповідність SHA/розміру дає контрольовану помилку українською, у чинному HTTP error contract — 422. Старий checksum у review-запиті чи неактуальна версія зберігає чинну поведінку конфлікту. Жодного автоматичного «виправлення» checksum або статусу.
5. Читання metadata використовує deferred BLOB/явну проєкцію. Це не привід прибирати історію версій або текст документа. Доступ перевіряється до читання приватного файла; відсутній дозвіл дає старий 403/404, а не oracle цілісності.
6. Загальна квота має точне документоване значення, одиниці й правило обліку старих BLOB, нових файлів, версій та архівних ChatFile. Не можна зробити квоту «безмежною» через відсутній setting або обнулити її архівацією. Два одночасні upload, кожен з яких окремо поміщається, не можуть разом перевищити межу. Фізичне подвійне зберігання збережених BLOB і їхніх копій явно врахувати в плані місця; не видавати логічну квоту за контроль вільного диска.
7. Файловий запис і SQL не є однією транзакцією. Використати staging/атомарне введення власного нового файла й гарантоване прибирання тільки своїх незавершених файлів після відмови. Не видаляти чужі файли, історичні BLOB або попередні версії. Існуючий ключ не перезаписувати.
8. Команда перенесення працює спочатку на новій явній копії БД/файлів. Preflight звіряє старий checksum, планує всі записи й видає manifest. Звіт містить ID, storage kind, source SHA/size, target key/SHA/size, статус і причину відмови. Перевірений BLOB копіюється, але не очищається. Повтор не породжує дубль/нову версію/інший ключ. Помилка нового файла не маскується старою копією.
9. Для старого ChatFile без історичного checksum manifest фіксує **спостережений SHA джерела на момент знімка**, а не доказ початкової справжності файла. Читання/копіювання й повторна звірка джерела та призначення мають завершитися до позначки перенесення. Немає джерела — явна неповнота, не вигаданий hash.
10. Restore A08 доводить повернення саме комплекту документів на нову синтетичну інсталяцію: original bytes, hashes, metadata, ID/FK, дозволи, версії. Повний backup/restore продукту й rollback оновлення лишаються A10; частковий документний доказ не закриває весь gate.
