## Усунуте зауваження

Початкова команда дозволяла створити каталог результатів усередині джерельного MEDIA_ROOT. Це змінювало вхідне сховище та могло спричинити рекурсивне копіювання власного результату. Тепер розміщення в самому джерелі, його підкаталозі та шлях із `..` відхиляються до `mkdir`. Реальний обмежений тест перевірив усі три відмови, відсутність створеного `nested-output`, точну незмінність рядків та media manifest.

## Підтверджений контракт

- Дозвіл видається лише після фактичного створення нових файлів; перевіряються ідентичність DB/media, фактична SQLite connection та відсутність сторонніх attached databases. План прив’язаний до конкретної копії.
- Передперевірка збирає конфлікти документів і вкладень з model/ID/reason. Неповний план повністю відхиляється; звіт зберігається. SHA старого ChatFile позначає спостережені байти, не вигадану історичну справжність. Видалення вже відомого SHA не легалізується старим планом.
- ERP mutex і durable-транзакція охоплюють staging та прив’язування. Після фактичного rollback прибираються тільки файли з власними невідкликаними квитанціями; історичні BLOB, текст, версії, права та зв’язки не очищаються.
- Oracle зберігає точні історичні migration rows, їх ID/applied, поля original_file/size/checksum, які вже існували перед міграцією, та ID/інші поля чинного ERP mutex. Для відсутнього mutex дозволено лише один очікуваний новий рядок із правильним наступним ID.
- У mixed typed-transfer сценарії порівняння незалежних ORM значень разом із повними typed manifests є правильним критерієм. SQL whitespace у JSON не є бізнесзначенням; чинний A07 codec канонізує його. Точні bytes, ID/FK, Decimal, JSON values, sequences та hashes залишилися критеріями приймання.

Канонічний запуск 9 методів та повний verify виконує root. PostgreSQL, Windows, виробниче перенесення і реліз цим висновком не приймаються. Reviewer не змінював checkout, робочі дані чи Git-історію.
