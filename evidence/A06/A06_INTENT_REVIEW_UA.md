Перевірено поточний checkout після змін root: `finance/models.py`, `commands.py`, `serializers.py`, `admin.py`, `views.py`, передачу ключа в `ai_assistant/views.py`, серверний guard та нові форми frontend. **Висновок:** блокувального порушення фінансової цілісності в перевірених шляхах не знайдено. Погоджую поточну реалізацію keyed create для подальшого A06 приймання. Цей висновок не замінює concurrency gate, PostgreSQL або браузерне приймання.

## Чому погоджую

- Ключ receipt обчислюється з типу фінансового запису, actor.pk та ключа наміру. Однаковий рядок ключа для іншого користувача або іншої моделі не повертає чужий результат.
- Хеш payload охоплює всі дозволені поля фінансової команди, зокрема призначення/опис і примітки. Зв’язки перетворюються на PK, Decimal нормалізується, типові значення беруться з моделі. Зміна істотних даних під тим самим ключем відхиляється.
- Claim, створення source, фінансовий AuditEvent і посилання receipt виконуються в одному atomic. Помилка валідації, запису або аудиту відкидає claim разом із фінансовою зміною. Конкурентний get_or_create спирається на унікальний первинний ключ; SQLite-конфлікт допускає явний 409 з наступним повтором того самого ключа.
- Повтор повертає поточний запис за тим самим PK; не відновлює первісні amount/status/archive/link. Власна команда виплати Salary лишається окремим idempotent шляхом за Salary PK, зі збереженим A02 блокуванням.
- Видалення ранньої DRF unique-валідації Salary потрібне для replay. Унікальність employee/period залишається у `candidate.full_clean()` під блокуванням Employee та в DB constraint; другий незалежний намір не отримує права створити дубль періоду.
- API create вимагає ключ; довірені внутрішні виклики без ключа залишаються одноразовими. Native admin додає прихований ключ і обробляє повтор до ModelForm unique-перевірки. Повернення receipt не обходить CSRF, чинну бізнес-роль чи staff-доступ.
- Frontend не генерує новий UUID на кожен retry: ключ зберігається у ref форми, а синхронний pending guard спрацьовує до await. Після помилки введені значення залишаються. Нове тіло, явне редагування, успішне завершення або нова форма відокремлюють наміри.

## Зауваження і межі

1. Знайдено ризик короткого замикання старих негативних create-тестів на missing-key 400. Root виправив `HistoryTestBase.api` та admin add передумови, додавши явні ключі без зміни assertions; це зафіксовано у `evidence/A06/TEST_CONTRACT_UA.md`. Зауваження закрите після перегляду актуальної правки.
2. Legacy `_run_tool_loop` передає `block.id`; `_create_salary` і `_create_transaction` передають ключ до спільної команди. Їхній actor наразі None, отже keyed внутрішні виклики належать довіреному службовому namespace. HTTP legacy-адаптер лишається вимкненим до C02. Перед увімкненням C02 необхідно передати справжнього actor та застосувати чинну Policy; цей огляд не приймає готовність зовнішньої LLM.
3. Salary bulk loop у served frontend відсутній. Поточна форма створює один запис, незалежні форми мають різні UUID. Новий масовий workflow не додавався й не перевірявся.
4. PostgreSQL, реальні гонки, навантаження та браузер цим spot-check не запускалися. Висновок про структуру транзакції є code review; він не видається за виконаний PostgreSQL тест.
5. Backend написаний root і оглянутий незалежно. Попередній frontend-кандидат готував цей агент; його огляд тут не є другою незалежною думкою щодо UI. Root має перевірити інтеграцію та провести браузерне приймання.

Розбіжностей із root щодо цього локального висновку немає. Повний MVP/verify готовим не оголошується.
