# A06 · передумови перевірок

Нові фінансові API create вимагають `Idempotency-Key`; форми admin передають прихований `bos_operation_id`. Це ідентичність одного наміру, а не порівняння сум чи дат. Старі перевірки позитивного create отримали ці обов’язкові вхідні поля. Жодного assertion, очікуваного ефекту чи порога не видалено і не послаблено. Кожен старий незалежний create отримує новий ключ; регресії A06 окремо перевіряють незмінний ключ при повторі.

`check_access` зберігає позитивний запис і контроль його ефекту для CEO, усі попередні заборони та обхід маршрутів. Fixture admin обчислює callable initial так само, як справжня Django-форма. SalarySerializer більше не відхиляє employee/period до команди: той самий UNIQUE перевіряє `candidate.full_clean()` усередині спільної фінансової команди під блокуванням. Збережена команда може спочатку повернути вже проведений intent; це не дозвіл створювати друге нарахування за період.

Початкові 37 ERP-тестів уже пройшли на SQLite: не вигадуємо для них падіння. Реальний red A06 — 3 фінансові HTTP/admin регресії та 2 регресії порядку блокування документів. Синтетична SQLite не заміняє PostgreSQL чи браузер.
