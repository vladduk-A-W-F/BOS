## Мінімальний пакет v1

Один явно погоджений namespace джерела на компанію, наприклад `synthetic-starter`. Формат `bos.initial-import.v1`, власний UUID `batch_id`, `as_of` як ISO-дата, `tax_basis=excluding_VAT`, `rows` та обов’язкові очікувані контрольні підсумки. До 100 бізнес-рядків і 3–5 відкритих замовлень у стартовому профілі; конкретний byte-limit має вкладатися в чинні HTTP-ліміти й перевірятися до JSON-парсингу. Це не обіцянка масштабного імпорту.

JSON — канонічна внутрішня форма. CSV — строгий адаптер до тієї самої форми: UTF-8 (допустимий один BOM), кома як роздільник, стандартне quoted поле, LF/CRLF, фіксовані колонки `entity,external_id,<поля сутності>`. Один вид сутності на файл; поля/файли задає manifest. Жодного sniffing роздільника, виконання формул, довільних файлових шляхів, SQL, Python або ZIP extraction. CSV money/quantity містять крапку й передаються у JSON як рядки. Manifest і вибрані CSV завантажуються одним multipart-запитом; серверні шляхи користувач не задає. Невідомі, повторні/порожні заголовки, extra cells і невідомі поля — помилки, не мовчазне пропускання. CSV export для перегляду має текстово екранувати формулоподібні значення; канонічний JSON зберігає їх буквально.

| entity | Поля та виконання |
|---|---|

| item | external_id, code, name, unit, kind, method=buy, revision, currency; optional planned_cost, minimum, lead_days, material, required_documents, явна document reference. Без BOM/routing/make/subcontract у першому підетапі. `erp_item`. |
| location | external_id, code, name, kind=warehouse. `erp_location`. Виробничі/підрядні локації — наступний профіль. |
| opening_lot | external_id, code, item_ref, location_ref, revision, quantity>0, unit_cost>=0, currency, documents, обов’язкове source_reference/reason зрізу. `erp_opening`, якість pending; імпорт не імітує лабораторне приймання. |
| sales_order / sales_line | Сталі external_id для шапки й кожної позиції, code, customer_ref, наявний owner_id, due_date, currency; item_ref, revision, quantity, price. Через спільний purchase writer з виданим server-only контекстом imported_open_balance (опис нижче). Це окремий новий підетап, не чинна `erp_purchase` команда для нового погодження. |

Посилання всередині пакета — `{entity, external_id}`; на наявні записи — лише явні mappings з типом, ID та показаним користувачеві кодом/версією. Спочатку валідний граф залежностей, потім стабільний порядок виконання. Номер CSV-рядка — адреса помилки, не identity. Employee, користувачів, фінансові транзакції, invoices/payments, RFQ/Quote, медіа, виробництво й резерви пакет v1 не створює.

**Окремий підетап B02 для історичного supplier PO — imported_open_balance.** Продажі без виконання, номенклатура й залишки безпосередньо використовують чинні команди. Історичний незакритий PO не є новим погодженням: прострочення допустиме й має відображатися зі справжньою датою. Спільний purchase writer потребує нового keyword-only server context, наприклад `import_context: ImportedPurchaseContext | None`. Такий immutable typed об’єкт видає тільки authenticated confirmed batch executor під спільним mutex після валідації batch/actor/namespace/row SHA; він прив’язаний до конкретного рядка, поточної транзакції та канонічних значень. Не приймати context, source або bypass прапорець з JSON. Звичайні preview/confirm/assistant `erp_purchase` завжди працюють без контексту та виконують усі B01 правила. Object constructor/type-check сам по собі не заміняє контрольовану видачу й перевірку binding.

Для context перевірити `original_quantity > 0`, `0 <= received_before_cutover < original_quantity`, `remaining_quantity = original_quantity - received_before_cutover > 0` із точною scale 0.001. В BoS записати `quantity=remaining_quantity`, `received=0`, status=ordered; нові приймання рахуються тільки після cutover. Це **залишок до виконання**, UI/receipt мають так його називати. Snapshot `source=imported_open_balance` зберігає namespace/external_id, оригінальні номер/рядок замовлення, первинні source reference, original_quantity/received_before_cutover/remaining_quantity, original_due/due_date, currency/price/original_extras/remaining_extras, cutover, batch SHA/row SHA та actor. `source_documents` використовує відомий policy shape для явно дозволених наявних документів; невідомі первинні номери зберігаються як текст provenance, не як вигадані BoS Document IDs. Не записувати supplier_confirmation/direct_reason, які видавали б цей факт за нове погодження B01.

`due_date` і `original_due` з джерела зберігаються буквально, у тому числі прострочені. `remaining_extras` — окрема явно підтверджена сума для залишку, не здогадний перерозподіл original_extras. Обидві суми невід’ємні, та в цьому профілі remaining_extras не перевищує original_extras; інше потребує уточнення джерела. Purchase.extras=remaining_extras, бо чинне receive розподіляє extras на Purchase.quantity. Snapshot зберігає початкові реквізити без відтворення минулих receipt/Movement/оплат; не переносити минулі received у нові Lot або резерви. request/quote/production FK у першому цьому профілі не прив’язуються до сучасних B01 джерел; їх зовнішні первинні номери можуть лишитися provenance. Будь-яке подальше зіставлення — окреме погодження, не мовчазне створення джерел.

Невідповідність item/revision/unit, неправильна валюта, прихований документ, уже імпортований змінений рядок, неузгоджений залишок/витрати — повна відмова batch. Чинні policy/projection і source card мають явно підтримати imported_open_balance: observer не отримує комерційного snapshot/довільного тексту, historical source не перетворюється на quote/direct. First_batch/ImportIdentity та snapshot зберігають повний первісний реквізит навіть після законних нових приймань.

Цього контексту й його тестів **ще немає**. Якщо наступна реалізація покриє лише простий підетап довідники/opening/невиконані продажі, B02 для open supplier orders лишатиметься незавершеним; не називати його повним імпортом відкритих замовлень. Частково відвантажені/проінвойсовані продажі також поза першим профілем: не скидати shipped/invoiced у нуль; для них потрібен окремий погоджений залишковий профіль після D01.

Початковий запас — лише явно виокремлений зріз/нові партії. Якщо по item/location уже є запас або рухи, повідомити conflict; не додавати повний повторний складський balance до існуючого. Випадки легітимного додаткового зрізу потребуватимуть окремого узгодженого режиму, не heuristic. Кількість від 0 не перетворювати автоматично в операцію, від’ємні/невідомі статуси — помилки.

## Журнал ID, симуляція та одне погодження

Пропоновані нові файли: `erp/importing.py` (strict normalization/plan/apply/reconcile), `erp/import_views.py` (тонкий upload adapter), `erp/test_initial_import.py`, `fixtures/synthetic/initial_import/`; моделі й міграція журналу в `erp/models.py`/`erp/migrations/`. Назви є проєктом, файлів поки немає.

Запропоновані моделі: ImportBatch(batch UUID, namespace, format, canonical payload SHA, original-file SHA, as_of, actor, immutable committed receipt) і ImportIdentity(namespace, entity, external_id, canonical row SHA, first_batch, target). DB UNIQUE на `(namespace,entity,external_id)` та на batch UUID. Target — явний перелік FK до дозволених моделей із PROTECT і CHECK «рівно один FK відповідає entity», не довільний GenericForeignKey. Для прив’язки вже наявного запису потрібен окремий явно погоджений mapping; однакові name/сума/дата не є доказом дубля. Другий external_id на той самий target у тому самому namespace має conflict. Item.external_codes може показувати мапінг, але не бути єдиним журналом ідемпотентності.

Повтор того самого batch UUID + semantic SHA повертає той самий receipt. Той самий UUID з іншим змістом — 409. Інший batch UUID з уже відомими external IDs та незмінним первісним canonical row SHA — no-op для тих рядків, ті самі BoS IDs; нові рядки можна додати одним атомарним пакетом. Відомий external ID із зміненим змістом — row conflict, не update. Payload SHA включає значущі поля, mappings, as_of, policy/profile й очікувані totals; byte SHA окремий, тому CSV whitespace не підміняє бізнес-identity. Сортування рядків/JSON-ключів канонічне, сортування позицій не змінює їх external ID. Після законного подальшого приймання/відвантаження replay не переписує поточний стан старими імпортними значеннями; повертає первісне джерело, перевіривши чинну видимість і наявність target.

Запропонований `POST /api/erp/import/preview/` приймає JSON або manifest+CSV. Лише CEO у першому профілі, бо пакет містить opening та комерційні дані; role/session/CSRF — чинні. Відповідь: `valid`, `errors[{entity,external_id,row,field,code,message}]`, warnings, dependency-blocked rows, create/reuse counts, source→target mappings, before/projected totals. Помилки не містять приховані реквізити або сирі рядки в серверних логах. Детерміновані input-помилки збираються по всіх рядках; залежний рядок отримує `DEPENDENCY_FAILED`. Системна SQL-помилка зупиняє всю симуляцію й дає загальну помилку, не продовжує з недостовірними totals.

Як у поточному ERP preview, симуляція може виконати реальні domain commands у транзакції з rollback; не називати її «жодного SQL». Усі бізнес-рядки й import identity відкочуються. Після успішної перевірки дозволений тільки новий ActionProposal із immutable normalized batch; помилковий пакет не отримує підтвердження. На PostgreSQL rollback може споживати sequence numbers — не вимагати gapless IDs й не видавати SQLite proof за PG.

Confirm використовує чинний `/api/operations/confirm/`. Додати `erp_import_batch` як один явно дозволений orchestration action, без прийняття списку довільних actions. Під спільним ERP mutex: заново перевірити user/role/session/expiry, mappings, джерела, namespace identities, fingerprint і bounds; apply весь граф; звірити counts, ID/FK, рухи й totals; створити Event/журнал/receipt; один commit. Збій на останньому рядку відкочує також попередні рядки, new ID mappings, audit/receipt. Ніяких окремих commit по CSV-рядках. Повтор успішного погодження не створює навіть дубль Event.

Наявний ERP fingerprint **не включає Counterparty, Employee, import ledger або дату dataset**. Для B02 треба включити всі поля, що впливають на binding/прийняття batch, разом з expected mappings і source-doc revision/checksum/status; не покладатися тільки на сьогоднішній fingerprint. Повторно валідовувати refs перед commit. Якщо чинний окремий CRUD довідника може змінити ці поля конкурентно поза ERP mutex, реалізація має конкретно серіалізувати/заблокувати ці релевантні writes або звузити v1 до незмінних mappings; fingerprint сам по собі не знімає race. Не перераховувати заново заморожені 85 шляхів/12 місць: описати точні зміни існуючих CORE/ERP допусків і новий scoped import entry.

## Контрольні підсумки та синтетичний еталон

Рахувати Decimal з достатнім локальним context; входи — рядки, невідомі валюти/scale/overflow відхиляти. Окремі суми EUR/USD/UAH, жодного FX чи загального «всього». Кількості групувати за item/revision/unit/location, не додавати кг до штук. Окремо показувати: фізичну кількість, доступну кількість, raw extended inventory value, суму записаних opening Movement.cost, відкритий продаж `Σ(quantity×price)`, закупівлю `Σ(quantity×price+extras)`, створені/reused rows. Не називати PO суму оплатою або запас доходом. Підсумки мають включати import delta і persisted before/after; unchanged існуючі рядки перевіряти по IDs/повних полях.

У поточному `money_total` Movement.cost округлюється до 0.01, а quantity×unit_cost може мати 5 знаків. Зберегти чинну семантику й явно показати різницю; для deterministic контракту зафіксувати ROUND_HALF_EVEN у scoped розрахунку. Не вимагати помилкової рівності raw valuation та ledger costs, не округлювати кожну вхідну кількість/ціну для проходження gate. Expected totals у manifest незалежні від server result; mismatch блокує confirm. Новий batch receipt/export має власний повний список рядків й exact totals, а не float totals CounterpartySerializer.

Запропонований еталон: одна нова синтетична компанія, наявний synthetic CEO/owner, 1 новий склад, 3 items, 1 постачальник/1 клієнт, 3 opening lots, 3 confirmed sales orders по одній позиції та 3 залишкові PO; один із них частково отриманий до cutover та вже прострочений. Фіксований fixture as_of=2026-09-12; звичайні SO мають майбутні дати, один imported PO зберігає original_due=due_date=2026-09-01. Ніяких первинних клієнтських документів чи вигаданого підпису. При method=buy BOM не потрібен.

| Валюта | Opening quantity × unit_cost | Raw value / Movement.cost | SO quantity × price | PO quantity × price + extras |
|---|---|---|---|---|
| EUR | 1.250 × 2.34 | 2.925 / 2.92 | 2.500 × 4.12 = 10.30 | залишок 5.000 × 1.23 + 0.40 = 6.55 |
| USD | 3.000 × 0.10 | 0.300 / 0.30 | 4.000 × 0.25 = 1.00 | 2.000 × 0.10 + 0.10 = 0.30 |
| UAH | 2.000 × 100.05 | 200.100 / 200.10 | 1.000 × 150.10 = 150.10 | 3.000 × 20.05 + 0.25 = 60.40 |

Для EUR PO первинна кількість 8.000, received_before_cutover=3.000, залишок 5.000, original_extras=0.80, remaining_extras=0.40; саме 5.000/received=0 та extras=0.40 записуються в BoS. Після справжнього нового receive 2.000 лишається 3.000, snapshot первинного зрізу незмінний; минулі 3.000 не створюють фіктивного надходження. Усі opening lots pending, отже придатний доступний залишок одразу після імпорту = 0. Для подальшого резервування потрібна справжня окрема `erp_quality`, а не прихований auto-approve. Сам пакет та виконані тести цього fixture ще не створені.

## Meaningful regression сценарії перед прийманням

1. **Фактичний JSON/CSV round-trip:** однаковий semantic пакет дає ті самі mappings і контрольні підсумки; помилковий manifest total блокує confirm. Незалежний ORM-оракул перевіряє всі створені FK, raw Decimal, opening movements і pending availability. Перевірити half-cent рядок EUR із таблиці та EUR/USD/UAH окремо.
2. **Dry run і row errors:** декілька одночасних помилок — duplicate external ID, missing ref, неправильна одиниця/версія, надлишкова scale, невідоме поле, duplicate JSON key/CSV header. Адреси entity/row/field точні, залежні рядки позначені, жодних committed Item/Lot/PO/Movement/ImportIdentity/Event; помилковий пакет не отримав proposal.
3. **Replay після розвитку бізнесу:** двічі confirm одного token, новий token/новий batch UUID із тими самими рядками; жодного дубля. Потім фактичне часткове receive PO та повтор імпорту — received, Lot і Movement не переписані, первісні IDs сталі. Змінений original payload під старим ключем → 409, без змін.
4. **Справжній пізній SQL-збій:** trigger відмовляє на останньому PO або ImportIdentity; усі попередні створення, journal і receipt rollback. Після усунення лише власного test-trigger повтор успішний рівно один раз. Не підміняти це mocked exception перед apply.
5. **Конкурентні HTTP confirmations:** дві реальні connections і barrier, однакові external IDs/коди; одна committed історія. Інший contender отримує контрольований conflict/replay, а не два запаси. Також конкурентний звичайний `erp_opening` не дозволяє подвійний початковий зріз.
6. **Застарілі binding/повноваження:** між preview/confirm змінити версію Item, тип постачальника, source document status/bytes, mapping або as_of — stale/refusal. Чужа сесія/роль, manager opening і observer — відмова, без price/text витоків у preview/receipt/export/error. Перевірити конкретну конкурентну зміну довідника на межі commit.
7. **Збереження історії й чесні межі:** заздалегідь існуючі PO/receipt/archived rows/PK незмінні; конфлікт внутрішнього code не викликає upsert. Історичний частково received і overdue PO проходить тільки виданий imported_open_balance context: quantity=залишок, received=0 для нового об’єкта залишку, snapshot первісного received збережений, прострочені дати буквальні, жодних вигаданих Movement. Той самий JSON у звичайній erp_purchase та підроблений context не обходять B01. Непогоджений partially fulfilled SO відхиляється. Документ іншої версії/прихований ref не імпортується обходом A08.
8. **Export і роль повного журналу:** receipt export відтворює всі batch IDs/hash/totals незалежно від UI truncation; повторний manifest звіряється. Формулоподібний текст безпечний у CSV для перегляду, canonical JSON буквальний. Видалення імпортованого джерела захищене PROTECT; міграції журналу не втрачають заповнені provenance при downgrade.

Спочатку bounded synthetic red → мінімальна реалізація → green на власній новій БД, потім незалежний огляд і root fullverify на замороженому source. Поточні B01/A07 assertions не послаблювати. PostgreSQL, Windows, клієнтська копія, підпис D01 та весь B02 не оголошуються виконаними на підставі цього плану.
