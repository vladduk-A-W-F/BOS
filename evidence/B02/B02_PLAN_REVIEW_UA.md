## Висновок

План придатний як основа першого невеликого synthetic-імпорту. Коректні рішення: зовнішні identity замість зіставлення за назвою; один атомарний пакет; dry run з видимими наслідками; суми окремо за валютою; pending-якість початкового запасу; відокремлений залишок історичного PO без вигаданих минулих надходжень; A07 restore не видається за бізнес-імпорт.

До першої реалізації необхідні **три уточнення**, уже погоджені координатором у межах цього огляду:

1. Контекст історичного PO видається окремо для preview і confirm, під тим самим ERP mutex; preview відкочується, його context не використовується повторно.
2. Незмінні контрольні підсумки джерела відокремлені від живих before/after. Replay не намагається відновити стан зрізу після законного receipt/ship.
3. Для imported PO потрібна окрема українська UI-гілка: до зрізу / після зрізу / залишок. Наявна картка quote/direct і звичайні лічильники неправильно пояснять такий запис.

Ще чотири невеликі контрактні рішення наведені нижче; вони не потребують нового стеку, інтеграції чи розширення аудиту. Поки ці правила не записані в схему й oracle, перший імпорт може технічно записати дані, але користувачеві буде складно перевірити його зміст.

## R1 · історичний PO повинен проходити справжній dry run

**Доказ коду.** `erp/procurement.py:purchase_source()` відхиляє `due_date < as_of()`, а `erp/service.py:purchase` викликає саме його. `erp/views.py:preview` та `erp/service.py:preview_effect` виконують domain dispatch у транзакції й відкочують її. У draft B02 контекст видає лише «authenticated confirmed batch executor», але preview історичного overdue PO також потребує цього контрольованого маршруту. Підміна due_date на майбутню або пропуск writer у dry run спотворить перевірку.

**Погоджений контракт:** серверний import coordinator має дві фази видачі immutable typed context: `preview` і `apply`. Обидві можливі лише після автентифікації CEO, строгого нормалізованого batch, повної перевірки джерел/identity та входу у відповідний ERP mutex + atomic transaction. Context зв’язаний із фазою, рядком, semantic SHA, actor, namespace, cutover і поточною транзакцією. Input не приймає context, import source або bypass-прапорці.

Preview використовує таку саму валідацію й purchase writer, але всі бізнес-записи/identity/Event/context-залежні результати відкочуються. Після виходу лишається тільки погодження нормалізованого пакета, не preview ID/context. Confirm заново перевіряє стан і видає **новий** apply-context для того самого рядка. Expired/stale/mismatched context не переноситься між фазами/транзакціями. Звичайні `erp_purchase` UI/API/assistant залишаються без такого контексту й дотримуються B01.

**Приймання:** overdue PO від 2026-09-01 при cutover 2026-09-12 проходить import-preview без committed Purchase/Movement; після confirm має буквальні початкову й поточну дати з файлу. JSON із тим самим due_date у звичайному `erp_purchase` відхиляється. Підроблений або preview-context не може провести apply. Два повтори confirm не додають PO/Event. Це заплановані тести, не отриманий результат.

## R2 · replay і контрольні суми мають різні часові основи

**Доказ коду.** `erp/service.py:receive` збільшує `Purchase.received`, створює нові lot/movement; `erp/queries.py` і `erp/experience.py:home` показують поточний залишок. Нормальний розвиток після початкового імпорту закономірно змінює before/after. Якщо manifest expected totals означають «майбутні живі totals всієї компанії», старий валідний пакет після receipt більше не збігатиметься з ними.

**Погоджений контракт:**

| Набір | Що перевіряється | Поведінка при повторі |
|---|---|---|
| `source_control_totals` | Незмінний канонічний зріз вхідного джерела за namespace/cutover; первісні rows і original values. Незалежні expected totals файлу звіряються з ним | Той самий вихідний payload має ті самі source totals навіть після receipt |
| `planned_delta` | Тільки ще не імпортовані rows цього перегляду; create та reuse окремо | Для повного replay — нуль; для mixed batch — тільки нові rows |
| `live_before`, `projected_after` | Поточний стан БД перед виконанням і його зміна від planned_delta, окремо по валюті та item/revision/unit/location | Переобчислюються за поточним станом; не зобов’язані дорівнювати вихідному зрізу |
| `first_commit_receipt` | Історичний receipt створення з початковими target IDs, SHA й фактичним тодішнім ефектом | Ідентичний для повтору того самого batch; не підмінюється новими totals |
| `current_targets` | Явно окремо завантажені поточні картки та видимість target | Можуть показати нові receipt/ship, не переписуючи first receipt |

Row replay визначається через первісний semantic row SHA і identity, а не порівнянням старого файлу з усіма поточними полями target. Повторно перевіряються права, існування і тип target, але не відновлюються його старі quantity/status/revision. Спроба використати **змінений вихідний рядок** під старим external ID — conflict; законні подальші операції в BoS — не причина upsert.

**Приймання:** EUR imported PO має remaining quantity 5, price1.23, extras0.40, source PO value6.55. Після реального нового receipt2 живий open PO value3.93; replay того самого вихідного пакета залишає received2, physical stock і movements незмінними. Source total лишається6.55, planned delta0, live before/after однакові. Сума original_extras0.80 та received-before3 не відновлюються в current operational fields. Mixed batch не додає старі opening balances вдруге.

Цю семантику треба назвати у manifest schema, а не лише загальним словом `totals`. Незалежні expected totals не можна автоматично підмінити серверним результатом для проходження перевірки; UI може дати шаблон і пояснення розрахунку.

## R3 · imported PO має читатися як перенесений залишок

**Доказ коду.** `frontend/boss_app_source.html:PurchaseSource` будь-який `source`, відмінний від `quote`, називає «Пряма закупівля» й пише «Ці умови збережені під час погодження». `view==='purchase'` та PO inspector показують звичайне «Замовлено / отримано» на основі `Purchase.quantity/received`. Для source `imported_open_balance` це створить хибний висновок, що історичне PO було на5 і нічого раніше не надходило. Не-request document зараз отримує назву «Пропозиція», що теж не завжди відповідає імпортному джерелу.

**Погоджений контракт:** окрема source-гілка, назва **«Перенесений залишок замовлення»**, дата зрізу, зовнішній номер/позиція, посилання на batch і доступні первинні джерела. Жодного тексту про нове погодження постачальника. Початкові та сучасні факти розділяються:

| Підпис у картці | Одразу після імпорту | Після нового receipt2 |
|---|---:|---:|
| Замовлено у джерелі | 8.000 | 8.000 |
| Отримано до зрізу | 3.000 | 3.000 |
| Перенесено до виконання | 5.000 | 5.000 |
| Прийнято у BoS після зрізу | 0.000 | 2.000 |
| Залишилось прийняти | 5.000 | 3.000 |

Кнопка «Прийняти поставку» пропонує3, не5/8; вона створює реальний новий receipt. Прості числа8−3−2=3 пояснюють стан без читання JSON. Дата2026-09-01 лишається простроченою, не змінюється на дату імпорту. Поточні статуси ordered/partial стосуються **залишку в BoS**; це треба підписати в списку, а не тільки в глибокій source-картці.

`source_documents` має показувати фактичний вид джерела або нейтральне «Первинний документ», без автоматичного ярлика quote. Наявні поля й текст provenance не можна просто передати всім ролям: manager/observer отримують лише погоджену явну projection; preview/import доступний тільки CEO. Snapshot, receipt, таблиця й inspector повинні використовувати один числовий контракт.

## Невеликі рішення, потрібні першому робочому кроку

### R4 · два opening lots одного item/location у тому самому пакеті

Draft відхиляє opening, якщо вже є запас або рухи по item/location. Це правильний захист від повторного повного зрізу, але не визначено, чи «вже є» включає першу створену в тому самому batch партію. `erp_opening` такої перевірки сам не робить: створює lot + movement. Построковий check після першого create заблокує другий легітимний lot; додавання цієї глобальної заборони до звичайного opening змінить чинну поведінку поза B02.

**Рекомендація:** перевіряти конфлікт групи against **persisted pre-batch state** під mutex; кілька явно виокремлених source lots однієї групи в одному новому зрізі дозволені. Їх identity й коди різні, totals враховують обидва. Reused rows відокремлюються до цього check. Після законного replay жодного другого opening; mixed batch із новим opening у вже заповненій групі відхиляється в цьому профілі. Чинний ручний `erp_opening` не переписувати задля імпортного правила; конкурентний writer серіалізується, і batch перевіряє новий persisted стан.

**Мінімальний oracle:** два lots2+3 одного item/location на порожньому зрізі → фізично5, два opening; replay → ті самі5/два; незалежний preexisting lot1 → весь новий зріз conflict. Запас у різних одиницях/валютах не змішується одним число́м.

### R5 · номер історичного PO і його позиція не тотожні BoS code

`Purchase` — одна номенклатурна позиція, його `code` глобально унікальний. Зовнішнє PO може мати кілька рядків з одним номером. Draft обіцяє зберегти первинний номер/рядок у snapshot, але таблиця полів не задає окремих `source_order_code` і `source_line_id`; source unit також не названа, хоча далі вимагається перевірка відповідності одиниці.

**Рекомендація:** у схемі явно розділити `external_id` позиції, первинний номер PO, первинний ID/номер рядка та унікальний `bos_code`; додати source `unit` для явного зіставлення. У preview показати результат відповідності. Консервативний v1 не вгадує code із назви: конфлікт коду показує рядок і просить явний вільний `bos_code`; для нових шаблонів UI може запропонувати код, але він входить у підтверджений payload. Довгі оригінальні номери не обрізати до60 заради `Purchase.code`: зберегти як окреме provenance поле в явній межі schema.

**Мінімальний oracle:** PO-7/line1 і PO-7/line2 → два різні BoS Purchase, один справжній source_order_code, різні source_line_id; replay переставлених CSV рядків не дублює позицій. «кг» проти «шт.» не конвертується автоматично.

### R6 · точна canonical identity для JSON/CSV

Draft правильно відокремлює byte SHA і semantic SHA, але варто назвати нормалізацію значень. У джерелі `erp.service.number` повертає Decimal зі scale введення; `str(Decimal('1.0'))` і `str(Decimal('1.000'))` відрізняються. Хеш сирого рядка дасть хибний conflict між еквівалентними JSON/CSV.

**Рекомендація:** після суворого допуску money/quantity привести до узгодженого канонічного десяткового рядка (2/3 знаки) без зміни значення; стабільно нормалізувати ISO-date і явно встановлені defaults. Текст/зовнішні ID не зливати за casefold, назвою чи довільним trim; правило допустимих ID задати окремо. Порядок rows не є identity. Для sales_order визначити immutable composition: додати нову позицію в уже імпортовану шапку як update v1 **не дозволяє**; або повний повтор того самого набору lines, або conflict. Інакше обіцянка «mixed batch може додати нові rows» виглядатиме як дозвіл тихо дописати прийняте замовлення.

**Мінімальний oracle:** JSON quantity1.0 і CSV1.000 при однакових решті значень → та сама row identity; quantity1.001 → conflict старого external ID; переставлені lines → same source; новий line у reused order → явна неподтримувана зміна, не частковий apply.

### R7 · перший UI не має вимагати ручного знання внутрішніх ID

Для мінімального результату достатньо одного послідовного екрана з трьома станами, без wizard-конструктора й без auto-mapping за схожістю:

1. **Підготувати файл.** Завантажити готовий приклад JSON або набір manifest+CSV, вибрати відому company/source, дату зрізу і наявного відповідального за ім’ям. Коротко показати: UTF-8, кома-роздільник, десяткова крапка, money без ПДВ; підтримані entity. UUID/namespace може сформувати UI й показати як довідкові реквізити, користувач не має писати їх вручну для першого demo. За редагування файлу новий batch ID створюється явно, external IDs лишаються стабільними.
2. **Перевірити зміни.** Таблиця source row → створити / уже імпортовано / помилка; human code/name, конкретне поле й причина. Один блок до/зміна/після на валюту. Фізично ≠ доступно: pending-партії одразу доступно0. Окремо original control totals і фактичний planned delta; формулу й half-cent0.005 пояснити в деталях. При помилках кнопка підтвердження недоступна; дані залишаються в екрані для виправлення, сервер повертає всі input errors.
3. **Погодити й відкрити.** Один confirm пакета; receipt з лінками на items/lots/SO/PO і позначкою повтору. Для втрати відповіді зберігати саме proposal ID, повторювати той самий confirm; не генерувати новий намір автоматично. «Назад» до commit нічого не імпортує; після commit пропонувати журнал і експорт, не кнопку фізичного видалення імпорту.

Числові FK документів/Employee в канонічному payload допустимі, але екран показує ім’я, код, версію і дозволяє явний вибір. Для CSV не потрібен зовнішній плагін. Manifest+CSV мають бути готовими downloadable файлами та перевірятися тим самим серверним адаптером; сам опис формату без прикладу не дає першого корисного демо.

Конкретний HTTP byte limit треба вказати до показу «100 rows»: чинний `operations.views.body()` обмежує JSON30000 байтів. Окремий import adapter може мати свій погоджений малий ліміт у наявних зовнішніх межах; не змінювати глобальний ліміт, щоб сховати помилку. Перший реальний шаблон мусить пройти саме цей маршрут; підписувати максимум рядків **і байтів**, а не обіцяти будь-які100 довгих рядків.

## Межі й приймання першого підетапу

Мінімально корисний synthetic результат: шаблон → JSON/CSV preview → видимий atomic confirm → клікабельний receipt → повтор без дублів; включно з одним overdue/partially-received-before-cutover PO. Якщо реалізовано тільки довідники/opening/невиконані SO, UI має прямо назвати цей профіль, а B02 open supplier orders лишається відкритою.

Не вимагати у B02 нового AP invoice, банківського імпорту, manufactured BOM, історичної реконструкції stock movements або автоматичного зіставлення реальних клієнтських документів. Погоджені первинні дані D01 все ще потрібні для пілотного приймання. Рекомендації вище виправляють конкретні неоднозначності стартового плану, не розширюють scope.

Для незалежного приймання наступної реалізації досить додати до вже перелічених у B02 eight regression сценаріїв oracle R1–R6 й перевірку першого UI R7. Нових тестів тут немає; browser/SQLite/PG/Windows pass не заявляються. Збірка JSX або simulated API response не замінює фактичний click → preview → confirm → receipt.
