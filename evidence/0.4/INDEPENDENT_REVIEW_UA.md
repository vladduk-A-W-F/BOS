# BoS · незалежний огляд check_invariants.py

11.09.2026. Read-only перевірено реалізацію та поточні serializers/матрицю ролей. Checkout не змінено. Повний 1000-run набір у цьому огляді повторно не запускався.

**Висновок: поточний червоний результат чесний, але рольовий oracle має конкретну можливість хибного green; потрібні дві вузькі правки.**

1. **Виправити перевірку тіла забороненої відповіді.** `denied = response.status_code in (401, 403)` безумовно приймає 401/403 незалежно від тіла. Наприклад, 403 з `{"error":"forbidden","salary":{"amount":"100.00"}}` пройде. Employee 200 перевіряється лише через `set(response.json())`: `{"employee":{"email":"synthetic@example.invalid"}}` теж пройде. Це суперечить інваріанту відсутності даних, хоча статус може бути правильним. Незалежно від status перевіряти заборонені поля рекурсивно й відсутність унікальних синтетичних секретів у всьому тілі відповіді. Сам статус залишається окремою вимогою.
2. **Виправити CEO fixture.** `ceo = client()` не створює User і не входить у систему. Після правильного A03 позитивний контроль `/api/salaries/` та попередній ERP replay цією анонімною сесією перестануть працювати. Створити справжнього синтетичного CEO з групою й login, так само як manager/observer; вимогу 200 та справжніх даних залишити. Це виправлення test setup, а не ослаблення політики. Зв'язок User–Employee має бути доданий у fixture разом з A03, коли відповідне поле з'явиться.
3. **Межа ≥1000 не знижена.** `--runs < 1000` та -O відхиляються. Кожний з п'яти лічильників має завершити щонайменше 1000 послідовностей; загальний `complete` вимагає і статус, і count. Два складські інваріанти перевіряються на тих самих 1000 послідовностях, що допустимо: обидва assertions реально виконуються після кроків.
4. **Послідовності справді випадкові та відтворювані.** Є фіксований seed; 8–16 кроків зі змінами запасу, резервів, випуску, перенесення й якості; випадкові кількості/ціни; 2–5 виплат зі stale/current instances; повтор proposal після іншої успішної зміни; випадковий порядок чотирьох маршрутів для випадково вибраного контексту. Це не просто 1000 повторів одного GET. У кожній складській послідовності створено початкові два резерви 5+5; фактичний finish далі обирається випадково, тому коментар про «включення дефекту» означає його передумови, а не гарантований випуск у кожному run.
5. **Основний oracle не підмінено результатом команди.** Залишки читаються з Lot і звіряються з агрегатом збережених Movement; витрата перевіряється за кількістю Transaction, полями, однаковим ID та зворотним зв'язком Salary; replay перевіряє receipt, fingerprint й кількість Event. Допоміжна межа резервів використовує production helper `erp.reserved`; це не джерело основного oracle залишок=рухи, але саму суму резервів за потреби краще читати незалежно.
6. **Мовчазного skip немає.** Очікуваний ValueError дії допускається лише за незмінного fingerprint, після чого стан перевіряється знову. Інші помилки переривають виконання червоним. Рольовий цикл збирає всі невдалі послідовності, завершує всі 1000 і повертає ненульовий результат. Failures не перетворюються на успішні рядки звіту.
7. **Межі покриття названі коректно.** Цей script перевіряє вибрані операційні послідовності та чотири рольові маршрути. Він не є повним route/admin/snapshot/export/cache sweep: це лишається gate 4. Послідовність зміни ролі в тій самій сесії та складні кешовані контексти також не доведені цими трьома незмінними clients. Не оголошувати A03/A04 або 0.4 завершеними на підставі чотирьох зелених підінваріантів.
8. Після двох правок потрібний той самий ≥1000-run набір. До реалізації A03/A04 очікується червоний результат за реальний витік, зі збереженням seed/count/контрприкладів. PostgreSQL, Windows і глобальний route sweep цим оглядом не підтверджені.
