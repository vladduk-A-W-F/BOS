# BoS · порядок 0.4 і checklist звірки 0.5

11.09.2026. Read-only огляд master v2.1 та моделей. Реальна `db.sqlite3` не відкривалася; checkout не змінено.

## Порядок 0.4

П'ятий інваріант потребує справжньої ідентичності A03 і прав A04, тоді як лінійна черга ставить 0.4 раніше. Червоний доступ manager/observer до зарплат є відомою незакритою вимогою, а не виправленням, яке треба замаскувати під успіх.

Рекомендований запис у PROGRESS/DECISIONS: **0.4 у роботі; фінансові/складські інваріанти мають власні результати, інваріант доступу очікує A03/A04 та поки червоний**. Усі п'ять перевірок залишаються обов'язковими у verify, кожна виконує ≥1000 реальних прогонів. Загальний gate 3 не зелений, 0.4 не готовий. Наступні дозволені задачі виконуються з явно записаною залежністю, після A03/A04 запускається той самий неослаблений набір. Стоп 8.5 тут не потрібний: змінювати перелік критеріїв не потрібно.

У промпті є буквальна неузгодженість із правилом «далі з червоним не йдеш»: повна перевірка містить ще не реалізовані задачі, без яких попередній крок не позеленіє. Її слід прямо назвати в абзаці незгоди, не вигадуючи, що весь промпт буквально виконаний. Практичне трактування зберігає червоні відомі/майбутні критерії, забороняє нові регресії у вже перевіреному й не оголошує реліз готовим.

У журналі інваріантів потрібні seed, кількість запущених/успішних/невдалих послідовностей **для кожного** інваріанта, довжина послідовностей, перший відтворюваний контрприклад і ненульовий підсумок. Один ранній assert не повинен непомітно припинити 1000 рольових прогонів: зібрати факти всіх запусків, після цього завершити gate помилкою. Не отримувати очікувані права з чинної реалізації; використати незалежну прийняту матрицю ролей. Включати зміну ролі після попереднього доступу CEO, щоб перевіряти залишковий контекст/кеш. Тисяча повторів одного GET не є тисячею випадкових послідовностей.

## 0.5: безпечний snapshot і межі

1. Зафіксувати шлях джерела, SHA основного файлу та наявність WAL/SHM, час, спосіб отримання копії. Для активної SQLite із WAL потрібен узгоджений snapshot через SQLite backup API з read-only source, а не копіювання тільки основного файлу. Не використовувати `immutable=1` для читання живої WAL-бази. SHA source та нового snapshot можуть відрізнятися; зафіксувати обидва, не оголошувати це фінансовою розбіжністю.
2. Перевіряти лише новий snapshot через URI `mode=ro`, `PRAGMA query_only=ON`. Жодних migrations, seed, UPDATE/DELETE, автоматичного «відновлення» чи запуску моделей, які можуть записати дані. Наприкінці звірити SHA snapshot та джерела; зміна живого джерела іншою програмою потребує пояснення, не автоматичного висновку про нашу мутацію.
3. Спершу отримати структуру з `sqlite_master`, наявність таблиць/колонок, `PRAGMA integrity_check`, `PRAGMA foreign_key_check`. Якщо в оригінальній БД немає ERP таблиць, записати «не перевірено: відсутній контур ERP», а не створювати порожні таблиці й не називати нуль рядків успішною звіркою.
4. Приватні результати з рядками зберігати локально в `evidence/RECONCILIATION_PRIVATE/`, виключеному з Git/CI. Публічний технічний звіт містить обсяг, класи проблем і рішення; без ПІБ, контактів, зарплатних описів, документів, session keys або вмісту чатів. Для локальної адресної звірки достатньо salary/transaction/lot/movement ID та числових фактів.

## SQL-факти і точні суми

**Склад.** Читати окремо Lot і Movement; не приєднувати їх одразу до Reservation, інакше JOIN перемножить рядки. Потрібні `lot_id`, `item_id`, кількості, собівартість, валюта, тип руху, структурні зовнішні ID. Порахувати суму рухів для кожної партії, потім для номенклатури; порівняти із залишком. Окремо перевірити від'ємні залишки/резерви, резерв понад залишок, відсутні FK, партії без рухів. Сума Quantity різних одиниць не має господарського сенсу; гроші різних валют не підсумовувати.

```sql
SELECT id, item_id, CAST(quantity AS TEXT) AS quantity,
       CAST(unit_cost AS TEXT) AS unit_cost, currency
FROM erp_lot ORDER BY id;
SELECT id, lot_id, CAST(quantity AS TEXT) AS quantity, kind,
       line_id, production_id, purchase_id
FROM erp_movement ORDER BY lot_id, id;
SELECT id, lot_id, CAST(quantity AS TEXT) AS quantity,
       line_id, production_id
FROM erp_reservation ORDER BY lot_id, id;
```

Фінальні кількості/суми рахувати Decimal із текстових значень, а не float або довільним epsilon; узгоджена точність — 0,001 для кількості і 0,01 для грошей. SQLite SUM може повертати двійковий float, тому його дрібний хвіст сам по собі не є бізнес-розбіжністю. Зафіксувати необроблені текстові значення та правило точного підрахунку.

**Зарплата і джерело витрати.** Вибрати явні поля, без Employee JOIN/опису. Для paid перевірити існування пов'язаної Transaction, direction=out, category=salary, точну суму/валюту/дату. Окремо показати pending/cancelled із прив'язаною витратою; нічого не виправляти.

```sql
SELECT s.id AS salary_id, s.status, s.transaction_id,
       CAST(s.amount AS TEXT) AS salary_amount, s.currency AS salary_currency,
       s.payment_date, t.id AS expense_id, t.direction, t.category,
       CAST(t.amount AS TEXT) AS expense_amount,
       t.currency AS expense_currency, t.date AS expense_date
FROM finance_salary s
LEFT JOIN finance_transaction t ON t.id = s.transaction_id
ORDER BY s.id;
SELECT t.id, t.currency, CAST(t.amount AS TEXT) AS amount, t.date
FROM finance_transaction t
LEFT JOIN finance_salary s ON s.transaction_id = t.id
WHERE t.category = 'salary' AND t.direction = 'out' AND s.id IS NULL
ORDER BY t.id;
```

**Кандидати на дубль.** Однакова сума+валюта+дата — лише група схожих операцій. Не присвоювати їй статус підтвердженого дубля, не прив'язувати її до працівника через здогад чи текстовий опис, не називати суму «переплатою». Доказ дубля потребує одного й того самого документованого джерела/ідентифікатора виплати або підтвердження людини. Структурно можна перевірити декілька Salary на одну transaction_id або порушення унікального періоду, якщо такі дані існують; це окремий факт, не автоматичний доказ двох банківських переказів.

**Інші фінансові межі.** За наявності відповідних таблиць перевірити Invoice `0 ≤ paid ≤ amount`, Purchase `0 ≤ received ≤ quantity`, Production `0 ≤ produced ≤ quantity`. Факти облікової системи не підтверджують стан банківського рахунку. Нуль знайдених розбіжностей не доводить повноту всіх первинних документів.

Кожна проблема у результаті: `ID перевірки → source IDs → точні факти → клас (розбіжність / несв'язаний запис / кандидат / не перевірено) → пропозиція → потрібне рішення`. Якщо підтверджено розбіжність робочих даних, яка стосується грошей, спрацьовує стоп 8.1: повідомити факт і запросити рішення щодо конкретного випадку, не перезаписувати історію. Сама група схожих сум/дат такого висновку не доводить.
