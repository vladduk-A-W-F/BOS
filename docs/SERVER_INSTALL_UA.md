# BoS · окрема серверна інсталяція

Серверний профіль використовує наявний Django та інтерфейс BoS. Кожна компанія має власні код, Python-середовище, базу, приватні документи, секрет і назву сесійного cookie. Поточний стенд — Linux amd64, Python 3.12, SQLite, Waitress 3.0.2 і Caddy 2.11.1. Проксі та застосунок слухають лише loopback. Публічний домен, Windows, PostgreSQL, оновлення та відновлення приймаються окремо.

**Стан приймання:** A09 НЕ ПРИЙНЯТА. Остаточний стенд пройшов 30 із 31 сценаріїв; на 13 MiB клієнт отримав ConnectionResetError замість HTTP 413. Звичайна зупинка перевірена, завершення всіх активних записів перед backup належить A10. Це інструкція стенда розробки, не паспорт виробничого релізу.

## Що робить інсталятор

Команда створює новий каталог, перевіряє повний SHA-пакет коду, створює окрему venv, встановлює точні версії з підготовлених wheels, застосовує міграції та збирає статику. Бізнес-таблиці залишаються порожніми. Навчальні бази й медіафайли не входять до пакета.

Шляхи пакета, приватного реєстру інсталятора й компанії мають бути окремими. Каталог компанії до першого запуску не повинен існувати. Інсталятор не приймає довільний наявний каталог навіть із скопійованим файлом manifest. Незавершену власну установку можна продовжити за UUID із того самого реєстру; готову установку не можна повторно мігрувати командою продовження.

## Підготовка й установка

Оператор заздалегідь готує wheels із `requirements-server.txt`, перевірений Caddy, TLS-сертифікат із правильним hostname та приватний ключ. Команда установки не звертається до індексу пакетів і не виконує незакріплені транзитивні залежності. Відсутній пакет або несумісні залежності дають помилку.

З каталогу BoS побудуйте пакет у новому окремому каталозі:

```bash
python3.12 scripts/package_server.py --output /srv/bos-package
```

Батьківський `/srv` у прикладі вже існує й доступний оператору. Для локального стенда можна використати інший абсолютний шлях у власному каталозі.

```bash
python3.12 /srv/bos-package/scripts/install_server.py \
  --source-root /srv/bos-package \
  --target /srv/bos-company \
  --registry /srv/bos-installer-registry \
  --origin https://localhost:8443 \
  --wheelhouse /srv/bos-wheels
```

`application_provisioned=true` підтверджує встановлення програми. На цьому етапі код виходу 2 та `complete=false` означають, що запуск HTTPS ще не перевірений. У звіті наведено UUID установи, версію, SHA коду та результати міграцій. Значення секрету у звіт не потрапляє.

Після перерваного встановлення повторіть ту саму команду з `--resume UUID`. Інші шлях, пакет, origin, невідомі файли або замінений каталог будуть відхилені. Збережені файли інсталятор автоматично не видаляє.

## Запуск і зупинка

```bash
python3.12 /srv/bos-package/scripts/lifecycle_server.py \
  --target /srv/bos-company \
  --registry /srv/bos-installer-registry \
  --installation-id UUID \
  --caddy /srv/caddy \
  --certificate /srv/tls/localhost.crt \
  --private-key /srv/tls/localhost.key \
  --ca-certificate /srv/tls/local-ca.crt \
  --http-port 8080
```

Для сертифіката від системно довіреного CA параметр `--ca-certificate` не потрібен. Тестовий CA передається лише клієнту перевірки: команда не додає його до системного сховища довіри. Приватний ключ повинен мати права 0600.

Подія `bos.bundle.ready` з’являється після реального TLS-з’єднання і двох успішних health-запитів. Відкрийте origin установки в браузері з налаштованою довірою до сертифіката. HTTP перенаправляється на цей точний origin. Невідомий Host відхиляється; `/media/` не публікується. Документи доступні через авторизований API з перевіркою SHA.

Процес працює у поточному терміналі. `Ctrl+C` або SIGTERM зупиняють лише створені ним Waitress і Caddy. Другий процес для тієї самої компанії відхиляється. Повторний старт перевіряє код і конфігурацію; він не запускає міграції та не додає демо.

**Перший адміністратор — відкрита умова установки.** Provision не створює технічний акаунт автоматично. Штатні Django-команди `createsuperuser` і `link_bos_user` існують, але підтриманого операторського CLI для їх запуску з перевіреною приватною конфігурацією цієї установки ще немає. Отже повний початковий вхід клієнта цим пакетом не прийнятий. Звичайний `manage.py` без правильного installation environment не є готовим bootstrap. Обмеження й source-підстава: [D03_OPERATOR_BOOTSTRAP_UA.md](../evidence/D03/D03_OPERATOR_BOOTSTRAP_UA.md).

Технічний адміністратор після підготовленого входу створює звичайні Django-акаунти; для бізнес-акаунта призначає рівно одну групу `ceo`, `manager` або `observer`, а також окремі дозволи на документи/експорт. Паролів за замовчуванням немає. Правила доступу — у `docs/ACCESS_UA.md`.

## Перевірка власної нової тестової установки

```bash
BOS_SERVER_WHEELHOUSE=/srv/bos-wheels \
BOS_CADDY_BIN=/srv/caddy \
python3.12 scripts/check_install.py --output /srv/install-check.json
```

Ця команда створює власну тимчасову установку, двох синтетичних користувачів і короткостроковий тестовий сертифікат. Виконує справжній вхід, CSRF-відмови, завантаження/скачування/перевірку документа, перевірку лімітів, ролей, статики, зупинку й повторний запуск. Робочі бази не є вхідним параметром. Без Caddy, wheels або OpenSSL перевірка повертає ненульовий код.

Health розкриває тільки статус. Readiness читає SQLite у режимі `ro`, перевіряє міграції, основну таблицю та доступність каталогу документів; вона не замінює звірку фінансів, квоти або backup/restore. Журнали застосунку містять дозволені службові поля та серверний correlation ID; журнали проксі проходять окреме очищення до запису на диск.

Модуль `runtime/status` показує серверний профіль і робочий режим даних. Фінансові KPI старого CEO dashboard залишаються позначеними як демонстраційні; локальний органайзер браузера не видається за серверну спільну базу. Готовність усього MVP визначають усі 11 критеріїв `verify`.
