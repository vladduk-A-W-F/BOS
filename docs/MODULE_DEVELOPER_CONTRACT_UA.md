# BoS · контракт модулів і спільних видів

Реєстр `bos.modules.v1` описує наявні функції Django та форми BoS. Чотири види «Контроль», «Потік», «Мережа», «Фокус» використовують ті самі записи й команди. Реєстр не містить власної бази, фінансового обліку або виконуваних виразів.

## API

`GET /api/erp/modules/` потребує чинної серверної ролі BoS. Відповідь приватна, `Cache-Control: private, no-store`, `Vary: Cookie`. Наявні middleware та `Policy` перевіряють користувача; перед відповіддю повторно звіряється revision його прав. Зміна прав під час побудови повертає `409 read_state_changed`. POST/інші методи не встановлюють модулі.

Контракт:

- `schema`: `bos.modules.v1`.
- `data`: `schema=bos.network.v1`, `endpoint=/api/erp/network/`, `export_endpoint` або `null` за відсутності права експорту.
- `views`: `{id, type, name}`. `control/list/Контроль`, `flow/kanban/Потік`, `network/map/Мережа`, `focus/inbox/Фокус`.
- `modules`: `{id,name,depends,models,views,actions,menus,permissions,automations}`. Меню мають чинні `section/sub`; залежності посилаються на ID інших видимих модулів.
- `models`: `{id,name,source,key,label_field,status_field,columns,relations,actions,views,default_view}`. `source.rows` є точним шляхом `rows.<id>` у мережевій відповіді; `source.django` документує фактичну модель, а не надає універсальний CRUD.
- `columns`: `{key,label,type,finance}`. Типи: text, integer, quantity, money, date, datetime, status. Кількість і гроші надходять із чинної проєкції; `money` зберігає десяткові рядки. Дескриптор не змінює точність чи валюту.
- `relations`: `{field,target}` для зв’язків між видимими моделями. Якщо ціль відсутня в поточній композиції або ролі, зв’язок не публікується.
- `actions`: `{id,name,model,ui_action,presets,preview_endpoint,confirm_endpoint,authorization}`. `presets` зіставляє назву параметра існуючої форми з полем поточного рядка. Відсутні значення не треба вигадувати.
- `permissions`: `{role,write,finance,export}` від поточного `Policy`. Це підказки для UI; кожна дія повторно перевіряє права й стан на сервері.
- `configuration`: `{mode:server_owned, mutable:false, scope:navigation_composition}`. `automations` поки порожній: реєстрація модулів не вмикає агентів або автопроведення.

Моделі: `points`, `lots`, `purchases`, `orders`, `jobs`, `transfers`, `invoices`, `retentions`. Ключ рахунку `invoice_id`, решти `id`. Стан партії читається з `quality`, закупівлі з `effective_status`, замовлення/роботи/переміщення/утримання зі `status`. Для точки та рахунку `status_field=null`: UI не повинен вигадувати статус.

Дані завжди беруться з чинного `/api/erp/network/` з фільтрами філії, точки й валюти. Права на документи/записи залишаються у `Policy`; філія є організаційним фільтром. Реєстр не створює нової ізоляції компаній або філій. Недоступні записи/посилання можуть бути відсутні в мережевій відповіді навіть за наявності дескриптора моделі.

## Композиція та доступ

Серверне налаштування `BOS_ENABLED_MODULES` необов’язкове; за замовчуванням описуються всі шість наявних модулів: operations, warehouse, procurement, sales, production, settlements. Можна вказати список/кортеж відомих ID разом з усіма залежностями. Наприклад: `('operations', 'warehouse', 'procurement')`. Порожній список, дублікати, невідомий ID, неправильний тип, відсутня залежність або цикл повертають `503 module_configuration_invalid` без часткового каталогу.

Це композиція навігації та видів. Приховування модуля не видаляє таблиці, історію чи файли, не зупиняє чинні backend endpoints і не замінює налаштування прав. Немає endpoint установки/видалення plugin та завантаження довільного коду.

CEO отримує фінансові моделі/колонки/дії. Manager не отримує `retentions`, грошові колонки, фінансові дії чи CEO-only команди. Ідентичність рахунку, клієнт, строк і валюта лишаються доступними manager/observer згідно з чинною мережевою проєкцією: модуль `settlements` для цих ролей містить лише метадані `invoices`, без сум і фінансових дій. Observer отримує опис доступних видів і моделей без будь-яких дій та експорту. Навіть наявна у каталозі дія може бути недоступною конкретному запису через його документи, стан чи джерела. Клієнтські `role`, `modules`, інші query-параметри не змінюють композицію чи права.

## Додати опис існуючої функції

1. Спочатку реалізувати й перевірити модель, проєкцію, `Policy`, транзакційний command/service шлях, журнал і preview/confirm. Окремий write через реєстр заборонений.
2. Додати незмінний `Model`, колонки та зв’язки у `erp/module_registry.py`. Джерело повинно існувати в серверній мережевій проєкції. Персональні/фінансові поля не публікувати за замовчуванням.
3. Додати `Action` лише для чинного `erp_<writer>` з `erp.service.SCHEMAS` та існуючої форми `ERP_ACTIONS[ui_action]`. Прив’язати тільки параметри, які writer приймає. Автоматичне виконання або права через manifest не надаються.
4. Призначити модель рівно одному `Module`, вказати залежності й чинне меню. Не додавати взаємні залежності.
5. Перевірити авторизований GET, ролі, відсутність прихованих сум, посилальну цілісність, відмову для невідомої композиції, відсутність записів у бізнес-таблиці. Для реального нового модуля потрібні окрема картка й незалежний review.

Відсутній реєстр або помилка його завантаження не дозволяє UI підміняти його ширшим локальним списком. Кнопки відкривають чинні форми; preview і confirm залишаються явними. Статуси канбану отримуються з фактичних рядків; переміщення картки не має приховано записувати новий статус.

Ця фаза не оголошує реалізованими OCR/LLM, конструктор довільних полів, бухгалтерський ledger, портал чи правову відповідність. Для них потрібні окремі контракти та перевірки.
