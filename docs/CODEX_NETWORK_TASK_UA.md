## Що вже реалізовано

Розділ ERP **«Мережа та операції»** працює з Django-моделями, спільним Policy та наявними preview/confirm. Карта України, реєстри й показники мають однакові фільтри філії, точки й валюти. Немає окремого фінансового стану в браузері.

| Блок | Призначення | Що перевірити |
|---|---|---|
| Огляд | Точки, залишки, рух між складами, борг та утримання | Карта/таблиці/підсумки узгоджені; точки без координат чесно позначені |
| Операції | Закупівлі, продажі, виробництво, переміщення, рахунки | Кнопка відкриває робочу форму; preview не записує; confirm має один ефект |
| Документи й звірки | Доступні документи, їхні групи, рівні доступу та переходи до звірок | Немає прихованих документів або сум; завантаження повторно перевіряє права |
| Контроль строків | Стадії заявок, прострочення, часові позначки, тривалість | Невідома дата не стає нулем; синтетична історія не видається за фактичне прискорення |

Нові дані та типові форми — UAH. Історична валюта зберігається. Ручний EUR/USD конвертер лише довідковий, вимкнений за замовчуванням і не змінює облік. Прив’язка філії є організаційним фільтром, а не новою межею безпеки. Країна походження/призначення позначає міжнародний процес; митні й банківські інтеграції не підключені.

## Окремий демопрофіль

Прочитай `docs/NETWORK_DEMO_UA.md`. Створи нову порожню SQLite-базу й окрему media-теку **поза робочими даними**. Для синтетичної перевірки застосуй `verification_settings` з явними `BOS_DATA_MODE=demo`, `BOS_TEST_DB_NAME=<новий абсолютний шлях до check_network.sqlite3>` і `BOS_TEST_MEDIA=<нова абсолютна тека>`. Для PowerShell задавай ці значення через `$env:...`, для POSIX через `export`; не використовуй наявний шлях за замовчуванням.

```text
python manage.py migrate --settings=verification_settings --noinput
python manage.py seed_network_demo --dataset workday --settings=verification_settings
```

Для `disruption` та `collections` потрібні дві інші порожні бази. Немає reset/force; повтор одного набору зберігає виконані після seed дії. Seed не створює паролів/облікових записів. Для браузера налаштуй лише локальні синтетичні акаунти ролей через чинний механізм BoS, не публікуй паролі та приватні media. Не використовуй verification_settings як production-профіль.

## Адресна перевірка нового кандидата

У новій перевірочній БД/media, після перевірки лімітів і попередніх receipts:

```text
python manage.py makemigrations --check --dry-run --settings=verification_settings
node scripts/build_frontend.cjs
node scripts/checks/network_ui.cjs
```

Перед будь-яким запуском звір історію спроб кожної проблеми. Модуль `erp.test_network` вже мав 3 invocations: його повтор заборонений автоматично. Не скидай ліміт новою назвою, середовищем або candidate. Читай наявні receipts. Нові конкретні регресії/PG-сценарії дозволені тільки як інший обґрунтований scope з власним обліком, без повтору вичерпаної проблеми. Для інших модулів також звір фактичну історію; загальна команда прогону навмисно не задана. Збережи raw stdout/stderr, exit codes, точні назви тестів і source SHA. PostgreSQL 16 залишається окремим **новим адресним** scope: лише disposable `bos_verify_<16 hex>` через `scripts/check_support.py`, без production DSN. Перевір два конкурентні підтвердження одного переміщення/утримання під реальним mutex. SQLite та підмінені frontend handlers цього не доводять. Не запускай загальні workflows для обходу історичних обмежень.

## Браузерне приймання на доступному локальному середовищі

- Desktop 1440×900 та вузькі екрани 390×844 і 320×740: українські підписи, читабельність, таблиці, горизонтальний scroll, клавіатура/фокус, dialog close/return. Збережи скріншоти, console і фактичні HTTP-відповіді.
- CEO, manager, observer: порівняй видимі поля, документи й доступні дії; observer не експортує. Спроба прямого API не обходить Policy.
- Філія → точка → валюта: однаковий зріз карти, KPI, реєстру та CSV/JSON. EUR-історія не входить у гривневий підсумок.
- Переміщення: відправити → «у дорозі» → прийняти → окрема pending-партія → перевірити якість. Повтор того самого proposal має один ефект. Preview/cancel не змінює залишки.
- Утримання: встановити → записати лише доступну оплату → звільнити → оплатити залишок. Саме звільнення не зменшує дебіторку.
- Заявка → пропозиція → пов’язана закупівля → часткове/повне приймання: покажи реальні джерела та часові позначки, поясни відсутні дані.
- Змінити право на документ під час читання: оновлення/конфлікт, без витоку старого scope. Змінити джерело після preview: typed stale conflict і новий перегляд. При втраті відповіді confirm повторюється лише початковий proposal ID.
- Ручний конвертер: вимкнений спочатку; правильний довідковий еквівалент; не приймає нуль/від’ємний курс; після reload валюта та суми записів незмінні.

## Окрема наступна картка NETWORK-PLAN-CURRENCY

Незалежний review виявив стару невідповідність: production-material цикли `erp.experience.next_step` можуть запропонувати матеріал іншої валюти; writer відхиляє несумісну собівартість. Не змішуй це з прийнятими новими sales/network змінами. Діагностуй конкретну пропозицію, додай вузьку синтетичну регресію UAH-job/EUR-lot, узгодь підбір резервів/матеріалів/закупівель із валютними правилами writer. Allowlist: `erp/experience.py`, окремий regression-test, evidence. Прийняття: пропозиція виконується для сумісного ресурсу або пояснює відсутність; чужа валюта не покриває потребу. Це не зміна валюти історичних записів.

## Результат

Онови `docs/orchestration/NETWORK_OPERATIONS_UA.md`, STATE/QUEUE та draft PR тільки підтвердженими фактами: що прийнято, що виправлено, raw evidence, SHA, відомі обмеження, наступні 1–3 картки. `TECHNICAL_READY=false`, `PILOT_ALLOWED=false` лишаються чинними до окремих умов. Не зливай main і не активуй Django production автоматично.

Щоденна перевірка ChatGPT читає синхронізовані GitHub-коміти/PR/CI; вона не бачить незбережені файли чи процеси на ПК. Після локального етапу збережи звіт і відправ свою review-гілку, щоб наступна перевірка побачила результат.
