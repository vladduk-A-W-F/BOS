# dev.10: кандидат і збереження owner-local даних

Обсяг — розділ 3 `BOS_STRATEGY_RELEASE_RU.md`: три навчальні кейси,
збереження прогресу й даних власника. Це інструкція підготовки доставки,
а не квитанція виконаної установки. Точний пакет — `DEV10_CANDIDATE.json`.

## Кандидат

- Основа: main `1dcaa8e0c84a109cc8a5df59f894d384268fe061`, після PR #16–18.
- Єдина версія UI/API: `boss_project/version.py`, `0.3.0-dev.10`.
- Пакет містить Django-код, `training`, `crm`, owner-local settings,
  наявні assets і посібники. БД, media, state та секретів у ньому немає.
- `BOS_PACKAGE.json` містить SHA-256 кожного включеного файла. Повний
  manifest і пакет зберігаються на D:; посилання та SHA — у паспорті кандидата.
- Frontend, посібники та код навчання/CRM не змінено після прийнятого джерела.
  45/45 SQLite перевірок успадковуються лише для незмінених байтів модулів.
  PG16, браузер, пароль і фактична доставка цим не доведені.

## Умови перед установкою

1. Незалежне рев'ю поточного head кандидата, CI і адресний PG16-звіт Claude
   за розділом 3; лише потім злиття та фіксація прийнятого commit.
2. Для `bos3-local` потрібна **чиста Git-копія** цього commit на D:.
   Каталог code-only пакета не замінює її: launcher перевіряє Git і весь source digest.
   Звірити всі файли копії з `BOS_PACKAGE.json`; не підмінювати source старим checkout.
3. Свіжо перевірити `D:/3/BOSDev/local-bos3/owner/state/prepared.json`,
   source digest, власника процесу, БД `data/bos3-fasteners.sqlite3` та media.
   Історична квитанція dev.8 із start exit 1 не доводить поточний стан.
4. Виконати штатний `scripts/bos3-local.ps1 stop` з поточного source,
   лише якщо процес підтверджено як власний. Невідповідність PID/source або
   незавершена попередня спроба — зупинка доставки, без force/видалення receipt.

## Резервна копія й застосування

5. До зміни прив'язки source створити новий приватний backup-каталог
   усередині захищеного owner-local root; перевірити успадковані ACL.
   SQLite скопіювати через стандартний `sqlite3.Connection.backup` із read-only
   джерела, перевірити `PRAGMA integrity_check` на копії. Зберегти media,
   `prepared.json`, `owner-access.json`, `runtime-secrets.json`; перевірити
   хеші копій. Секрети, рядки БД та паролі не виводити й не додавати до Git.
6. До установки звірити перелік потрібних міграцій на копії БД. Якщо поточна
   схема не підходить, спершу підготувати точний план збереження даних і його
   незалежну перевірку. Не викликати `init`, seed, reset, flush чи генерацію пароля.
7. Лише після перевіреної резервної копії змінити у `prepared.json` два поля:
   `source` та `source_sha256`; решта поля і захищені файли мають бути незмінними.
   Штатний `start` викликати з нової прийнятої Git-копії. Без автоматичних повторів.
8. Звірити запущений source/version, дані й media, незмінність пароля та
   навчального прогресу. Перевірка звичайного входу й узгоджених маршрутів
   має окремий фактичний результат; старий HTTP 200 не зараховувати.
9. За розбіжності не повідомляти про успіх: штатно зупинити власний процес,
   зберегти діагностику й відновити точні дані/source із перевіреної копії
   за незалежно перевіреною процедурою; не замінювати дані синтетичним seed.

## Невиконана частина доставки

Поточний PR готує code-only кандидат. Кроки 3–9 **не виконано**.
Історичні dev.8/dev.9 maintenance/recovery templates мають старі точні pins
і витрачені вікна; запускати їх для dev.10 без нової перевіреної прив'язки не можна.
Після рев'ю кандидата інтегратор готує й незалежно перевіряє конкретний
backup/rebind/restore запуск за свіжим станом установки та цим прийнятим commit.
Дозвіл власника на dev.10 із резервною копією вже записаний в AGENTS.md;
нового загального питання про перевстановлення не потрібно.

Після успішної доставки — квитанція з source, manifest, адресою і результатом
збереження даних, потім 10 кроків ручної перевірки з розділу 3.1 стратегії.
`TECHNICAL_READY`, `PILOT_ALLOWED` та загальна прийомка цим PR не змінюються.
