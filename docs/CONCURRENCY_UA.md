# BoS · повтор і одночасні дії

## Для користувача

Натискання «Зберегти» у фінансовій формі створює один намір. Під час збереження поля й кнопка заблоковані. Якщо мережа перервалася або сервер повернув конфлікт, форма зберігає значення; повтор незмінної форми використовує той самий ключ. Успішний повтор показує той самий запис. Якщо запис уже архівовано, виплачено чи дозволено відредаговано, повертається його поточний стан; старі значення не відновлюються.

Зміна даних або відкриття нової форми починає новий намір. Два різні платежі з однаковими сумою й датою дозволені. Після перезавантаження сторінки спочатку перевірте список збережених записів: це вже нова форма, її попередній незавершений стан не зберігається між завантаженнями.

ERP-перегляд видає proposal_id. Повтор погодження цього ID має один матеріальний результат. Застарілі джерела, зміна прав або вичерпання залишку дають відмову без часткових рухів. Виплата одного нарахування Salary завжди посилається на одну витрату.

## Контракт інтеграції

Нові `POST /api/transactions/` і `POST /api/salaries/`, включно з JSON aliases, потребують заголовка `Idempotency-Key`. Допустимі 1–128 ASCII літер, цифр і `_ . : -`. Ключ створює клієнт до відправлення; після network/409 його не генерують повторно. Авторизація та CSRF залишаються обов’язковими.

| Результат | Дія |
|---|---|
| 201 | Створено запис або повернуто той самий PK. Перевірити відповідь та оновити список. |
| 400 | Виправити обов’язкові поля або некоректний ключ. Зміна payload — новий намір. |
| 409, запис зайнятий | Повторити незмінний запит із тим самим ключем після завершення іншої дії. |
| 409, ключ уже використано для інших даних | Перевірити початковий намір; для справді нової операції використати новий ключ. |
| 401/403 | Відновити дозволений доступ; ключ не обходить актуальні права. |

Користувач і тип команди визначають область ключа; поточна роль визначає дозвіл на виконання. Різні користувачі не отримують чужі результати. Номер рядка, повний payload, валюта та джерельні FK перевіряються на сервері. Однакові сума й дата не використовуються для злиття записів.

Native admin передає прихований `bos_operation_id`. Внутрішні `save_transaction` / `save_salary` приймають `operation_id` і `actor`; використовують той самий writer. Без ключа внутрішній виклик означає новий однократний факт, а не ідемпотентний повтор. Зовнішній LLM-контур не входить до перевіреного запуску.

## Межі доказу

Складські рухи та документний допуск користуються одним ERP mutex; зміну чинної версії документа не можна вклинити між захищеним рішенням і рухом. `scripts/check_concurrency.py` запускає реальні пари HTTP/ORM, перевіряє залишки, валюти, рухи, audit, receipt і rollback. SQLite не є доказом поведінки PostgreSQL. Критерій 5 вимагає обидві СУБД; непроведена перевірка залишає загальний verify червоним.
