# BoS · результат інвентаризації та рішення щодо A05

11.09.2026 · за `BoS_MASTER_PROMPT.md` v2.0 · контрольна точка, не реліз.

**Спрацювала ваша стоп-умова 8.6:** інвентаризація виявила **12 окремих дефектних місць**, два відомі та десять додаткових. Незалежний аудитор і основний виконавець узгодили цей підрахунок після повторного відтворення. API-обгортки, варіанти URL та одиничне/масове видалення одного типу запису не подвоюють число місць.

Код застосунку не змінено. Підготовлено журнал усіх 30 задач, матрицю 85 шляхів запису, докази та два прийняті ADR. Таблиця охоплює всі 26 ERP-дій, фінансові API, адмінку, документи, закупівлі, старі обробники ШІ та службові команди.

## Що підтверджено до виправлення

| Сценарій | Фактичний результат |
|---|---|
| Два резерви 5+5 із партії 10, випуск 10 | Залишок **5**, сума рухів **0**. |
| Два одночасні виклики виплати 100 | Створено **дві витрати на 200** загалом. |
| Створення/редагування зарплати через API та адмінку | Можливі статус «виплачено» без витрати та зміна суми після виплати. |
| Редагування пов’язаної витрати | Суму та напрям можна змінити без узгодження із зарплатою. |
| Видалення зарплати, витрати або працівника | Втрачається джерело витрати або залишається виплачена зарплата без витрати. |
| Зарплата в EUR | Витрата записується в **UAH**. |

Незалежний запуск відтворив **18 діагностичних сценаріїв** на новій синтетичній SQLite: exit 0 означає відтворення дефектів, stderr порожній. API й адмінка викликались через Django Client із перевіркою CSRF; паралельна виплата — через справжній ORM у двох потоках. Бізнес-функції не підмінялися. SHA коду та обох наявних баз до/після збігаються. Результатів **після виправлення немає**: реалізацію зупинено за вашим правилом.

## Конкретне розширення A05

Пропоную змінити оцінку **з 3–5 на 6–10 людино-днів**: приріст 3–5. Це оцінка трудомісткості, не дата релізу.

| Частина | Людино-дні |
|---|---:|
| Спільні правила створення й зміни фінансових записів через API | 1,5–2,5 |
| Збереження історії та джерела виплати при архівуванні | 1–1,5 |
| Ті самі правила для форм і масових дій адмінки | 1–2 |
| Приєднання решти наявних шляхів запису, документів і обробників ШІ | 1–2 |
| Перевірки реальних API/admin-дій, повторів і повноти інвентарю | 1,5–2 |

Робочі дії мають виконуватися через спільні команди зі збереженням історії; приховування кнопок не є виправленням. A01/A02 залишаються першими. A03/A04, конкурентність A06, обмеження й міграції A07 та процеси B01/B03 не включені в A05 повторно. Для передачі валюти й перевірок EUR/USD/UAH додаткова оцінка A02 — 0,25–0,5 людино-дня. Інших задач плану не перепогоджуємо.

Звірка робочих даних 0.5 **не запускалася**: виявлені розбіжності стосуються синтетичних прикладів. PostgreSQL, Windows, браузер, навантаження, зовнішня модель і повний `verify` **не запускалися**. PostgreSQL/Windows-виконавця в перевіреному середовищі не виявлено; це не доказ неможливості їх підготувати. Продукт за вашим критерієм ще не готовий.

**Відкрите рішення:** погодити наведене розширення A05 та поновити A01 → A02, або залишити реалізацію на цій контрольній точці до перегляду обсягу. Робочі гроші та історичні записи не виправлялися.

**З чим не погоджуюся у промпті:** обидва початкові дефекти не мають однакової причини. У `finish` уже є транзакція й блокування, але кілька ORM-об’єктів зберігають застарілий стан однієї партії; у зарплаті перевірка статусу відбувається до захищеного запису. Тому потрібні різні мінімальні виправлення з перевіркою спільних інваріантів. Прийнятий стек і порядок роботи зберігаються.
