## Уточнения перед возможным допуском

1. **Оракул recipient history неполон.** S3 требует тот же audit ID, actor, reason, before/after и transition, но не сравнивает `history.items[].handoff` с `S2.receipt.handoff`. Это сравнение важно для сквозного доказательства сохранения `expected_result`, recipient и всех `source_refs` при чтении другой ролью. Финальный manifest должен требовать равенства этих полей и отдельно учитывать добавляемые в текущей проекции list/detail `handoff.current`/`state` (`tasks/history.py:21-27`, `tasks/handoffs.py:94-103`). Снимки raw response позволяют выполнить это сравнение; требование надо сделать явным.
2. **Fixture не закрепляет различие результатов.** S3 требует `expected_result` отличным от сохранённого фактического `Task.result`, но `synthetic_instance_contract_if_admitted.source_fixture` оставляет исходное значение `Task.result` неопределённым. До будущего исполнения нужно записать точное исходное `Task.result` и выбрать отличный `expected_result`, затем проверить неизменность `Task.result` после S2 и S5 (`tasks/handoffs.py:65-90`, `tasks/queries.py:55-62`).
3. **Усилить атрибуцию replay.** S5 задаёт исходную sender session, а status API возвращает `same_session` (`tasks/history.py:51-63`). Финальный manifest должен проверять `same_session=true`, совпадение `proposal_id` и неизменность числа/ID `ActionProposal` после S5. Это уточнение делает утверждение «тот же proposal в той же сессии» проверяемым по raw HTTP и snapshots.
