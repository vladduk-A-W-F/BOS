# БОС — команды цепочки и экономии контекста

Назначение: выполнять механическую сверку обычными локальными командами; передавать готовые результаты существующим чатам через проверяемые короткие сообщения. Отдельный постоянно работающий процесс или дополнительный таймер не создаётся. Команды используют существующие BOSDev, Codex и журнал доставки.

## Команды

Из задачи Codex или её терминала:

```powershell
# Свежая сверка main/integrator/writer/design/quality и обновление локального индекса.
& 'D:\3\BOSDev\setup\bos-flow.ps1' refresh

# Короткий сохранённый статус без модели и без сетевого опроса.
& 'D:\3\BOSDev\setup\bos-flow.ps1' status

# Подсказки из legacy индекса C; не источник продуктовых назначений BoS 3.0.
& 'D:\3\BOSDev\setup\bos-flow.ps1' next

# Доступные рабочие профили; настройки уже работающих чатов не меняются.
& 'D:\3\BOSDev\setup\bos-flow.ps1' models

# Проверить подготовленную передачу без отправки.
& 'D:\3\BOSDev\setup\bos-flow.ps1' handoff -Packet 'D:\3\BOSDev\handoffs\flow-packet.json'

# Передать ровно это задание через ledger.
& 'D:\3\BOSDev\setup\bos-flow.ps1' handoff -Packet 'D:\3\BOSDev\handoffs\flow-packet.json' -Execute
```

`flow-packet.json` — пример имени; сначала создаётся конкретный пакет. `refresh` не запускает модель, тесты, приложение или новую задачу. Он один раз запрашивает статусы шести чатов (`main`, `integrator`, `writer`, `design`, `quality`, `enablement`), отдельно добирает отсутствующих адресатов, сохраняет cursor и обновляет индекс. Недоступный адресат становится unknown; старый результат сохраняется. `status`/`next` сообщают о просроченном индексе. `next` строит подсказки из старых C queue/config/observer и отчётов; его actions и available_chat_owners не разрешают продуктовые назначения BoS 3.0. Текущие карточки и зависимости берутся из `docs/orchestration/QUEUE.json#current_bos3.tracks`, а sole integrator и граница запусков — из текущего `execution` в `docs/orchestration/STATE.json`; `CONTROL_STATE.json` сохраняет датованные состояния. Эти команды не выдают idle за разрешение на продуктовую работу и не оценивают свободные subagent-слоты по числу чатов.

Дополнительное поле `next.current_bos3` читает только точный HEAD канонической копии: `docs/orchestration/QUEUE.json#current_bos3.tracks` задаёт карточки, а текущий `execution` из `docs/orchestration/STATE.json` — sole integrator и границу запусков. Позднее подтверждённое статическое применение GC-F06 показано отдельно от планового статуса карточки по точному operational receipt. Хеши контрольных документов и источников выводятся без длинной истории. Если HEAD, Git-чистота фиксированных документов, их сырые рабочие байты между двумя чтениями, receipt, карточка или хеши не совпадают, поле получает `NEEDS_RECONCILIATION` и не предлагает продуктовую работу. Допустимая CRLF-разница между Git blob и рабочим файлом показана отдельными хешами, а не считается правкой. `available_chat_owners` означает только liveness, без права на slot, claim или assignment. Рекомендации `REVIEW`/`PREPARATION` не устанавливают dynamic QA, admission или готовность runtime.

## Цепочка

Разработчик → QA → независимый reviewer → подготовка пакета → решение текущего integrator → последовательное применение → фактическая квитанция.

1. Текущий integrator заранее задаёт существующую canonical карточку, source, завершённые зависимости, копию, allowlist, допустимые проверки/среду/лимит и критерий готовности. Для незавершённой проверки не требуется повторно обсуждать уже выданное точное назначение.
2. Автор сохраняет собственный отчёт. Следующий назначенный получатель получает короткую передачу с exact hashes. Полные логи остаются в файлах; сам факт передачи не создаёт независимый verdict.
3. При готовом результате integrator/контролёр вызывает `next` для сверки legacy отчётов и статусов, затем сверяет новое evidence и текущее владение по каноническому плану BoS 3.0. Независимые части можно назначать одновременно, максимум три активных subagents плюс их root. Перед запуском используются фактические collaboration.list_agents, отдельные копии и непересекающиеся файлы. Интеграция и ERP mutex остаются последовательными.
4. На новом результате, блокере или завершении передачи выполняется одна сверка. Нет циклов «получил — подтверждаю», бесконечного polling и повторного чтения всего чата. Существующий heartbeat — резервная сверка.
5. Обязательный FAIL/skipped/NOT_RUN сохраняет пакет незавершённым. Текущий integrator принимает конкретный hash/target; применение фиксируется отдельным receipt. Команды сами не меняют product queue/claims/STATE, готовность или source pin.

## Модель и контекст

| Профиль | Модель/усилие | Применение |
|---|---|---|
| none | Без модели | Простой, статусы, хеши, индексы, проверка схемы |
| economy | gpt-6-luna / medium | Короткое резюме evidence, ограниченная механическая документация |
| standard | gpt-6-sol / medium | Ограниченная реализация или выполнение уже проверенного QA-плана |
| review | gpt-6-sol / high | Независимый review кода и evidence |
| critical | gpt-6-astra / high | Сложная диагностика, архитектура и существенные межмодульные решения |
| inherit | Текущая модель адресата | Главный и назначения, для которых явная смена не нужна |

Это выбранная для BoS рабочая политика, не утверждение о точной цене или проценте экономии. Наличие моделей и параметров проверено по свежей схеме установленного `send_message_to_thread`. В официальной документации описаны [модели и усилие subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents). Обычный send без override сохраняет настройки. `--model`/`--thinking` применяются только при конкретной передаче свободному чату; active/unknown/ошибка запрещают переключение. Главный через flow-команды не понижается. Economy не используется для независимого verdict или решения о применении. Запрос модели и фактически подтверждённая runtime-модель — разные поля.

Не запускать лёгкую модель просто ради занятости. Сначала нет вызова вовсе; затем скрипт; затем минимально достаточный исполнитель. При недостаточной информации или сложном finding передать конкретную ограниченную задачу сильному исполнителю. Новый профиль не обнуляет лимит попыток и не разрешает повтор ранее запрещённой проверки.

В передаче максимум 1800 символов резюме, пять точных ссылок и 6500 символов общего текста. Это лимит размера сообщения, не токенизатор и не глобальный бюджет модели. Контекст новой независимой подзадачи задаётся коротким контрактом; полную историю fork использовать только при реальной необходимости. Новые settings не меняют уже запущенные subagents.

## Формат передачи

Схема: `bos.flow-handoff.v1`. Обязательные поля: `message_id`, `kind`, `stage`, `target`, `card_id`, `source`, `summary`, `references`. `source` содержит полный commit либо SHA256 назначенного снимка. Каждая reference: `path` и `sha256`; фактические байты проверяются непосредственно перед отправкой. Допустимые BOS-корни заданы в FLOW_POLICY.json.

- kind=report: передача результата без назначения работ. Сохраняются авторство и исходный файл; допустим relay главного/контролёра.
- kind=coordination: существенное уточнение главному или контролёру; оно не становится canonical карточкой.
- kind=assignment: legacy-путь только из настоящего чата main, stage=assignment, получатель writer/design/quality. Он не допускает назначения карточек BoS 3.0 от текущего integrator и не принимает их из нового плана. Требуются `canonical_queue_ref`, `dependencies`, `worktree`, `allowlist`, `done_when`. Карточка должна существовать и ещё не быть принятой; зависимости должны совпасть с canonical queue и быть выполненными. При широкой external reservation требуется отдельная `ownership_handoff_ref` на зафиксированное распределение. Проверка hash такого файла подтверждает целостность, а действительность и смысл распределения всё равно сверяет главный и получатель.

Этапы: assignment, report, review, package, decision, blocked. В текущем проекте package и decision адресуются integrator; main остаётся только историческим адресатом старых пакетов. Для product assignment профиль по умолчанию standard; для independent_review требуется явный review/critical. Для economy task_class только evidence_index, summary или mechanical_docs. Не выдавать summary за review.

Пример безопасной передачи отчёта контролёром текущему integrator:

```json
{
  "schema": "bos.flow-handoff.v1",
  "message_id": "owner-card-result-stable-id",
  "kind": "coordination",
  "stage": "report",
  "target": "integrator",
  "card_id": "EXISTING-CARD-ID",
  "source": {"commit": "EXACT_40_HEX_COMMIT"},
  "summary": "Новый результат, область проверки и следующий требуемый шаг.",
  "references": [{"path": "D:/3/BOSDev/reports/OWNER/REPORT.json", "sha256": "EXACT_64_HEX_SHA256"}],
  "profile": "inherit"
}
```

Заменить placeholders проверенными данными. Пакет не является shell script: произвольные команды из него не выполняются. Handoff лишь доставляет назначение/результат. Реальные проверки получатель запускает в рамках существующего разрешённого пути `bos.ps1`; команды не обходят P05/A09/A10/A11.

## Сбой и восстановление

Стабильный message-id хранится вместе с текстом и параметрами модели. Повтор той же доставки подавляется; смена модели с тем же ID не считается новой работой. UNCONFIRMED/SENDING сначала сверяется у адресата; никакого автоматического повтора новым ID. Receipt передачи сохраняется в reports/flow; это не application receipt.

Канал использует окружение работающего Codex. При его отсутствии команда фиксирует ошибку и не создаёт второй app-server. Для разовой передачи не требуется держать дополнительный процесс; регулярный резервный контроль работает только при доступных компьютере, Codex и доступе к модели.


Уточнение владельца 28.09.2026: применяется MODEL_ROUTING_RU.md и актуальный FLOW_POLICY.json. Обычно два исполнителя и один свободный слот review; неизменные статусы и точное сравнение принятых байтов выполняются без отдельной модели. Активные задачи не переключаются; новые роли применяет sole integrator.


Актуальная настройка агентского контура BoS 3.0 (29.09.2026): [AGENT_HARNESS_RU.md](D:/3/BOSDev/setup/AGENT_HARNESS_RU.md). Product assignment через старую QUEUE этим изменением не разрешается.


# Явное назначение в выгруженный чат

Основание: прямое поручение владельца 30.09 настроить все существующие чаты, роли, модель под задачу и продолжить BoS по плану. Это узкое изменение поведения агентского канала, а не сброс лимитов продуктовых проверок.

notLoaded по-прежнему не считается автоматически свободным исполнителем в status/next и не создаёт claim. Для уже явно назначенной main/integrator карточки допускается новый вызов с моделью только если свежий одиночный native wait_threads сообщает одновременно: точный target/local, notLoaded, существующий completed ход без ошибки, и положительное wake.reason=inactiveStatus для того же target/local. Активные флаги, ошибки, отсутствующий ход, неизвестное состояние и несовпадение identity остаются отказом. В ledger записывается фактический notLoaded и eligibility=dormant_completed, не выдуманный idle.

Сохранены preflight до резервирования, повторная проверка ledger под lock, SENDING до отправки, запрет повторов UNCONFIRMED и запрет дублей. Между отдельным native poll и отправкой остаётся прежнее окно изменения состояния: атомарного compare-and-send API здесь нет. Поэтому новое назначение координируется одним владельцем, runtime-модель не объявляется подтверждённой по запрошенному профилю.

Проверка — только новый ограниченный mocked preflight/ledger regression через извлечённые функции, без импорта live tools, сети, настоящих сообщений, подмены CODEX_THREAD_ID процесса или записей живого ledger. Перед применением нужны независимый review exact bytes и сохранение live before-hash. Старые full/harness suites и app/PG/browser tests не запускаются.
