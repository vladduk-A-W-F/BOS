# BoS · пакет впровадження та перша компанія

20.09.2026. Пакет BATCH-03 для інтегратора й оператора. Джерела: `docs/SERVER_INSTALL_UA.md`, `docs/BACKUP_RESTORE_UA.md`, `docs/orchestration/STATE.json` станом на читання. Це упаковка наявного кандидата й умов впровадження, а не прийнятий виробничий реліз. `TECHNICAL_READY=false`, `PILOT_ALLOWED=false`.

## Фактично наявні можливості

BoS має Django-застосунок та український інтерфейс. Початкова модель надання сервісу передбачає керовану окрему установку для кожної компанії: власні код, Python-середовище, база, приватні документи, секрет і сесійний cookie. Спільна база кількох компаній цим пакетом не передбачається.

Інсталятор створює новий каталог, перевіряє SHA коду, встановлює закріплені залежності з підготовлених локальних wheels, застосовує міграції й збирає статику. Бізнес-таблиці залишаються порожніми; демодані не переносяться автоматично. Є контрольований запуск і зупинка, перевірка TLS/health, авторизований доступ до приватних документів та ролі `ceo`, `manager`, `observer` з окремими дозволами на документи й експорт. Прийнята частина серверного стенда обмежена Linux amd64, Python 3.12 та SQLite.

Реалізовано кандидат резервного копіювання бази, документів, коду й конфігурації та чистого відновлення в новий каталог. Старі результати малих синтетичних репетицій підтверджують окремі сценарії; вони не є SLA чи прийманням усього A10.

Чинний STATE підтверджує адресну перевірку PostgreSQL 16 у CI для BATCH-01: 26 green-методів, з яких 16 виконують бізнесові HTTP-сценарії, а 10 перевіряють захист тестового підключення; додатково 7 unit-тестів. Це не повний suite, бізнесовий E2E чи прийнятий PostgreSQL-профіль установки. BATCH-02 на момент читання ще інтегрується.

## Обов’язкові умови перед робочим запуском

1. **Перший адміністратор.** Завершити й прийняти підтриманий операторський bootstrap із перевіреною приватною конфігурацією установки; підтвердити первинний вхід клієнта та призначення ролей. Звичайний `manage.py createsuperuser` без installation environment не закриває цю умову.
2. **Прийнятий серверний профіль.** Визначити цільовий хост, сховище, домен, origin і TLS та окремо підтвердити публічний доступ. Наявний стенд слухає loopback. Windows і PostgreSQL потребують окремого приймання, лише якщо їх обрано для установки.
3. **Незакриті серверні дефекти.** A09 лишається неприйнятим через ConnectionResetError замість HTTP 413 для 13 MiB. A10 не має прийнятих activation, upgrade N→N+1, rollback і відновлення після знеструмлення. Приймання чистого restore має включати фактичний післявідновлювальний HTTPS-вхід, а не лише `complete=true` для даних і коду.
4. **Повне приймання продукту.** P06 і загальний результат залишаються BLOCKED; обов’язкові всі 11 критеріїв. Адресні успіхи не підвищують readiness. P05 уже 3/3, A09 targeted retry, A10 activation/upgrade/rollback та заблоковані A11 маршрути автоматично не повторюються й не обходяться. Для цих блокерів потрібні окремо дозволені наступні рішення.
5. **Експлуатаційна відповідальність.** До передачі компанії призначити оператора, власника доступів і резервних копій; погодити приватне місце зберігання, частоту й строк зберігання копій, допустиму втрату даних і час відновлення. Фактичні цілі підтверджуються на обраному профілі, не беруться з часу малого стенда.
6. **Паспорт першої компанії.** Визначити процес, відповідального, дані та критерії приймання. Реальні клієнтські дані й платний GPT API зараз не ввімкнені. Підключення зовнішнього AI потребує окремого обсягу дозволених даних, API-проєкту й бюджету.

## Відомості для першої компанії

- Назва компанії, контакт власника процесу, технічний оператор та адміністратор доступу.
- Перший наскрізний сценарій: поставка готових виробів, робота через підрядника або власне виробництво. Один приклад від початкової потреби до прийнятого результату та критерії успіху.
- Користувачі й ролі; кому доступні фінанси, документи, завантаження оригіналів та експорт. Дані паролів і секретів у brief не вносити.
- Країна й часовий пояс роботи, робочі валюти, номенклатура та одиниці, правила версій, склади/місця, відповідальні й потрібні документи.
- Джерела перенесення: система або файли, орієнтовні обсяги, відкриті замовлення й закупівлі, залишки та історія. Для початкового узгодження достатньо опису й знеособленого прикладу; реальний імпорт не починається з цього brief.
- Бажане розміщення, домен, вимоги доступу й резервного копіювання; власник оплати інфраструктури та погоджений бюджет.
- Потрібні майбутні інтеграції та помічник: конкретна задача, джерела, допустимі дані й відповідальний за результат. Не обіцяти вже підключений банк, пошту, OCR або GPT.

Послідовність передачі: погоджений сценарій і синтетичний приклад → прийнята установка та первинний вхід → рольова перевірка й навчання → звірене перенесення після окремого допуску → контрольований пілот → приймання власником процесу. Наразі готується перший етап; наступні залежать від умов вище.

## П’ять тез для лендинга

1. **BoS — пов’язане керування операціями компанії.** Замовлення, матеріали, документи та відповідальні в одному робочому просторі.
2. **Від показника до джерела.** Перевіряйте записи, на яких ґрунтуються операційні дані, у межах свого доступу.
3. **Окреме середовище для вашої компанії.** Початкова модель впровадження передбачає власну установку, базу й приватні документи.
4. **Доступ відповідно до ролі.** Керівник, менеджер і спостерігач працюють із призначеними їм можливостями.
5. **Починаємо з вашого процесу.** Узгоджуємо перший сценарій, потрібні дані та критерії результату, потім готуємо контрольоване впровадження.

Поруч із пропозицією має бути видимий статус: **«BoS у розробці. Готуємо демонстрацію й пакет впровадження. Робочий запуск потребує технічного приймання.»** Доречна дія: **«Обговорити сценарій впровадження»**. Не використовувати «готовий production SaaS», «запуск за один клік», гарантію безперервної роботи, обіцяний SLA або активний GPT-помічник. Лендинг не змінює готовність застосунку; поточний дозвіл Sites зберігає наявну приватну аудиторію власника.
