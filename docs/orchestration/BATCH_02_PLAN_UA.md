Для N2 прийнята поведінка: чужа незалежна зміна не скасовує pending proposal, якщо його суттєві дані, показаний ефект і права незмінні. Це ще не доказ безпеки конкретного patch. Перша область — CEO erp_adjust через ERP preview; generic/старі proposals можуть зберігати глобальну перевірку. Усі input, read-membership, документи й bytes, доступ після lock та фактичний impact мають бути покриті. Невідомий або неповний контекст не дає права на запис. Міграція лише additive metadata в ActionProposal, якщо це обґрунтує inventory; реальні БД не мігруються.

Allowlist READ/UX — у прийнятих PLAN_LINKS_READ_CARD_UA та ROUTE_SCOPE. Для N2: новий вузький dependency helper/tests, operations model+одна additive migration, operations service, erp preview integration; інші дії/Policy не послаблювати. Спільний erp/views.py інтегрує root по hunks, не копіюванням старого файла поверх іншої картки.

## SaaS, лендинг, помічник, системи клієнта

1. **Працююча панель.** Пов’язані операції, джерела показників, ролі, журнал і підтвердження. Основний synthetic case: закупівля → склад → продаж → рахунок → оплата/доручення. Власне виробництво першого клієнта не підтверджене.
2. **SaaS-пакет.** Керована ізольована установка для компанії, доступи, onboarding, backup/restore proof, спостережуваність, статус інтеграцій і зрозумілі межі сервісу. Брендинг як SaaS не вимагає зараз спільної БД. Billing, тариф і реальне provision/deploy визначаються окремими картками та не обходять історичні заборони.
3. **Лендинг.** Показує реальний продукт і один перевірений сценарій; чітко відрізняє наявне від roadmap. Перехід до демонстрації/запиту контакту без вигаданого прийому заявки. Чинний Sites-проєкт повторно використовується після звірки його джерел; Django-панель не замінюється шаблоном лендингу.
4. **Помічник поверх панелі.** Спершу пояснює видимі факти з source refs; потім готує пропозицію через наявний preview/confirm. Контроль, нагадування й автоматизації потребують окремих правил подій, отримувачів та лімітів. Зовнішній API залишається off до допустимих полів/проєкту/caps.
5. **Підключення клієнта.** Конкретні ERP/CRM/документи обираються за фактичною системою клієнта. Перший контракт: читання/import з provenance, mapping, дедуплікацією, правами й ревізіями; write-back окремо після preview/confirm. Плагіни розробника в ChatGPT не є автоматично продуктовими інтеграціями клієнтів.

## Приймання пакета

Кожна кодова картка: patch → raw targeted regression → незалежний review → один atomic commit. Інтегрований кандидат звіряється source SHA; scoped PG16 — окремий новий bounded CI тільки для цього обсягу. Full suite/E2E не повторюється; P05 3/3 та A09/A10/A11 незмінні. Тести лише на нових синтетичних БД/media. TECHNICAL_READY=false, PILOT_ALLOWED=false до повного приймання. Після пакета — модульний звіт, актуальна черга та наступний виконуваний крок.
