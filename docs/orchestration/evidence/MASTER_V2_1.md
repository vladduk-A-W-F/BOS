# BoS · мастер-промпт: от текущего состояния до готового продукта

Версия 2.1 · единый промпт, заменяет предыдущие
Учтена контрольная точка 0.1 от 11.09.2026: инвентаризация принята, решения ниже вшиты, стоп-условие по объёму A05 снято.
Основание: `BoS_Plan_UA.md` (30 задач, 10.09.2026), `BoS_PROMPT_PACK.md`, `BoS_Plan_Pack_UA.zip`
Язык всех документов и артефактов — украинский. Код и комментарии — как в текущей базе.

## 0. Задача и режим

Довести BoS от локального MVP до состояния, в котором команда проверки `verify` проходит полностью, а сквозной рабочий сценарий выполняется на чистой установке.

Работаешь автономно. Сам выбираешь следующую задачу, сам доказываешь результат, сам обновляешь состояние. Не останавливайся после одной задачи, не спрашивай «продолжать ли». К человеку обращаешься только по стоп-условиям раздела 8.

План принят, аудит принят. Решения раздела 1 не переоткрываются: если считаешь какое-то ошибкой — напиши отдельным абзацем в отчёте и всё равно выполняй как описано.

## 1. Принятые решения (не обсуждаются)

1. Стек сохраняется: Django + текущий фронтенд. Никаких переписываний, смены фреймворка, микросервисов, очередей, локальной LLM.
2. Серверная версия — **отдельная установка на каждую компанию**. Shared-DB SaaS отложен.
3. Идентичность — Django `User` со связью на `Employee`, без изменения исторических ID.
4. Первыми исправляются два дефекта целостности (блок 0). Всё остальное ждёт.
5. Покупка сервера, домен, публикация, платная LLM — вне работы.
6. **Объём A05 расширен до 6–10 человеко-дней**, плюс 0,25–0,5 на передачу валюты и проверки EUR/USD/UAH в A02. Принято по итогам инвентаризации; переоткрытию не подлежит.
7. **Причины двух исходных дефектов разные** и требуют разных минимальных исправлений: в `finish` транзакция и блокировка есть, но несколько ORM-объектов держат устаревшее состояние одной партии; в зарплате проверка статуса идёт до защищённой записи. Общими остаются инварианты, а не патч.
8. **Инвентарь заморожен**: 85 путей записи и 12 дефектных мест — база этой работы. Новые найденные дефекты записываются в список `docs/WRITE_PATHS_UA.md` с оценкой; в работу берутся только те, что касаются денег или склада. Расширение объёма по остальным — отдельное решение после блока 3.

## 2. Определение «готово» — единственный критерий

Собери команду `scripts/verify.sh` (и `verify.ps1` для Windows), которая запускает всё перечисленное и возвращает 0 только если пройдено всё.

**Этот список менять нельзя.** Ослаблять, пропускать, помечать `skip`, оборачивать в `try/except`, понижать пороги — запрещено. Не проходит пункт — чинится код, а не проверка.

1. Миграции применяются на пустой базе без ошибок — на SQLite и на PostgreSQL.
2. Весь набор тестов зелёный на обеих СУБД: существующие 151 функциональная + 5 launcher + все добавленные.
3. Инвариантные проверки на случайных последовательностях операций, не менее 1 000 прогонов каждая:
   - сумма движений по номенклатуре и партии = остаток, всегда;
   - остаток никогда не отрицателен;
   - на одну выплату — ровно одна расходная транзакция;
   - повтор операции с тем же идентификатором предложения не меняет состояние;
   - ни один пользователь не получает данные, недоступные его роли.
4. Права: автоматический обход **всех** фактических маршрутов API и admin прямыми запросами от каждой роли. Запрещённое поле не появляется ни в ответе, ни в snapshot, поиске, экспорте, истории, кеше и контексте ассистента.
5. Параллельность: для каждой денежной и складской операции — два одновременных вызова. Ровно один результат; второй получает согласованный отказ или тот же ответ; дублей движений нет.
6. **Сквозной сценарий** `scripts/e2e_scenario.py` проходит на чистой базе и сходится с эталоном `tests/e2e_expected.json` до копейки:
   требование → предложение поставщика → согласование → заказ → частичная приёмка → возврат части → складское движение → счёт → импорт банковской выписки → сверка оплаты → поручение с результатом → отчёт руководителя.
7. Бэкап разворачивается в **чистую** установку: количества, суммы, версии документов и SHA файлов сходятся.
8. Пакет развёртывания ставится на чистой машине одной командой и стартует с боевым профилем: без demo-secret, без AllowAny, без демороли; TLS, cookies, proxy, health check, логи работают.
9. Обновление живой установки: база с данными версии N мигрирует до N+1, проверка после миграции проходит, откат к N восстанавливает исходное состояние.
10. Интерфейс: 390 / 768 / 1440 px, zoom 200%, клавиатура и Escape, длинные названия, двойное нажатие, медленная сеть.
11. Чистая установка Windows с Python 3.12 проходит пункты 1–3 и 6.

Пока `verify` не вернул 0 — продукт не готов, сколько бы задач ни было помечено выполненными.

### 2.1 Среда запуска — CI подключён, собираешь сам

Репозиторий GitLab доступен. Отсутствие PostgreSQL, Windows или браузера в твоей локальной среде не является причиной пропустить пункт и не является поводом остановиться — всё это поднимается в CI.

1. **PostgreSQL** — сервис-контейнер `postgres:16` в `.gitlab-ci.yml`, плюс `docker-compose.yml` для локального запуска. Изолированный профиль из A06.
2. **Браузер** — Playwright с headless Chromium, ставится в job.
3. **Windows** — job с тегом Windows-раннера, Python 3.12. Если Windows-раннер в проекте не зарегистрирован: напиши готовую инструкцию регистрации self-hosted раннера на машине владельца (три команды, копируются из настроек проекта), job оставь в конвейере с `when: manual`, пункт пометь `НЕ ЗАПУЩЕНО (нет раннера)`. Не удаляй job и не понижай требование.
4. **Если проект на самом деле на GitHub, а не GitLab** — то же самое через `.github/workflows/verify.yml` с матрицей `ubuntu-latest` + `windows-latest`. Определи по наличию `.git/config` и сделай под фактическую платформу, не спрашивая.

Пункты, которые не удалось запустить, помечаются `НЕ ЗАПУЩЕНО (причина)` в `docs/PROGRESS_UA.md` с указанием, что именно нужно предоставить. Зелёными они не считаются; `verify` не может вернуть 0, пока они не пройдены на реальной среде. Работу по остальным задачам это не останавливает.

**Реальные данные в CI не попадают никогда.** В конвейере только синтетические фикстуры. Сверка накопленных данных (0.5) запускается локально, на копии `db.sqlite3`.

## 3. Состояние работы

Веди `docs/PROGRESS_UA.md` и обновляй **после каждого шага**, не в конце. Таблица по всем 30 задачам плана:

`ID · статус (не начата / в работе / готова / заблокирована) · дата · доказательство (файл в evidence/) · что осталось`

Плюс разделы: текущая задача · очередь · заблокированные с причиной · принятые решения · известные проблемы с числом попыток.

Это единственный источник правды о прогрессе. Новая сессия начинает с чтения этого файла и продолжает с текущей задачи, не переделывая готовое. Файла нет — создай до первой строчки кода.

## 4. Протокол одного шага

Повторяй, пока очередь не пуста:

1. Прочитай `docs/PROGRESS_UA.md`, возьми первую незаблокированную задачу.
2. Напиши проверку, которая **падает сейчас** и описывает требуемое поведение. Сохрани вывод.
3. Сделай минимальное изменение, делающее проверку зелёной.
4. Запусти `verify`. Сломалось что-то ещё — чини. Дальше с красным не идёшь.
5. Положи доказательства в `evidence/<ID>/`: команды, вывод до, вывод после, окружение, дата, SHA использованных копий базы.
6. Обнови `docs/PROGRESS_UA.md`.
7. Следующая задача. Без паузы и без вопроса.

Один коммит на задачу. Задачи в одном изменении не смешиваются.

## 5. Очередь задач

### Блок 0 · целостность данных — делается первым

**0.0 Сборка и конвейер — первая задача, до любого исправления.**

Пока нет команды, которая одним запуском отвечает «зелено или нет», все последующие исправления недоказуемы. Поэтому сначала конвейер, потом код.

Собери и запусти:

- `scripts/verify.sh` и `scripts/verify.ps1` — каркас со всеми одиннадцатью пунктами раздела 2. Пункты, для которых проверок ещё нет, возвращают явный `НЕ РЕАЛИЗОВАНО` и красный статус. Заглушек, возвращающих успех, быть не должно.
- `docker-compose.yml` с `postgres:16` для локального запуска.
- `.gitlab-ci.yml`: job `tests-sqlite`, job `tests-postgres` с сервис-контейнером, job `e2e`, job `ui-playwright`, job `tests-windows` (при отсутствии раннера — `when: manual` плюс инструкция регистрации), job `verify-full` на релизной ветке.
- Существующие 151 + 5 проверок подключены к конвейеру как есть.

**Приёмка 0.0:** конвейер запущен в GitLab, ссылка на прогон и его вывод — в `evidence/0.0/`. Красный результат на этом шаге нормален и ожидаем: он показывает исходное состояние. Ненормально — зелёный при нереализованных пунктах.

Дальше очередь блока 0.

Оба найденных дефекта — один класс: **чтение состояния и последующая запись без общей транзакции и блокировки**. Чинишь класс, а не два экземпляра.

**0.1 Инвентаризация.** `docs/WRITE_PATHS_UA.md` — все места, где читается состояние склада, партий, остатков, денег, зарплаты, оплат и затем пишется движение. По каждой строке: модуль и функция · что читает · что пишет · внутри ли `transaction.atomic` · есть ли блокировка · идёт ли через proposal/confirm · есть ли идемпотентность · вердикт. Найденное сверх 0.2 и 0.3 не чини — зафиксируй с оценкой в человеко-днях, это реальный объём A05.

**0.2 A01 · списание при повторных резервах одной партии.** Тест, падающий на текущем коде: два резерва по 5 из партии 10 → `finish` на 10. Исправление: одно актуальное состояние партии или согласованное агрегирование вместо нескольких устаревших ORM-объектов; блокировка берётся до fingerprint и снимка «Было»; повтор того же `proposal_id` не создаёт второго выпуска; согласованный частичный выпуск разрешён в пределах остатка. Запрет повторного резерва исправлением не считается. Приёмка: остаток и сумма движений = 0; повторные резервы, частичный выпуск и разные партии проходят.

**0.3 A02 · двойной учёт выплаты зарплаты.** Тест: два одновременных подтверждения одной зарплаты 100 → две транзакции. Исправление: проверка «уже оплачено» внутри той же защищённой транзакции, что и создание ровно одной записи; повторный вызов возвращает согласованный прежний ответ; ошибка после записи откатывается полностью; связь с источником выплаты обязательна. Скрытие кнопки исправлением не считается.

**0.4 Инвариантные тесты** — пункт 3 раздела 2. Два точечных теста ловят два известных случая, инвариант ловит класс.

**0.5 Сверка накопленных данных.** Запускается на копии реальной `db.sqlite3` с зафиксированным SHA, а не на синтетике. Собери `docs/DATA_RECONCILIATION_UA.md`: расхождения остатков и движений, возможные дубли выплат, несвязанные транзакции. Ничего не переписывать и не удалять; совпадение суммы и даты дублем не доказывает. Каждая строка — факты и предложение; решение принимает человек.

**0.7 Остальные десять мест из инвентаря.** Подтверждённые сценарии: статус «выплачено» без расхода; изменение суммы после выплаты; правка связанного расхода без согласования с зарплатой; удаление зарплаты, расхода или работника с потерей источника; зарплата в EUR с расходом в UAH; те же дыры через формы и массовые действия админки. Каждое — падающий тест до исправления. Исправления идут через общие команды с сохранением истории; удаление заменяется архивированием с сохранением источника; валюта передаётся явно и проверяется на EUR/USD/UAH. Скрытие кнопок исправлением не считается. Это и есть содержание A05 — выполняется после 0.2 и 0.3, до блока 1.

**0.6 PostgreSQL сразу.** Расхождение «31 символ проходит на SQLite при поле в 30» — признак, а не единичный случай. Подними изолированный профиль PostgreSQL и прогони на нём весь набор. Дальше набор гоняется на обеих СУБД по умолчанию.

## 6. Инварианты качества

- Функциональность не отключается ради прохождения проверки. Скрытая кнопка, закомментированный маршрут, заглушка вместо реализации — это красный, а не зелёный.
- Тесты не удаляются и не ослабляются. Мешает тест — либо он описывает верное поведение и чинится код, либо он неверен, и его изменение объясняется отдельным абзацем в `evidence/`.
- Не мокается то, что должно работать в продукте. Мок допустим только для внешних платных сервисов и реальных банковских действий.
- Исторические данные не переписываются и не удаляются никогда.
- Каждое видимое пользователю изменение — в `CHANGELOG_UA.md`. Версия штампуется внутри установки и видна в интерфейсе.
- Не рефакторишь то, что не входит в задачу; не переименовываешь; не трогаешь зелёные тесты ради вида.

## 7. Когда не получается

- Три полные попытки на одну проблему. Не вышло — запиши в «известные проблемы»: что пробовал, что увидел, гипотеза. Бери следующую задачу. Один цикл не крутится.
- Нет клиентских данных — не жди. Сделай эталонный набор в `fixtures/synthetic/`, явно помеченный как временный, работай на нём, задачу отметь заблокированной.
- Нужен выбор между разменами — выбери вариант, который меньше ломает принятые решения, запиши в `docs/DECISIONS_UA.md` с обоснованием и **условием пересмотра**, продолжай.

Отдельно оформи два решения как ADR, каждое с условием пересмотра: **ADR-01** сохранение стека; **ADR-02** отдельная установка на компанию — при каком числе клиентов или какой доле времени на обслуживание возвращаемся к вопросу общей базы.

## 8. Стоп-условия — только здесь спрашивай человека

1. Расхождение в рабочих данных, затрагивающее деньги.
2. Исправление требует переписать или удалить исторические записи.
3. Нужна покупка, оплата, публикация, доступ к боевым системам или персональным данным реальных людей.
4. Найденный дефект означает, что принятое архитектурное решение неверно.
5. `verify` невозможно пройти без изменения самого списка раздела 2.
6. Найден дефект **вне замороженного инвентаря**, который делает уже исправленное неверным. Число дефектов само по себе больше не является стоп-условием: инвентарь принят, объём A05 согласован.

Во всех остальных случаях решай сам и записывай.

## 10. Финал

Когда `verify` возвращает 0 на обеих СУБД и на чистых Linux и Windows, собери `docs/RELEASE_UA.md`:

1. Версия, дата, SHA сборки, состав.
2. Полный вывод `verify` с окружением.
3. Что продукт делает — по сквозному сценарию, шагами.
4. **Что продукт не делает** — явным списком: полная бухгалтерия, налоги, банковские переводы, гарантия сроков поставщика, всё из блока 4.
5. Границы проверенного: число пользователей, объём данных, версии ОС и Python. Непроверенное названо непроверенным.
