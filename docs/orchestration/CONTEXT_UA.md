## Вектор власника
«Система нового порядку»: усі процеси пов’язані через інформацію, рух і показники; управління та комунікація зрозумілі й прозорі; ШІ прискорює та оптимізує бізнес-операційні процеси. GPT/Codex потрібні і для розробки, і як помічник усередині BoS. Промислові поставки — корисний початковий наскрізний сценарій, але не остаточна межа продукту. Наявність власного виробництва у першого пілота ще не підтверджено.

## Принцип користувацької цінності
З кожного показника користувач переходить до джерельних операцій, їх документів, причин відхилення, відповідального й допустимої наступної дії. Одна зміна показує вплив на пов’язані строки, залишки, зобов’язання і задачі. Комунікація прив’язана до справи/операції, а рішення залишає автора, час, причину та результат.

Приклад цільової поведінки, ще не завершена функція: постачальник затримує партію → ризик строку замовлення → видно відповідального, документ і запас → GPT пояснює варіанти та готує доручення → людина бачить наслідки і погоджує → система виконує дію й показує новий стан. Не кожне попередження повинно бути LLM-висновком: факти, суми й формальні правила обчислює застосунок.

## Наявна технічна основа
Python 3.12; requirements декларують Django 6.0.5, DRF 3.17.1. Модулі tasks, finance, employees, branches, ai_assistant, operations, erp. Цільова серверна перевірка PostgreSQL 16, SQLite для локального синтетичного профілю. Збережені frontend та окрема установка на компанію.

У наявному коді є закупівлі, приймання/повернення, склад, продажі, рахунки, CSV-виписки, погоджені оплати та доручення. Це наявність реалізації, не твердження про повне приймання. Зміни ERP централізуються у service/dispatch; operations керує preview/confirm та аудитом. Assistant зараз має історичну Anthropic-залежність; GPT у продукті ще не інтегровано цією підготовкою.

## Цільова модель зв’язків
| Елемент | Що має бути відомо | Перевірюваний результат |
|---|---|---|
| Бізнес-об’єкт | ID, тип, статус, версія, відповідальний, залежності | Шлях від замовлення до пов’язаних документів і руху |
| Подія | Дія, автор, час, підстава, об’єкт, зміна | Відтворювана історія без прихованих змін |
| Рух | Матеріал/кількість/одиниця або сума/валюта, джерело й призначення | Залишки й суми сходяться з операціями |
| Документ | Джерело, редакція, доступ, зв’язок з операцією | Використовується правильна версія |
| Показник | Формула, джерела, період, свіжість, права | Число пояснюється до вихідних записів |
| Комунікація | Об’єкт, учасники, питання, рішення, задача | Рішення має контекст та відповідального |
| GPT-пропозиція | Доступні факти, джерела, невідоме, наслідки | Відсутній непідтверджений автозапис |

Це логічна модель поверх наявної схеми, не рішення встановити graph database, event bus чи новий framework. Спочатку gap-map фактичних моделей; міграції — окремі картки.

## Два контури ШІ
1. Розробка: головний оркестратор, діагност, виконавець, QA/CI, reviewer, evidence, архітектор, UX, readiness і pilot. Робота з дозволеним кодом та синтетикою; GitHub — джерело версій.
2. Продукт: серверний OpenAI adapter → факти в межах ролі → відповідь з джерелами → структурована пропозиція → чинний preview/confirm → аудит. Спочатку читання/пояснення, потім підготовка дій. Жодного довільного SQL, секретів у frontend чи виконання інструкцій з вкладених документів. Модель, бюджет, перелік полів та доступ до API визначаються перед інтеграцією; відсутній ключ не обходиться.

## Критерій успіху
Власник і співробітник можуть завершити наскрізну справу, пояснити кожне суттєве число, знайти вузьке місце і відповідального та виконати погоджену дію. Фактичний час роботи, частка завершених сценаріїв, число помилок/повторних вводів і точність звірки вимірюються на пілоті; вигаданих цільових ROI тут немає.
