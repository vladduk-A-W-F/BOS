# PLAN-UX · джерела виконання замовлення

20.09.2026. C3, `PREPARED_SPEC_ONLY`. Це brief для review, не реалізований або прийнятий UX. Код, Figma, runtime й тести не змінювалися. Основа: чинний `frontend/boss_app_source.html` (`BoSHome`, `ERPWorkspace`, `BoSInspector`, `ERPTable`, `DocViewer`, `NextAction`) і виправлені PLAN-LINKS/PLAN-GPT.

## Завдання

Людина відкриває замовлення, бачить, що залишилось виконати, перевіряє джерела кількості, знаходить відповідального та переходить до чинної дозволеної дії. Перший зріз доповнює наявний inspector секцією «Джерела виконання»; новий workspace чи окремий навігаційний розділ не потрібний.

Для загального сценарію вимога → закупівля → склад → продаж можна підготувати UX на синтетиці зараз. Компанію й власника пілота для цього не вигадуємо й не очікуємо. Власне виробництво першого пілота не підтверджено; роботи/виробництво показуються лише за фактичними пов’язаними записами, не як обов’язковий крок усіх замовлень.

## Наявне і запропоноване

| Частина | Уже є в коді | Пропонується C3 |
|---|---|---|
| Вхід | «Сьогодні», «Показники», ERP → «Продажі»; order відкривається у `BoSInspector` | Ті самі входи; без нового dashboard |
| Order inspector | Клієнт, owner, строк, позиції, резерви, роботи, рахунки, відвантаження; фінансові поля за правами | Одна компактна секція джерел після «Позиції й виконання»; зв’язок кожної величини з дозволеним source ref |
| Фактичні відвантаження | `source_movements` уже включає доступні receipt/shipment без межі300 | Зберегти охоплення. Нову секцію не продавати як виправлення нібито зниклих shipments |
| Джерела | Картки партії, закупівлі, рахунку; `DocViewer` з версією/статусом | Явні типи зв’язку та походження, обсяг і свіжість нового trace |
| Дії | `NextAction`, форми, preview/impact/confirm, receipt | Нова секція лише читає; наступна дія лишається у чинному контурі |
| Помічник | Локальні сценарії; external adapter off | Пояснення trace — наступна C4 інтеграція, не активна GPT-кнопка першого зрізу |

## Рольові входи й інформація

| Роль | Чинний вхід | Що дає нова секція | Дії й обмеження |
|---|---|---|---|
| CEO | «Показники» → показник → замовлення; або «Сьогодні» / ERP → «Продажі» | Quantity/source trail, резерви, shipment refs, роботи, доручення; перехід до дозволеної фінансової картки | Чинні CEO-форми. Фінансові підсумки не дублювати у першому trace |
| Manager | «Показники» відкриває «Операційний огляд»; «Сьогодні»; ERP → «Продажі» | Доступні операційні факти й відповідальні; реквізити рахунку через дозволений InvoiceLink | Чинні дозволені операційні дії. Жодної собівартості/банківського оригіналу через source details |
| Observer | Ті самі доступні огляд/продажі для читання | Лише role-scoped факти; пояснення restricted/partial без прихованих реквізитів | Немає write/confirm controls. Наявність лінка не надає права на документ або фінанси |

Права визначаються серверним `Policy`, а не тим, що JSX приховав кнопку. При зміні ролі чи object ID стару відповідь прибрати, незавершений запит ігнорувати/скасувати. Повторне відкриття джерела має нову серверну перевірку доступу.

## Секція «Джерела виконання» — запропонована будова

1. Короткий підпис: бізнес-дата зрізу й час перевірки. Не називати generated_at атомарним snapshot або гарантією актуальності після нової операції.
2. За кожною позицією: код/версія/одиниця; «Замовлено», «Відвантажено», «Скасовано», «Залишилось виконати», «Придатний резерв». Показувати серверні Decimal-рядки; не рахувати суми чи відсотки через JS float. Не складати шт. і кг.
3. Біля величини — кнопка «Показати джерела»: дозволені reservation/shipment/cancellation refs, партія й кількість. Нуль має джерело й complete; null/restricted нулем не стає.
4. Короткі списки «Пов’язані роботи», «Доручення», «Рахунки»: code/title, строк, стан, фактичний відповідальний. Owner order, owner job і assignee task підписати своїми ролями; не призначати закупівлі вигаданого owner.
5. Для партії — зв’язок «Походження партії»: receipt → purchase лише за доведеним прямим джерелом. Це не твердження, що вся PO виділена цьому замовленню. Непризначені закупівлі не включати в «Пов’язано» за самим збігом item/revision.

Текст за відсутнього призначення очікуваних PO: «Призначення очікуваних закупівель цьому замовленню не зафіксовано». Не показувати гарантовану дату поставки із симуляції. Для перегляду повного бізнес-плану лишається чинний ERP «Огляд виконання» з його simulation/basis.

## Переходи до джерел

| Джерело | Перехід і повернення |
|---|---|
| Партія, робота, PO, invoice, shipment/correction | Відомий `kind/id` відкриває відповідну чинну картку; label походить тільки з дозволеного DTO |
| Документ | `DocViewer`: точний code/revision/status; download лише за окремим дозволом. Немає автоматичного відкриття «найновішого» замість процитованого джерела |
| Доручення | Чинний inspector зараз веде до HR → «Доручення». Передати task ID для виділення/відкриття конкретної задачі — запропоноване доповнення, не вже наявний deep link; якщо воно поза allowlist, чесна кнопка «Відкрити доручення» веде до чинного списку з видимим task code/ID для пошуку |
| Назад до замовлення | Запропонована локальна історія selection з кнопкою «До замовлення …»; повертає контекст позиції й фокус. Не створює другого незалежного набору даних |

Не малювати ребро процесу, якщо його немає в джерелах. Наявна JSON-схема, FK або source movement — підстава; схожа назва, примітка, збіг клієнта чи item — ні. Якщо потрібного detail нема у свіжому контексті, показати стан недоступності/потреби оновлення, а не підставляти інший запис.

## Стани нової секції

| Стан | Текст / поведінка |
|---|---|
| Loading | «Перевіряємо джерела замовлення…», role=status; старі величини іншого order прибрані, подвійний GET не створює дій |
| Complete, немає записів | «Пов’язаних доручень серед доступних записів немає» або конкретний тип. Не оголошувати відсутність у всій компанії |
| Restricted | «Повне пояснення цього показника недоступне для поточного доступу»; значення «—». Не показувати назви/типи/counts прихованих джерел |
| Partial | «Показано частину дозволених джерел». За лімітом100 refs не називати список повним; не малювати кнопку «Ще», доки її API не реалізовано |
| 409 read_state_changed | Прибрати неприйняті факти: «Дані змінилися під час перевірки. Оновіть джерела». Одна явна кнопка «Оновити»; без automatic retry/polling |
| 401 / 403 / 404 | Закрити або очистити недоступний контекст; нейтральне «Запис недоступний для поточного доступу». Жодного збереженого CEO payload за повідомленням про помилку |
| Network / server error | «Не вдалося перевірити джерела», role=alert, ручний повтор. Немає фальшивого 0/порожнього complete |
| Зміна ролі / order під час запиту | Пізня відповідь попереднього context не відображається; повернення до неї через локальний back-stack теж не обходить перевірку |

Стан, що впливає на число, стоїть поруч із числом. Колір підтримує текст/іконку, не є єдиною ознакою. «Частина джерел» і «Немає записів» не взаємозамінні.

## Критерії майбутньої UX-перевірки

- 390/768/1440 px та zoom200%: без обрізаних кількостей, валют, кодів, повідомлень чи кнопки закриття. На вузькому екрані факти/джерела переходять у вертикальний порядок; горизонтальний scroll дозволений усередині таблиці, не всієї сторінки.
- Клавіатура: кожна джерельна дія доступна Tab/Enter/Space; видимий focus; діалог має зрозумілий heading, фокус усередині та Escape. Після закриття джерела фокус повертається до кнопки, що його відкрила; після закриття order — до початкового рядка.
- Довгі українські назви й коди переносяться без втрати ID/значення. Кнопки не залежать від hover; достатня площа торкання, щонайменше44×44 CSS px для основних дій нового блоку.
- Loading/status та error оголошуються допоміжним технологіям без перенесення фокусу при кожному GET. Рядок таблиці має явну кнопку, а не тільки click handler на всьому рядку.
- Синтетично перевірити дві однакові номенклатури у різних orders, прихований reservation, старі uncapped shipment refs, partial>100, revoked access, повільну мережу, швидке перемикання order і double click. Відкриття джерела не викликає preview/confirm.
- Наявні форми погодження й receipts зберігають чинний шлях; зміна дизайну не знижує перевірки ролі, строку, fingerprint або повтору. Цей brief не є доказом, що поточний UI уже виконує всі ці критерії.

## Межа першої реалізації

Залежність — прийнятий PLAN-LINKS-READ DTO та additive route coverage з `PLAN_LINKS_ROUTE_SCOPE_UA.md`. Основний UI-файл — `frontend/boss_app_source.html`; похідні assets/template тільки штатною дозволеною збіркою в майбутній картці. Нова local selection history і точний task handoff мають бути явно включені в її allowlist або лишитися наступним малим UX-кроком.

Готовий brief дозволяє створити конкретні екрани/state variants і сценарій review без вибраного пілота. Він не активує external GPT, не підтверджує виробництво, не змінює master/readiness і не закриває UI gate. Figma-прототип, реалізація та фактична перевірка залишаються наступними окремо облікованими результатами.
