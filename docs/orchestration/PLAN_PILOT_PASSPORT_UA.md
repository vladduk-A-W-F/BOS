# PLAN-PILOT · паспорт першого пілота

20.09.2026. Чернетка C6 для review; `PLANNING_ONLY / NOT_AUTHORIZED_TO_START`. Компанія, люди й реальні дані ще не визначені. Підготовка паспорта дозволена; запуск пілота, production activation/upgrade/rollback цим документом не дозволяються. `TECHNICAL_READY=false`, `PILOT_ALLOWED=false` залишаються чинними.

## Паспорт із незаповненими реальними реквізитами

| Поле | Поточне значення / що має бути зафіксовано |
|---|---|
| Компанія / окрема установка | Не визначено; не підставляти вигадану компанію чи shared-DB tenant |
| Власник процесу | Не визначено; конкретна людина з правом прийняти результат |
| Операційний відповідальний | Не визначено; людина, що проводить сценарій і фіксує винятки |
| Відповідальний за приймання | Не визначено; особа, що звіряє первинні джерела, звіт та підписує результат |
| Гілка процесу | Відкрите рішення: закупівля готових виробів / підрядне виготовлення / власне виробництво |
| Кандидат BoS / source SHA | Заповнюється фактичним SHA прийнятого кандидата перед стартом; поточна статична специфікація не є runtime-кандидатом |
| Середовище / engine / версія | Окремий дозволений стенд; фактичний engine/version і докази готовності. SQLite не замінює PostgreSQL16 у відповідному критерії |
| Дані / правова й організаційна підстава доступу | Дозволений перелік наборів, людина, що його погодила, дата, межа доступу; реальні записи не завантажувати до цього погодження |
| Вікно пілота / число кейсів | Не погоджено; визначити після вибору процесу та доступності кандидата. Немає календарної обіцянки |
| GPT усередині продукту | За замовчуванням off. Пілот чинного процесу може обійтися локальними сценаріями; зовнішній GPT оцінюється окремо після своїх умов |
| Дозвіл на старт | Не надано; потрібне окреме рішення власника після технічних/людських умов |

## Запропонований перший процес

Практичний кандидат — **вимога й документ → пропозиція постачальника → погоджена закупівля → часткове приймання/повернення → якість і склад → резерв → продаж/відвантаження → рахунок → CSV-виписка й звірка → доручення з результатом → звіт керівника**. Він спирається на наявні Django-моделі й command шляхи, але потребує фактичного приймання кандидата.

Синтетичний еталон для підготовки міститься в `PLAN_LINKS_SCENARIO_METRICS_UA.md`: 10 шт., часткове приймання 6, повернення 1, доприймання 4, окрема заміна 1, продаж на 1 500,00 EUR та оплата. Це fixture, не історія клієнта й не baseline бізнесу.

Якщо перший пілот закуповує готовий виріб, пряма PO→SalesLine allocation поки відсутня: це явна межа плану, не готове виділення закупівлі. Походження прийнятої партії можна простежити через рухи, резерв та відвантаження. Якщо потрібні підрядне чи власне виготовлення, окремо звірити фактичні BOM/routing/location/owner і потрібні функції; не додавати цю гілку мовчки до першого пілота.

Кожен кейс має заздалегідь визначений кінцевий стан. Приклад: goods shipped/invoiced і payment reconciled, або документовано погоджений виняток із незавершеним зобов’язанням. Статус «виняток погоджено» не прирівнюється до повністю виконаного замовлення.

## Межі й ролі

Керівник бачить фінансові підсумки та виконує CEO-only операції; менеджер працює з доступними операційними джерелами; спостерігач читає дозволене. Власник процесу, виконавець і автор погодження — різні реквізити навіть якщо одна реальна людина виконує кілька ролей. Призначена роль Django визначає права; назва посади їх не надає.

Усі зміни ERP/доручень — чинний preview/confirm/service шлях. Реєстрація оплати не є банківським переказом; чернетка запиту не є відправленим повідомленням. Зовнішні листи/повідомлення та автоматичні платежі не входять у цей пілотний процес без окремої дозволеної функції.

Початковий обсяг даних: лише погоджені специфікації/пропозиції/сертифікати, номенклатура, order/PO/lot refs, синтетичні або дозволені документи виписки й мінімальні службові реквізити людей. Паролі, ключі, зарплати й кадрові приватні поля не потрібні для цього сценарію. Конкретні дозволені реальні поля залишаються рішенням власника; автоматичної передачі GPT немає.

## Як зібрати baseline

До пілотного порівняння зафіксувати поточний спосіб виконання тієї самої справи: її обсяг, ролі, складність, винятки й визначення «готово». Виконаний наперед навчальний приклад не є історичним baseline компанії. Якщо зіставного baseline немає, у звіті буде лише фактичний результат пілота без відсотка економії.

Рекомендований журнал одного case-run — таблиця/CSV за схемою нижче; це запропонована схема evidence, зараз файл із реальними даними не створено.

| Група | Обов’язкові поля evidence |
|---|---|
| Ідентичність | `pilot_id`, `case_id`, `run_id`, `phase` baseline/pilot, `process_variant`, `scenario_version`, `fixture_or_allowed_dataset_id`, `dataset_sha256`, `candidate_source_sha` для BoS |
| Порівнянність | `matched_case_id`, число order lines/PO/receipts/returns/invoices/allocations, одиниці/валюти, roles, `complexity_notes`, `training_status`; відмінності описати |
| Хто й коли | псевдонімний `actor_ref` і роль, `reviewer_ref`, `start_at_utc`, `end_at_utc`, часовий пояс business dates; не вигадувати користувача з автора документа |
| Час роботи | `activity_segment_id`, `activity_kind`, `segment_start_utc`, `segment_end_utc`, `pause_reason`, `wait_kind`, `observation_source`; перерви й очікування не ховати |
| Результат | `expected_outcome`, `actual_outcome`, `outcome` completed/partial/blocked/failed, `blocker_id`, `exception_decision_ref`, `acceptance_time_utc` |
| Звірка | тип/ID джерела, source document ID/revision/checksum, expected/actual quantity або amount як decimal string, unit/currency, tolerance, `reconciliation_status`, reviewer, checked_at |
| Дії та повтори | proposal/receipt/audit/event refs, підтверджений результат, `retry_kind` transport/user_correction, `duplicate_effect_count`, `manual_reentry_count`, `error_id` |
| Пошук джерела | запит/показник, початок пошуку, час відкриття правильного джерела, source_ref, чи знайдено відповідального, результат перевірки джерела |
| GPT — лише якщо дозволений | enabled, model/schema/prompt version, request_id, fact/source refs, outcome, latency, actual tokens/monetary usage, budget status; не записувати вигадані значення за disabled |

Первинні докази: доступні реєстри рухів/рахунків/виписки, proposal receipts і audit із джерельними документами; для часу — спостереження/журнал сегментів. Час між `created_at` двох бізнес-записів не дорівнює активному часу праці, тому не використовувати його як приховану заміну baseline.

## Метрики й точні правила

| Метрика | Формула та джерело | Межа тлумачення |
|---|---|---|
| Завершення сценаріїв | completed / усі started case-runs; окремо counts partial/blocked/failed | Не вилучати blocked із знаменника задля кращого відсотка; покажіть причини |
| Активний час на кейс | Сума тривалостей відмічених робочих сегментів цього кейса | Для одночасних учасників це person-minutes. Один сегмент не зараховувати двом кейсам повністю; правило розподілу записати |
| Календарний цикл | end_at−start_at; для незавершеного — censored на зафіксований час звіту | Не називати очікування активною працею; медіана завершених показується разом із числом незавершених |
| Час пошуку джерела | correct_source_opened_at−search_started_at | Лише якщо reviewer підтвердив правильність джерела; незнайдене — окремий outcome, не 0 секунд |
| Повторний ручний ввід | Кількість повторних наборів уже наявного факту за заздалегідь узгодженим правилом | Нові факти й свідоме виправлення іншої величини не вважати копіюванням; rule_version у evidence |
| Помилки та переробка | Підтверджені error_id за класом; час correction segments | Відрізняти бізнес-помилку, проблему UI, прав, мережі, fixture та блокер готовності |
| Звірка кількостей | Для кожної lot/unit: сума рухів=залишок; для sales line: quantity−shipped−cancelled=open | Decimal; очікувана розбіжність 0 у затвердженій точності; повернення окремо, не мовчазне зменшення gross історії |
| Звірка грошей | Для invoice/currency: amount−active credits=net; receivable=max(net−paid,0); звірка statement allocations із фактами | Decimal до копійки для підтриманих валют; різні валюти окремо. Ручна оплата без виписки не видається за bank-confirmed |
| Дубльований ефект | Кількість зайвих movements/payments/tasks після повтору того самого дозволеного intent/confirm | Очікування 0; transport retry і реальна нова операція мають різні класи |
| Простежуваність | Число обов’язкових показників із перевіреним source path / число обов’язкових показників кейса | Джерело, роль, дата, відповідальний і допустима дія перевіряються окремими полями; hidden/null не видається за повне пояснення |
| Якість explanation-only GPT | Число прийнятих відповідей / число оцінених; окремо groundedness, numeric fidelity, access, unsupported_action counts | Лише для реально ввімкненої погодженої версії. За off — not_evaluated, не 0% і не PASS |

Порівняння baseline/pilot робити по зіставних case IDs і наводити сирі значення, кількість випадків, медіану та діапазон. Для пари delta=pilot−baseline; відсоток=(baseline−pilot)/baseline×100 лише якщо baseline>0 і порівнянність підтверджена. Для малого або неоднорідного набору не заявляти причинний ефект. ROI не розраховується без погоджених і виміряних витрат, періоду та правил оцінки часу.

## Приймання та умови зупинки

Початок пілота потребує фактичного технічного кандидата й дозволу власника, визначених людей, набору даних, scope та протоколу. Документи C2/C4 не підміняють 11 GATES; історичні обмеження P05 3/3, A09/A10/A11 не знімаються планом пілота. Недоступний обов’язковий proof лишається BLOCKED.

Для кожного кейса: очікуваний результат узгоджений до старту; звірки кількостей/грошей сходяться; джерела та версії доступні правильній ролі; підтверджені дії мають receipts/audit; результат доручення записаний явно. Нуль непогоджених записів, нуль витоків за рольові межі й нуль дубльованих грошових/складських ефектів — умови, а не статистичні побажання.

За розбіжності руху/оплати, порушення доступу, втрати джерела або непогодженого запису зупинити відповідний кейс, зберегти доказ і створити blocker. Не виправляти реальні записи shell/SQL або зміною еталона заради PASS. Інші незалежні підготовчі роботи можуть тривати; постраждалий кейс не закривається як completed.

Людське приймання: власник процесу й reviewer звіряють фактичний outcome, відхилення та unresolved obligations; рішення accept/accept_with_open_items/reject має автора, дату й підставу. `accept_with_open_items` не закриває невиконаний технічний gate чи порушення доступу/обліку. Продуктова економія оцінюється за evidence, не за враженням від демонстрації.

## Три рішення, які потрібні пізніше

1. **Перший процес і його люди:** обрати готові вироби / підряд / власне виробництво та назвати власника процесу й особу приймання. Це визначить межу пілота й необхідні джерела.
2. **Дані:** погодити конкретний набір для пілота; окремо — які поля/уривки можуть виходити до GPT, термін зберігання й використання історії. До цього можна завершувати синтетичні сценарії та локальні проєкції.
3. **Зовнішній GPT:** якщо він потрібний у цій хвилі, визначити API-проєкт/відповідального й жорсткі per-request/day/month caps; або залишити зовнішній adapter off і провести перший пілот чинного процесу після його дозволу. Доступ до моделі й ключа перевіряється штатним налаштуванням, не припускається.

Ці рішення не потрібні для завершення нинішніх планових документів. Календар і вимірні цілі продуктивності встановлюються після baseline та підтвердження готовності; вигаданих target ROI або строків тут немає.
