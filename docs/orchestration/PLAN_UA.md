## Історична послідовність BATCH-01

Нижче — погоджений початковий порядок, не нові доручення на повтор. P10-003, N1 REQUEST/SHIP, F03, F06 і SOURCE прийняті в адресному scope; N2 probe завершений, ADR запропонований; TIME причини ще OPEN.
1. **P10-003 / P06-F02:** перевірка ізоляції InitialImportFixture з урахуванням СУБД. Не перейменовувати у N1. Лише тестова проблема; джерельна БД лишається захищеною.
2. **PLAN-N1:** перевірити довжини вводу відносно max_length усіх фактичних шляхів, потім окрема мінімальна продуктова правка без розширення колонок за замовчуванням.
3. **PLAN-F03:** відокремити валідні invoice-коди у concurrency fixtures від спеціальних негативних тестів довжини. Не обрізати коди мовчки.
4. **PLAN-F06:** збереження e2e-report.json, completeness check і SHA-індексу. Підготовка CI не запускає його.
5. **PLAN-TIME:** встановити причину F04/F05 після перевірки впливу попередніх правок. Не збільшувати timeout без доказу.
6. **PLAN-N2:** замір глобального fingerprint і конфліктів двох користувачів; запропонувати варіант адресної перевірки/версій. Рішення щодо механізму після даних; обмеження одним користувачем не приймається мовчки.
7. **PLAN-SOURCE:** міжплатформне сортування source SHA (P04-F01), окрема картка.
8. Повтор P06 та подальші приймальні suites — лише після врегулювання конкретного ліміту й дозволеного середовища. Поточний план не скидає P05 3/3.
`PLAN-*` — нові планові ключі; історичні P10-ID для них ще не призначені. Остаточні номера видає оркестратор після перевірки реєстру.

C2/C3/C6 мають незалежні підготовчі частини й виконуються паралельно за чинним дорученням. Канонічні зміни інтегруються послідовно після review. C4 потребує правил доступу, погоджених полів та API caps; C5 — кінцевого кандидата після C2–C4. Нові регресії блокують наступну залежну кодову картку.

## Як працює контроль
На кожній картці: ID/залежності → факти і гіпотеза → allowlist → очікувана перевірка → patch → незалежний review → evidence → звіт. Картка й setup можуть бути завершені при червоному продукті. Успішний scoped-тест не закриває full gate. Пауза вже знята останнім дорученням власника. Воно не скидає історичні ліміти конкретних дій.
