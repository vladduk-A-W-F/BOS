# ADR-N2 · адресні ревізії погодження з глобальною перевіркою за замовчуванням

20.09.2026. **DIRECTION_ACCEPTED_FOR_IMPLEMENTATION — механізм ще не активований.** Власник після пропозиції доручив додати реалізацію в план і продовжувати. Інваріанти та поступова область erp_adjust збережені; конкретний patch потребує inventory, regression і незалежного review. Початковий текст нижче описує предмет ADR, не доказ готовності.

## Підстава й рекомендація

Прийнята адресна діагностика N2 підтвердила: два користувачі готують ERP proposals для різних lot; B підтверджує зміну з HTTP 200; A отримує 409, хоча його граф Item/Location/Lot/Movement не змінився. На цьому малому SQLite fixture десять fingerprint-викликів виконали по 24 SELECT, wall-медіана 8.343 ms. Це доказ зайвої інвалідації в конкретному сценарії; не доказ причини F04/F05, продуктивності PostgreSQL або поведінки великої БД. [1]

**Рекомендація:** проєктувати адресний набір ревізій залежностей для кожної дії окремо. Чинний глобальний fingerprint зберегти як початковий режим і fallback для дій без доведеного покриття. Спершу описати контракт однієї дії `erp_adjust`, яку використано в N2; не вмикати загальне адресне погодження всіх ERP-команд. Не зменшувати блокування в цій зміні й не вводити обмеження одним користувачем.

## Варіанти

| Критерій | Чинний глобальний fingerprint | Адресні ревізії + глобальний fallback |
|---|---|---|
| Що порівнюється | Усі рядки 19 ERP/correction моделей і 5 додаткових наборів | Версії сутностей, наборів і контексту, від яких залежить конкретне рішення; непокриті дії використовують чинний hash |
| Незалежна зміна | У N2 зміна B відхилила pending A | Ціль: зберегти A, якщо всі суттєві залежності й права A незмінні; ще не реалізовано |
| Ризик коректності | Зайві конфлікти; повноту чинного hash для всіх дій цей замір не доводить | Пропущений read або writer може дозволити застарілу дію; потрібний явний реєстр залежностей і всіх шляхів їх зміни |
| Вартість | Є лише наведені 10 вимірів малого SQLite fixture | Читання токенів, підтримка ревізій, додаткові записи й fallback; підсумкова ціна невідома |
| Запровадження | Наявна поведінка | Окрема кодова картка, сумісність старих proposals, адресні докази; швидкодія не є обіцяним результатом ADR |

## Пропонований контракт

Proposal має серверно визначений режим, версію контракту залежностей, незмінний payload, actor/session, строк дії та токени стану **до** preview-симуляції. Для адресного режиму це read-revisions об'єктів і наборів, конфігурація, потрібні документні checksum/revisions і access-revision. Чинний глобальний token також знімається з того самого початкового стану для сумісного fallback. Вибір режиму не надається клієнту. [2–4]

Для `erp_adjust` недостатньо тільки `Lot.id/version`: `move()` перевіряє фізичну кількість і суму резервів; preview показує impact, обчислений через snapshots. Потрібно спочатку описати всі суттєві reads валідації, розрахунку й показаного користувачу ефекту. Набір резервів потребує власної ревізії/еквівалентного захисту, щоб новий рядок не залишив старий token чинним. Це початкова карта, не вже повний dependency manifest. Відокремлення довідкових екранних даних від даних, за якими користувач погоджує ефект, має бути явним контрактом. [2–3]

Ревізії змінюються атомарно з відповідними бізнес-записами. Потрібне покриття створення/редагування/видалення, membership та агрегатів, включно з import, admin, bulk/update і суміжними service-шляхами. Непокритий writer означає, що адресний режим для залежної дії ще не готовий. Токен має розрізняти видалення/повторне створення, а не спиратися лише на ID чи час зміни.

Fallback без послаблення: невідома дія, неповний контракт, невідома версія або відсутні tokens → звірка з первісним глобальним token за сумісною схемою; якщо такої звірки немає — новий preview, жодного запису. Поточний глобальний hash не можна видати за початковий token уже створеного proposal. Старі proposals не переводяться мовчки в адресний режим.

## Незмінні вимоги

1. **Policy та доступ.** На preview і confirm перевіряються актуальні actor, session, роль, дозволи й доступ до джерел; після очікування lock вони перевіряються знову. Access-revision охоплює контекст прав, а read-revisions — стан джерел; одне не замінює інше. Зміни дозволів чи видимості документів не обходять перевірку. Наявний `Policy.access_revision()` — джерело для проєктування, не доказ повноти майбутнього контракту. [4–5]
2. **Preview → confirm.** Preview виконує симуляцію dispatch із rollback. Confirm перевіряє строк, payload і tokens до збереження бізнес-ефекту. Будь-яка суттєва зміна залежностей потребує нового preview; показаний ефект не можна мовчки перерахувати й застосувати.
3. **Locks та атомарність.** Зберегти чинний `erp_write` mutex, спеціальні reference locks, порядок перевірок після захоплення lock і compare-and-set receipt. Бізнес-запис, нові ревізії, audit та receipt комітяться або відкочуються разом. Адресні tokens не є заміною locks. [2,4]
4. **Idempotency.** Повтор завершеного proposal не створює другого ефекту. Зберегти current-Policy проєкцію receipt й спеціальні правила перевірки джерельних bytes/операцій; не підмінити чинні replay-гілки загальним порівнянням усіх нових ревізій. [4]
5. **Dependency coverage.** Включати рішення на відсутності рядка, унікальності, membership, сумах і доступності ресурсів, а не лише перелік існуючих PK. Усі шляхи зміни цих залежностей мають оновлювати tokens у тій самій транзакції. До доказу покриття діє global fallback.
6. **Перевірюваність.** Proposal/evidence фіксують режим і версію контракту та причину stale. Свіжі права й read revisions мають бути доведені на фактичному backend. Доказ для двох незалежних дій не заміняє конфлікт на спільному ресурсі, повтор receipt, зміну прав або вставку нової залежності.

## Що ще невідомо й наступний крок

Немає повного dependency/writer inventory, обраного зберігання ревізій, плану сумісної міграції, PostgreSQL-доказу, масштабу вартості та частки конфліктів. Невідомий вплив на snapshot/impact і спеціальні task/import/statement/correction контракти. Спостереження N2 не встановило причину 600 s; P05 3/3 та відкриті F04/F05 незмінні.

Наступна картка — статичний read/write inventory `erp_adjust`, контракт tokens/fallback і незалежний review; після нього окремо визначити мінімальні кодові зміни й адресні перевірки. Цей документ не дозволяє новий full/PG suite/gate3/E2E або автоматичний retry.

**Прийнятий напрям за новим дорученням власника:** чи залишати pending proposal чинним після незалежної зміни, коли його суттєві джерела, показаний ефект і права не змінилися. Рекомендація — так, лише для дій із доведеним покриттям і без втрати stale protection. Підготовка цього ADR та наступного inventory не потребує зупинки для нового дозволу. Схема таблиць ревізій і деталі tokens — технічний review, не окреме питання користувачу.
