# PLAN-LINKS · фактичні зв’язки та прогалини

20.09.2026. Статична специфікація C2; продуктові зміни не виконані. Джерело — дозволений код у `BOS`, а не дані компанії. Наявність коду не означає приймання функції. Нове доручення власника дозволяє пакетну підготовку; історичні паузи в документах не відновлюються.

## Висновок

BoS уже має значну частину наскрізного шляху: замовлення → позиція → резерв партії → відвантаження → рахунок → облік оплати; виробнича робота зв’язується з позицією, закупівля — з виробничою роботою та документованою вимогою/пропозицією. Доручення вже мають `sales_order` і відповідального працівника. Наступний малий крок — серверна картка джерел одного замовлення: показати доведені зв’язки та походження чисел із чинними правами.

Прямого призначення закупівлі готової продукції позиції продажу зараз немає. Збіг номенклатури й версії — кандидат забезпечення, а не доказ, що поставка належить цьому замовленню. Загальна історія комунікації з учасниками, рішеннями й документами також не реалізована як єдина справа.

## Фактична модель

| Ланка | Реалізація в коді | Що ще не можна стверджувати |
|---|---|---|
| Клієнт → замовлення | `SalesOrder.customer`, `owner`, `due_date`, `status`; `SalesLine.order/item/revision/quantity/price` | Немає універсального об’єкта справи чи версії кожного бізнес-об’єкта; `revision` — версія виробу, а не optimistic lock |
| Документована потреба → пропозиція → закупівля | `ProcurementRequest.document/owner`; `SupplierQuote.request/document/supplier`; `Purchase.request/quote/approval_snapshot`; `erp.procurement.purchase_source()` | Засвідчення менеджера `supplier_confirmation` не є незалежно отриманим підтвердженням постачальника; закупівля не містить прямого `SalesLine` FK |
| Закупівля → приймання → партія | `Movement.purchase/lot`, `kind='receipt'`; `Purchase.received`; `Lot.quantity/documents/quality` | Власний відповідальний у `Purchase` відсутній; його не можна підставляти з користувача, що переглядає картку |
| Партія → якість | `Inspection.lot/inspector/result/note/created_at`; `Lot.documents` з ID документів; `usable()` та `accepted_documents()` | Документні ID в JSON не дають загального реєстру всіх зв’язків чи документного маршруту погодження |
| Запас → потреба | `Reservation.lot` і рівно одна ціль `line` або `production`; `free()` | Вільний запас ще не виділено замовленню. `free()` не приймає Policy й враховує всі резерви партії; він не є безпечною рольовою проєкцією. За прихованих складників новий показник має бути null/restricted |
| Позиція → робота → матеріал/результат | `Production.line/item/bom/routing/location/owner`; `Movement.production`; `OperatorEntry` | Немає доведеного календаря потужностей, змін чи обладнання. Наявність `make/subcontract` не підтверджує власне виробництво першого пілота |
| Партія → відвантаження → замовлення | `Movement.line`, від’ємна quantity для `shipment`; `SalesLine.shipped`; перед відвантаженням потрібен резерв | `Movement.reference` — текстове посилання, не гарантований FK на документ; не всі рухи мають окреме поле автора |
| Відвантаження → рахунок | `InvoiceLink.invoice/order/lines`; `SalesLine.invoiced`; рахунок створюється за невиставленим відвантаженням | `InvoiceLink.lines` — збережений JSON-сnapshot, не нормалізована таблиця рядків рахунку |
| Рахунок → оплата → виписка | `Invoice.paid`; `erp.payments.post_payment()`; `StatementAllocation.invoice/payment_event/line`; `StatementLine.transaction/first_import`; `StatementImport.document/source_sha256` | Ручний `erp_payment` — локальний запис, не банківський переказ і не автоматично банківське підтвердження; зв’язок із випискою є лише коли справді створено рознесення |
| Скасування / повернення / кредит | `OrderCancellation`, `CancellationRelease`, `GoodsReturn.source/result`, `SupplierClaim`, `InvoiceAdjustment`, `InvoiceAdjustmentLine`; `erp.balances` | Фізичне повернення не зменшує історичне приймання/відвантаження, не відкриває автоматично замінне замовлення, не списує борг без окремого коригування |
| Замовлення → доручення → результат | `Task.sales_order`, `assignee_employee`, `deadline`, `result`; `tasks.commands`; `AuditEvent` schema `bos.task-change.v1`; `tasks.history` | Не можна оголошувати доручення відсутніми у продукті. Прив’язка до procurement request частково зберігається в audit/source_refs; загального FK на довільну операцію немає |
| Дія → погодження → доказ | `ActionProposal` з user/session/role/fingerprint/expiry/receipt; `operations.service.execute()`; `erp.Event` та `operations.AuditEvent` | Загального `event.object_id/actor_id` поля немає: посилання й автор ERP часто в JSON payload/result. Історичні записи можуть не мати такого автора; його не можна відновлювати здогадкою |
| Комунікація | `SalesOrder.notes`, причини операцій, результат доручення, чернетка `orders/<pk>/draft/`, особиста `ChatMessage` історія | Немає єдиної розмови справи: учасники, рішення, підтвердження доставки, відповіді постачальника та зв’язок повідомлення з order/event/document не задані моделлю. Чернетка не надіслана |

## Вже наявний користувацький шлях

`frontend/boss_app_source.html` містить `BoSHome`, `BoSInspector`, `NextAction`, `ERPActionDialog` та `BoSActionDialog`. Керівник може відкрити фінансовий показник і вихідний запис. Картка замовлення вже показує позиції, фінансовий результат у межах прав, рахунки, фактичні відвантаження, роботи та резерви. Картки партії/закупівлі/рахунку мають власні джерела й операції. Пропозиція наступного кроку йде через `/api/erp/orders/<pk>/next/`; виконання — через чинний preview/confirm.

Це основа для доповнення наявної картки, а не підстава створити ще один workspace. `erp.queries.snapshot()` обмежує загальні `movements` останніми 300, а `events` останніми 150, але окремий `erp.corrections.snapshot_rows()` уже повертає `source_movements`: усі доступні receipt/shipment та результати відповідних повернень без такого ліміту. `BoSInspector` замовлення використовує `source_movements` для фактичних відвантажень. Отже, межі 300/150 **не доводять втрату відвантажень у чинній картці**. Загальні movements/events не можна називати повним універсальним журналом, проте наступний endpoint обґрунтований ясним order-scoped контрактом джерел, ролей і походження показника, а не непідтвердженим дефектом відвантажень.

## Правила зв’язків для наступних карток

1. **Прямий зв’язок:** FK або перевірений явний ID у відомій схемі snapshot. Повертається разом з типом джерела й ID. Невідомий JSON не обходиться рекурсивно як універсальний граф.
2. **Походження партії:** приймання тієї самої партії дозволяє простежити закупівлю після резервування/відвантаження. Воно не доводить, що вся закупівля призначалася одному замовленню. Для переміщень без прямого source FK не будувати довільне дерево лише за текстовим `reference`.
3. **Кандидат забезпечення:** однакові `item_id/revision`, строки та відкритий залишок. Відображати окремо від призначеного забезпечення; не додавати до резерву. Навіть один кандидат не перетворюється на підтверджений причинний зв’язок.
4. **Право на джерело:** застосувати `Policy` до початкового замовлення і кожного включеного об’єкта, після цього — явний allowlist полів. Фінансові суми/тексти історії не потрапляють спостерігачу через labels, причини, приховані JSON, count або помилки.
5. **Повнота:** `complete`, `restricted`, `partial` або `unavailable` — різні стани. `0` допустимий лише коли джерела прочитані й повні. Ознака неповноти не повинна видавати кількість, тип чи назву недоступних об’єктів.
6. **Відповідальний:** `SalesOrder.owner`, `Production.owner`, `ProcurementRequest.owner`, `Task.assignee_employee` — різні ролі. Автор дії з audit — ще одна роль. Відсутній власник закупівлі показується як відсутній; власник замовлення не стає ним автоматично.
7. **Час та узгодженість:** `as_of` — бізнес-дата з `operations.service.as_of()`, `generated_at` — час підготовки відповіді, не доказ стабільного багатозапитного зрізу. `created_at` — час запису. Новий endpoint перевіряє внутрішній read_revision і заново обчислений access_revision до/після читання; конфлікт повертає 409 без business payload, автоматичних повторів немає. Точний алгоритм і обмеження описані в картці.
8. **Вартість прав:** `Policy.erp_ids()` зараз виконує глобальні обходи Item/Lot/SalesOrder/Production/Purchase тощо. Scoped endpoint обмежує власні бізнес-запити, але не робить чинний Policy локальним чи O(розмір замовлення). Цю вартість і повторну перевірку прав треба виміряти адресно; оптимізація Policy — окрема картка без ослаблення доступу.

## Прогалини з чергою, без розширення найближчої картки

| Пропонований ключ | Прогалина | Мінімальний результат / залежність |
|---|---|---|
| PLAN-LINKS-READ | Потрібний явний order-scoped контракт походження показників; поточні source_movements вже охоплюють відвантаження | Дозволена read-only проєкція кількості, резервів, робіт, доручень, рахунків і зв’язків; специфікація в сусідньому файлі |
| PLAN-LINKS-ALLOC | Закупівля готового виробу не виділяється позиції продажу | Після вибору пілотного процесу — окрема модель/міграція виділення кількості та один command шлях з preview/confirm; підтримати часткове виділення, скасування й одночасне погодження. Не додавати сьогодні |
| PLAN-LINKS-HISTORY | ERP audit розподілений між JSON, рухами, proposals і task audit | Окрема картка типізованої індексації/проєкції історії з пагінацією; legacy позначається явно; не переписувати історію |
| PLAN-LINKS-OWNER | Немає явного власника закупівлі та універсальної відповідальності за відхилення | Погодити матрицю ролей у пілоті; не підмінювати її схемою доступів |
| PLAN-LINKS-COMMS | Немає розмови справи і структурованого рішення з учасниками | Спершу рішення/доручення з посиланням на order/event/document; зовнішнє надсилання — окрема дозволена функція |
| PLAN-LINKS-DATES | Розрахункова дата не враховує потужність і спільну конкуренцію за майбутні надходження | У UI залишити маркер симуляції та basis; не називати прогноз обіцяною датою |
| PLAN-GPT-READ | GPT у продукті не інтегровано | Окремий серверний adapter після правил даних/бюджету; спочатку читання джерельного пакета, жодних записів |

Це пропоновані ключі, а не присвоєні історичні P-ID. Оркестратор звіряє реєстр перед виконанням. Інвентар 85/12, 11 GATES, master та C1-блокери не редагуються цим документом.

## Два контури ШІ

**Розробка:** оркестратор, виконавець і незалежний reviewer працюють з дозволеним кодом та синтетикою; не використовують продуктову історію чату як повноваження чи джерело клієнтських даних.

**Продукт зараз:** `/api/operations/chat/` виконує локальні сценарії; `erp.assistant.answer()` пояснює план/запас і спрямовує до форм. У `ai_assistant/views.py` є історичний Anthropic adapter, tool loop та usage log. Але `operations/middleware.py` блокує POST `/api/chat/`, `/api/chat/file/`, `/api/meeting/protocol/`, `/api/dictate/process/` з 503; `Policy.capabilities()` повертає `external_llm=False`. Старий loop не можна просто ввімкнути ключем як реалізацію GPT.

**Продукт далі:** сервер обчислює числа й дозволені source refs; GPT пояснює відомі факти, позначає відсутні дані та цитує джерела. Спочатку потрібні погоджені поля, модель, ліміти витрат/запитів і retention. Подальша структурована пропозиція проходить чинний preview/confirm; підтвердження не успадковується із тексту розмови. Текст вкладення — дані, не інструкція для інструментів. Невідомий ID не допускається.

## Рішення власника та незалежна робота

| Питання | Коли потрібне | Що можна завершити до відповіді |
|---|---|---|
| Пілот: закупівля готових виробів, підрядне чи власне виробництво? | До виділення закупівель, виробничих норм, відповідальності й сценарію пілота | PLAN-LINKS-READ на синтетичному замовленні; варіанти процесу залишаються явними |
| Які поля/документи можуть передаватися зовнішньому GPT? | До зовнішнього запиту, навіть read-only | Локальну схему facts/source refs, рольові тести та правила redaction |
| Яка модель/API-проєкт, бюджет і жорстка межа витрат? | До інтеграції зовнішнього виклику | Контракт adapter, локальні детерміновані відповіді; ключ у чаті не запитується |
| Хто власник процесу й хто приймає результат? | До пілота | Сценарії приймання та незаповнений паспорт пілота |

Жодне з цих питань не блокує завершення цієї статичної специфікації. `TECHNICAL_READY=false`, `PILOT_ALLOWED=false` залишаються без змін; вигаданих ROI немає.
