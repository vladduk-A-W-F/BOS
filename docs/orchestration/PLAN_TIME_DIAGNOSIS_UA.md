# PLAN-TIME · діагноз за збереженими доказами

20.09.2026. Виконавець: `bos_e2e_evidence`, окреме доручення root. Статус підготовки: **DONE_READ_ONLY**. F04/F05: **OPEN_CAUSE_UNPROVEN**. Нових виконань застосунку, тестів, PostgreSQL, CI, E2E або build немає. Змінені лише три документи у `execution/time/`; канонічне дерево не редагувалося. Незалежний review цього висновку ще не виконано.

## Висновок

F04 і F05 доводять два окремі перевищення 600 секунд дочірніми процесами. Вони не доводять конкретний deadlock, повільний тест, деградацію fingerprint або порушений інваріант. Виправлення F02/F03 не є доведеним лікуванням часу: вони дозволяють виконатися раніше зупиненим fixture/setup і можуть збільшити обсяг роботи Django suite. До `check_invariants.py` ці fixture взагалі не входять.

Дві гіпотези з GPT-пакета потребують звуження. По-перше, блокування від `check_operations.py` не переноситься безпосередньо до наступних процесів через ту саму БД: verifier видає їм різні disposable БД. По-друге, накопичення Movement між усіма 1000 ітераціями gate3 не відповідає прочитаному коду: складський і replay цикли відкочують кожну ітерацію. Глобальне читання fingerprint справді є потенційно дорогим, але саме квадратичне зростання цього gate3 не доведено.

Прочитані локальні звіти F02/F03 є адресними SQLite перевірками; вони не містять нового повного PostgreSQL профілю. Їхні PASS не переносяться на F04/F05. Чотири setupFAIL і 15 fixture errors у gate5 мають конкретні test IDs; часткові F/E у Django stdout/stderr не дозволяють механічно приписати їм усі ті самі IDs. Gate5 історично **завершився** за 213.847 s, з failures=4/errors=15; це окремий процес після timeout gate3. [E05, E10, E12–E17, E27–E28]

P05 історично мав 578 завершених SQLite тестів за 545.635 s у другому CI; перший CI перевищив 600 s. Причина варіації не встановлена. Саме близькість одного SQLite результату до 600 s не дає ані PG прогнозу, ані дозволу підняти ліміт. P05 timeout cycle лишається **3/3**. [E07, E26]

## 3. N2: статична карта дорогих ділянок, без замірів

| Ділянка | Фактичний шлях у поточному коді | Гіпотеза / межа |
|---|---|---|
| `erp.service.fingerprint()` | 13 базових + 6 correction моделей; додатково invoices, docs, procurement_requests, supplier_quotes, dataset. Загалом 24 materialized querysets; більшість читає всі рядки/поля | Вартість залежить від суми прочитаних рядків/байтів. 24 — статичний підрахунок querysets, не замір SQL/часу |
| ERP preview | `erp.views.preview`: mutex → fingerprint → snapshot до → dispatch у rollback → snapshot після → proposal з готовим token | Fingerprint, подвійний snapshot, симуляція записів та mutex усі є кандидатами у витрати; їхніх часток немає |
| ERP confirm | `operations.service.execute`: mutex → актуальний fingerprint → snapshots до/після dispatch | Глобальна серіалізація й читання можуть впливати на latency. Звичайний replay готової receipt повертається до перевірки fingerprint |
| Інваріанти | Stock: fingerprint перед кожним із 8–16 кроків і повторно після відхилення; replay: preview/confirm + кілька прямих fingerprint та Event.count на ітерацію | Багато повторних читань навіть на маленькій БД; немає доказу домінування цього часу |
| `queries.snapshot()` | Читає набори моделей, перераховує рядки, залишки, резерви, документи, плани й суми | Можливі витрати SQL/проєкцій поза fingerprint; зосередження лише на SHA може пропустити основний час |
| Import / statements | Import fingerprint додає контрагентів, працівників, identities/batches; statement fingerprint додає сім моделей, actor/access/payload і перевірку bytes документа | Також глобальні читання; не змішувати їхню ціну з простим ERP preview |

Джерела: [E17–E23]. Зокрема, stock і replay роблять `transaction.set_rollback(True)` у кожній ітерації [E12]. Кількість Movement не зростає наскрізно від першої до тисячної ітерації через їхні бізнес-записи. Тому твердження GPT-пакета «у цьому 5×1000 циклі зростання квадратичне» **не підтверджене**; зростаючі sequence ID не дорівнюють зростанню числа рядків. Для виробничої БД, яка накопичує рухи, залежність ціни від розміру таблиць лишається реальною гіпотезою до заміру. GPT-пакет сам вказує, що N1/N2 взято зі старої локальної збірки; актуальний висновок спирається на прочитані файли й їхні SHA. [E24–E25]

Двокористувацький конфлікт має конкретний статичний сценарій: дві дозволені CEO-сесії мають pending ERP proposals для різних lot; обидва preview знято до змін. B підтверджує зміну lot B; hash усіх Lot змінюється; A підтверджує незмінений lot A і потрапляє до stale conflict. Це висновок із коду, **не виміряна частка 409 і не виконаний HTTP-тест**. Формулювання «будь-яка зміна будь-де скасовує всі погодження» надто широке: готові receipts мають replay, task-команди мають окремий fingerprint, statement no-change і correction replay мають власні гілки; сам `erp_write` mutex не входить до hash dataset. Рішення про залежності рядків або версії потребує окремого ADR; обмеження одним користувачем не прийняте.

## 4. Мінімальний NEXT: підготувати один адресний діагностичний probe

Наступний дозволений крок підготовки — окремо оформити й незалежно перевірити діагностичний harness для **однієї** replay-послідовності на новій синтетичній PostgreSQL 16 БД. Це ще не запущений експеримент і не спосіб обійти P05. Перед фактичним запуском root має зіставити конкретну картку, ліміт і наявний дозвіл; поточний документ не дає дозволу на четвертий full або повтор `postgres`/`e2e` suite.

Межі конкретної пропозиції:

1. Зафіксувати точний source SHA, PostgreSQL version, disposable DB/media provenance; мінімальні синтетичні Employee/Location/Item, як у gate3. Справжні preview → confirm → interleaved adjust → replay; зберегти незмінними assertions обраної послідовності. Сам `check_invariants.py`, п'ять інваріантів, minimum 1000 і 600 s не редагувати; не викликати gate3 із `--runs <1000`.
2. Окремий процес із загальною межею **60 s**, включно з bootstrap; рівно одна вимірювана replay-послідовність, жодного автоматичного повтору. Якщо bootstrap вичерпує час, зберегти саме цей факт і зупинити експеримент. Це діагностика функцій, не gate3 acceptance й не вибіркова підміна потрібних 1000 прогонів.
3. Записати monotonic початок/кінець bootstrap, role-client setup, preview, confirm, interleaved dispatch, replay; для fingerprint і snapshot — число викликів, wall time, query count та накопичений SQL час через observation wrapper без зміни рішень. На cutoff потрібен stack dump до завершення процесу; якщо видно очікування SQL, зберегти обмежений знімок `pg_stat_activity`/`pg_locks` лише цього disposable DB. Не додавати `lock_timeout` як приховану зміну поведінки.
4. Вихід: повний raw log, exit/timed_out receipt, фазові metrics, source/file SHA; результат назвати `SCOPED_DIAGNOSTIC`, а не PASS F04/F05. Одна replay-послідовність не локалізує будь-який test ID повного Django suite й не доводить масштабування 1000/10000/100000.
5. Рішення після даних: якщо fingerprint домінує — окрема N2-картка для bounded масштабу та двох сесій; якщо snapshot/роль/SQL wait — адресно досліджувати показаний виклик. Якщо probe не відтворив затримку — лишити причину OPEN, не запускати повний набір «для впевненості». Для F04 наступний конкретний test ID обирати лише з завершеної адресної діагностики або нового законно отриманого per-test trace.
