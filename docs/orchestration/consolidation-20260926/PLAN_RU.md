# BoS: план консолидации и следующего поколения

Дата: 26.09.2026. Карточка этой подготовки: CONSOLIDATION-PLAN-01.
Статус: PLAN_FOR_OWNER_REVIEW. Этот пакет публикует план и реестр исходников поверх последней проверяемой версии v17. Реализация следующего поколения и полная приёмка остаются последующими этапами.

## 1. Предлагаемый результат

Собрать один прослеживаемый кандидат BoS: существующий Django и frontend, украинский интерфейс, отдельная установка для каждой компании, связанные процессы от заявки до результата и расчёта. Для каждого включённого изменения должны быть исходный commit/patch, независимый review, проверка на итоговом кандидате и известные ограничения.

На GitHub должны находиться код кандидата, история коммитов, инструкция запуска, матрица модулей и приёмки, доказательства и релизный манифест. Обозначение «последняя версия» относится к конкретному SHA. Обозначение «готова к эксплуатации» допустимо только после технической и человеческой приёмки.

Рабочее название следующего этапа: **BoS Next**. Номер релиза назначается после формирования и проверки кандидата; v17 остаётся точкой восстановления и сравнения.

## 3. Как учитывать все коммиты

1. Сохранить исходные ветки и полный Git-граф; [INVENTORY.json](INVENTORY.json) является фиксированным снимком remote refs до публикации этого пакета. Новые коммиты самой подготовки видны в PR.
2. Базой исполнения назначить c4a68d4. Для каждого другого источника записать `source SHA -> module -> disposition -> target SHA -> evidence`. Disposition: уже включён, переносится после review, заменён более новым поведением, исторический документ, отложен с причиной.
3. Общая база c4a68d4 и abb8845: `edd5227e666442d8324044559b6e8cf10eaf8be1`; 39 уникальных коммитов у v17 и 15 у сетевой ветки. Это расходящиеся линии, а не последовательные версии для простого fast-forward.
4. `26f67e3` уже содержит композицию сетевого runtime. `erp/module_registry.py`, `erp/module_views.py`, `erp/test_module_registry.py` и ряд связанных файлов совпадают с PR #2; `erp/experience.py` и `erp/test_network_currency.py` содержат исправление f00a2fa. Оставшиеся отличия проверять по функциям и файлам, а не по отсутствию исходного SHA среди предков.
5. Отдельно перенести после review недостающие документы/evidence CORE-MODULE-REGISTRY, CORE-WORKSPACE-VIEWS и NETWORK acceptance с исходной идентичностью. Старый PG/browser PASS не становится приёмкой v17 или BoS Next. Импорт CI из PR #2 требует проверки условий запуска и лимитов.
6. В Git-графе main имеет два уникальных SHA: `57f651f` и `ecb8cf7`. При этом `verify.yml` из исторического `57f651f` уже присутствует в c4a68d4 с тем же содержимым. Уникальное содержательное дополнение main, `ecb8cf7`, добавляет `.github/workflows/blank.yml`, общий push/PR workflow. Его включение является отдельным решением по CI: объединение не должно неявно запустить исчерпанные suites или дублировать проверки.
7. `dc839dd`, `ce7f829` из tracking и `24cd91f`, `6148d0b`, `a1564c1` из daily-review учитывать как историю документации. У 6148d0b есть merge-parent: решение о переносе принимать с учётом его родителей, не слепым cherry-pick merge-коммита. Daily-review также меняет STATE.json: его датированные наблюдения нужно согласовать с актуальным состоянием отдельно, не заменять ими всю каноническую STATE/QUEUE.

Приоритет следующего поколения: завершить уже начатый рабочий цикл и доказать его на одном источнике. GPT и новые подключения не заменяют эту приёмку.

Параллелить можно инвентаризацию/evidence, независимую диагностику и подготовку контрактов. Общие `frontend/boss_app_source.html`, `frontend/boss_app_html.html`, `assets/app.js`, `erp/urls.py`, миграции и канонические STATE/QUEUE редактируются и интегрируются последовательно. Собранные frontend-файлы должны происходить из принятого source тем же штатным сборщиком.

## 6. GitHub и результат ревью

Текущий пакет: ветка `codex/bos-consolidation-20260926` от c4a68d4, отдельный PR в `setup/bos-gpt-orchestration-20260920`. Ветка уже наследует полный исходный код v17 и его историю. Изменения этой карточки ограничены `docs/orchestration/consolidation-20260926/`.

Реестр сохраняет все наблюдавшиеся remote-коммиты, в том числе ещё не интегрированные. Публикация реестра не утверждает включение каждого изменения в runtime. Слияние продуктовых веток, изменение main, перенос private union и новый production release не являются результатом этой плановой карточки.

При исполнении плана каждый модуль проходит независимый review перед интеграцией. Release packager готовит неизменный архив; root проверяет manifest и verdict. Итоговый release dossier включает Git SHA, runtime SHA, migration graph, frontend hashes, зависимости, инструкции, таблицу `исходник -> решение -> итог`, ограничения, 11 gates и условия пилота.

Критерий завершения консолидации: у всех источников есть принятое решение и сохранённая история; всё включённое проходит допустимую проверку на едином кандидате; непринимаемые компоненты явно исключены. Критерий готовности продукта: все обязательные технические и человеческие условия действительно выполнены.
