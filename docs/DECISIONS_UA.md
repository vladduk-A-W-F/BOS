# BoS · прийняті рішення

Джерело: `BoS_MASTER_PROMPT (1).md` v2.1. Дата: 11.09.2026. Ця нумерація ADR застосовується до реалізації за master v2.0; попередні планові пропозиції не є новими дозволами.

## ADR-01 · зберегти поточний стек

Статус: прийнято користувачем. Django й поточний frontend зберігаються; історичні ID не змінюються. Django User пов’язується з Employee. Виявлені проблеми цілісності виправляються в поточному застосунку.

Підстава: користувач прийняв цей спосіб реалізації. Відтворені дефекти пов’язані з правилами запису й актуальністю стану; інвентаризація не доводить непридатність Django.

Умова перегляду: відтворюваний доказ, що обов’язковий критерій приймання неможливо виконати в поточному стеку без його заміни. Це запускає стоп-умову 8.4 і рішення користувача, а не автоматичне переписування.

## ADR-02 · окрема установка на компанію

Статус: прийнято користувачем. Одна компанія має окрему інсталяцію та базу. Shared-DB SaaS, мікросервіси, черги й локальна LLM не входять у реалізацію.

Підстава: прийнятий формат постачання. Автоматизовані установка, оновлення, backup, restore і rollback входять до A09/A10.

Умова перегляду: досягнення 10 активних клієнтських інсталяцій або витрати на їх технічне обслуговування понад 20% робочого часу команди протягом двох послідовних місяців. Це запропонований поріг обговорення, а не прогноз кількості клієнтів чи дозвіл на спільну базу. Спочатку порівнюються фактичні витрати й можливості автоматизації окремих установок; зміну архітектури погоджує користувач.

## DR-03 · прийнятий обсяг інвентаризації

Статус: прийнято master v2.1. 85 шляхів / 12 канонічних місць заморожено. A05 6–10 людино-днів та A02 +0,25–0,5 погоджено; попередню зупинку знято. Порядок A01 → A02 зберігається.

Історію не переписувати. Проведені фінансові факти мають зберігатися, а коригування — створювати нові пов’язані записи. Це обмеження майбутньої реалізації, не твердження про її поточну готовність.


## DR-04 · недоступні середовища не приховуються

Статус: застосовано за пунктом 2.1 master v2.1. Репозиторій BoS не має remote; доступний FOS належить іншому проєкту. Підготовлено GitLab CI за вказаною користувачем платформою. Зовнішній запуск 0.0, PostgreSQL та Windows лишаються НЕ ЗАПУЩЕНО. Локальні A01/A02 продовжуються після справжнього червоного запуску каркаса; це не приймання 0.0 або релізу. Умова перегляду: поява адреси/доступу до репозиторію BoS чи відповідного runtime; тоді запускаються обов’язкові jobs без зміни критеріїв.


## DR-05 · залежність інваріанта доступу

Статус: відома залежність, без зміни 11 критеріїв. Крок 0.4 містить рольовий інваріант, який потребує A03/A04, хоча ці задачі стоять далі в черзі. Рольові контрприклади записуються, gate 3 лишається червоним, 0.4 не позначається готовим. Реальні перевірки виконуються ≥1000 разів, без skip. Це не нова архітектурна проблема або новий дефект поза прийнятим аудитом.

Буквальне правило «не рухатися з червоним» несумісне з лінійним порядком майбутніх ще не реалізованих перевірок. Застосовано практичне трактування: не допускаються регресії вже перевіреного, а відомі незакриті залежності зберігають червоний статус. Дозволена звірка 0.5 лише читає копію; після A03/A04 запускається той самий неослаблений набір. Умова перегляду: реалізовані A03/A04; до того ні gate 3, ні продукт не прийняті.


## DR-06 · конкретні права A04

11.09.2026. Прийнята маршрутна матриця з планового пакета зберігається. Окреме право масового експорту — `operations.export_workspace` (CEO/manager; observer відмова навіть із цим permission). Читання документів для manager/observer — `operations.view_document`; завантаження для всіх — окреме `operations.download_document`. CEO має видимість всіх документів. Рівні Document.access_level: operational / management / ceo; старі некласифіковані рядки отримують безпечний default ceo без переписування тексту, bytes або ID. Manager бачить operational/management, observer — operational. Зміна classification та надання permissions лише явно уповноваженим адміністратором.

Manager Transaction GET залишається корисною проєкцією: id/date/direction/category/currency/contract/counterparty/branch/archived_at. Без amount, description та будь-яких зарплатних джерел; закритий Contract FK не розкривається. Закупівельні ціни видимих операцій manager зберігає. Observer не отримує фінансові суми; мінімальний довідник працівників обох ролей не містить кадрових полів.

Історія асистента має owner та visibility_role; legacy NULL не зіставляється навмання. Після пониження ролі її давні приватні повідомлення не віддаються. DELETE архівує власні видимі повідомлення CEO/manager, зберігаючи ID й bytes. Глобальне знищення суперечить master; старий test цього контракту буде замінений сильнішими перевірками збереження історії з окремим поясненням.

Глобальний cache приватних контекстів прибирається: вони будуються через спільну policy для поточного request. Локальні браузерні дані розділяються за користувачем і роллю, старі unscoped записи не видаляються і не переносяться випадковому першому користувачу.

Умова перегляду: погоджена складніша матриця пілотного клієнта або виміряна потреба кешувати контекст. Після цього додаються конкретні grants/ACL чи cache revision з регресіями; shared-DB, нові ролі та автоматична класифікація не вводяться цим рішенням.

Адмінка A04: окремий технічний User без бізнес-груп BoS, з явно наданими native Django permissions. is_staff / is_superuser на бізнес-акаунті не обходять цю межу. Історичні журнали, повідомлення, файли та usage у технічній адмінці лише для читання. Звичайні фінансові форми й A05 команди архівування збережено. Сира /media/ не роздається навіть у DEBUG.

Браузер отримує серверну ревізію користувача, ролі та permissions. При зміні ревізії наступна відповідь закриває робочий екран і його оперативний cache до нового входу. Відмова через відкликання identity має окремий заголовок; звичайний 403 окремої дії не маскується як вихід.


## DR-07 · ідентичність фінансового наміру A06

11.09.2026. Нові ручні Transaction і Salary через HTTP вимагають `Idempotency-Key` (1–128 ASCII літер, цифр або `_ . : -`); native admin має прихований `bos_operation_id`. Ключ належить користувачу й типу команди. Різні ключі означають різні наміри; сума/дата ніколи не є правилом дедуплікації. Той самий ключ порівнюється з канонічним повним payload, включно з валютою та джерельними FK. Незмінний повтор повертає поточний запис з тим самим PK без нового audit; конфлікт payload або зайнята транзакція — 409. Після transient 409 той самий запит повторюється з тим самим ключем.

Нова FinancialIntent зберігає непрозорий hash ключа та payload, PROTECT-посилання на джерело; receipt і запис комітяться разом з audit. Старі рядки не отримують вигаданих ключів. Внутрішній однократний імпорт/fixture може викликати shared command без ключа; це новий факт, гарантія повтору потребує явного operation_id. Виплата Salary уже ідентифікована її PK; ERP — proposal_id. Другий writer не вводиться. Legacy AI helper передає operation_id, але зовнішня модель та її lifecycle лишаються відкладеною C02.

Форма тримає ключ до підтвердженого успіху; помилка мережі не скидає його. Зміна payload або нова форма починає новий намір. Ключі й незбережені фінансові дані не переносяться між користувачами. Перезавантаження сторінки починає нову форму; тривала черга offline-намірів поза A06.

Умова перегляду: погоджений offline workflow або інтеграція зовнішнього клієнта без ідентифікаторів. До цього такий клієнт має отримати явну схему ключів; історичні факти автоматично не зливаються.

## DR-08 · перенесення фактів і кандидати на звірку

У A07 read-only preflight відхиляє неповне покриття, порушення типів/файлів/FK, підтверджені грошові та складські розбіжності й committed FinancialIntent без джерела. Класи `candidate` і `unlinked` із 0.5 залишаються явними попередженнями; самі по собі вони не доводять дубля. Перенос зберігає всі рядки, ID і суми, включно з такими кандидатами; dedup, автоматичного прив’язування та ремонту немає. Це приймання точного переносу, а не людське підтвердження первинних документів. Перегляд рішення: лише якщо новий доказ підтверджує фінансову розбіжність або контракт пілота вводить окремий обов’язковий контроль перед cutover.

Репетиція A07 використовує тільки нові синтетичні джерела й одноразові цілі. Перевірки наступних ID та повторів виконуються на окремій похідній proof-копії; вони не змінюють незмінний snapshot і перенесену контрольну ціль. SQLite-перебудова таблиць зберігає історичний high-water, у тому числі порожньої таблиці. Збереження числових метаданих не означає безперервної нумерації без пропусків.
